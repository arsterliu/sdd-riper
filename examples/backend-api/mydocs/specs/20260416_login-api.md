## §1 目标 (Goal)
实现 `POST /api/login` 接口，完成对用户凭证的验证并签发 JWT，以支持前端进行无状态的鉴权请求。

## §2 范围 (Scope)
**包含:**
- `POST /api/login` 路由及处理逻辑
- 请求体参数验证（email, password）
- 数据库查询（根据 email 获取用户记录）
- 密码哈希对比
- JWT 签发及响应构造

**不包含:**
- 用户注册接口
- 基于 Session 的认证机制
- 忘记密码等相关业务流程

## §3 约束 (Constraints)
- 必须符合 JWT 标准（RFC 7519），负载（payload）中需包含 `user_id`，且不包含敏感信息。
- 不绑定特定框架或语言（如 Java Spring 或 Node.js Express），逻辑应具备通用性。
- 密码比对必须使用恒定时间的哈希比较算法，防止时序攻击。

## §4 风险 (Risks)
- **风险1：JWT 密钥泄露** 
  - *缓解措施:* 密钥配置不应硬编码，必须通过环境变量注入，并定期轮换。
- **风险2：防暴力破解 (Brute-force Attacks)** 
  - *缓解措施:* 推荐使用限流中间件（Rate Limiting）对单个 IP 失败尝试进行限制。

## §5 验收清单 (Checklist)
- [x] 正确的邮箱和密码返回 `200 OK` 及有效的 `token` 字符串。
- [x] 错误的邮箱返回 `401 Unauthorized` 和 `invalid_credentials`。
- [x] 错误的密码返回 `401 Unauthorized` 和 `invalid_credentials`（避免信息泄露）。
- [x] 缺失请求参数时返回 `400 Bad Request` 及具体的参数错误提示。
- [x] 生成的 JWT 可被正常的 `verify` 函数解析，且 `user_id` 匹配。

## §6 调研结果 (Research Findings)
- **数据库查询方式:** 采用现有的 `UserRepository.findByEmail(email)` 进行用户获取。
- **密码处理:** `password_hash` 采用 bcrypt 加密，需调用 `bcrypt.compare(password, hash)` 方法进行比对。
- **JWT 生成:** payload 为 `{ "user_id": user.id }`，配置参数为 `{ "expiresIn": "1h" }`。

## §7 方案创新 (Innovate Options)
- **方案A：Session 验证机制** 
  - *优点:* 易于管理用户在线状态（例如服务器端登出）。
  - *缺点:* 扩展性较差（分布式部署需要集中存储），与前端要求不符。
- **方案B：JWT (JSON Web Token) 无状态认证** (✅ 选中方案)
  - *优点:* 扩展性强，无需服务器存储状态，前后端分离友好。
  - *缺点:* Token 无法主动撤销（需使用黑名单或较短过期时间结合刷新机制）。
