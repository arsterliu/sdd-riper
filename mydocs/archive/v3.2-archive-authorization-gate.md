## Intake

### Requirement
requirement: 修复归档授权语义不清：归档就绪不得被表达为立即归档指令，sdd archive 必须具备独立、显式、可审计的用户授权门禁。
goal: 分离归档就绪与归档授权，统一 next、resume、Console 与 archive 命令语义，防止自主 Agent 未获明确授权直接归档。

### Constraints
constraints: CLI 不自动归档；归档必须由用户明确授权；保持 Spec 控制面与可审计性；同步更新测试和文档；当前问题与仓库代码作为 context，无外部参考资料。

### Scope

包含 `spec-state` / workflow 的归档等待状态、`next` / `resume` / `cruise` 与 Cruise Run 输出、`validate` 语义、Console 展示、`archive` 命令授权门禁、CLI 帮助、自动化测试与 GUIDE/README/TEAM-GUIDE/协议及生成的 Agent 指令。排除身份认证服务、远程审批系统、Console 写操作和历史归档文件迁移。

### Risks

- 归档会移动 Spec 及其 Design、Execute Log、Learning，并更新 archive index，属于不可逆语义较强的文件系统操作。
- 若只改提示而不改 `archive`，Agent 仍可直接调用命令绕过授权。
- 若只改 `archive` 而不改状态投影，自动运行 Agent 仍会被错误引导，形成反复失败或伪造授权的压力。
- 既有脚本直接调用 `sdd archive` 将受到有意的破坏性接口变更；本任务不以兼容旧调用为目标。
- `human:<name>` 与授权证据是调用者声明，CLI 无法验证其是否真的来自对话中的人类；若 Agent 协议未同步禁止自行构造授权参数，技术参数门禁仍可能被伪造。
- 若授权失败发生在 `archiveDir` 创建之后，即使命令拒绝归档也会留下文件系统副作用，违背 fail-closed 的零写入承诺。

### Initial Acceptance Hints

- 完成条件满足时，`next` 和 `resume` 只能表达“等待用户归档授权”，不得表达立即执行 archive。
- Console 必须区分“完成条件满足”与“已归档”，不得把前者显示为动作指令。
- 未携带合法、显式、可审计的人类授权时，`sdd archive` 必须在任何写入前 fail-closed。
- 合法授权与完成条件同时满足时才允许归档，并在归档产物中留下审计证据。
- 所有消费者必须读取同一中央状态事实，回归测试覆盖成功、缺授权、非法授权与未就绪场景。
- Agent 协议必须明确：只有当前对话中获得用户明确授权后才能传递归档授权参数，禁止根据 Ready、PASS、Plan Approval、Challenge 或历史授权自行构造。

## Research

### Requirement Review

用户报告的不是 CLI 自动执行缺陷，而是控制面语义缺陷：自主主 Agent 会把 `PHASE_HINT: archive` 当作下一条执行指令。修复必须同时约束“路由提示”和“真正写命令”，否则只能降低误触概率，不能建立门禁。

### Findings

1. `src/core/spec-state.js` 在 Challenge/Learning 等门禁全部通过时固定返回 `target: Ready`、`action: archive_ready`、`archiveReady: true`；这里的 `archiveReady` 实际只代表完成条件满足。
2. `src/commands/next.js` 原样输出 `NEXT_ACTION: archive_ready`，形成动作式接口。
3. `src/commands/resume.js` 将 `archive_ready` 映射为 `PHASE_HINT: archive`；同文件还把 `repair_learning_check` 映射为 `archive`，进一步混淆等待学习与归档动作。
4. `src/web/console.js` 把 `ready` 展示为 “Ready to archive”；`spec-index` 直接投影中央 WorkflowState，因此 UI 继承了同一语义。
5. `src/commands/archive.js` 只调用 `validateSpec(..., { archiveReady: true })` 并检查 `workflowState.archiveReady`，随后直接创建/移动/删除文件；没有独立授权输入或审计字段。
6. `bin/cli.js` 的 archive 接口只有 `--force`；现有测试普遍假设满足完成门禁即可归档。
7. v2.5 的中央状态设计刻意统一了消费者，但把 `archive_ready` 同时用作“事实”和“动作”。本任务应保留单一状态源，同时拆分事实、等待状态与副作用授权。
8. `src/core/workflow.js` 对外包装中央状态；`src/commands/cruise.js`、`src/core/cruise-run.js` 及生成的 Claude Prompt 传播 `nextAction`，同样可能被自主循环解释为执行动作。
9. `src/commands/validate.js` 的 `archiveReady` 选项和 `ok` 结果表示完成质量门禁，而非归档许可；设计中必须保留这个事实能力并重新命名或明确语义，不能因新增授权而删除完成校验。
10. `src/core/project-indexer.js`、`src/commands/console.js` 和 `src/web/console.js` 将 `phase=ready` 用于数量、筛选、详情与 Validate 文案；变更 phase/nextAction 会影响 Console API 和测试夹具。
11. 生成/安装的 Agent 配置与 `protocols/`、README、GUIDE、TEAM-GUIDE 必须同步禁止 Agent 自行构造授权声明；否则 CLI 参数只是形式门禁。

### Open Questions

- 一次性授权记录写入归档 Spec 的固定字段后，archive index 是否也需要摘要展示授权人，还是只以归档 Spec 为规范 source of truth？

### Assumptions

- “明确授权”必须来自 `human:<name>`，Agent 自批不满足归档授权。
- 授权不能由完成门禁、Challenge PASS、Plan Approval 或 `--force` 推导。
- CLI 无法验证对话真实性，但可以要求调用者提供结构化人类身份与非空证据，并将其写入不可变归档制品供审计。
- 不兼容旧的无授权 `sdd archive` 调用是预期的 fail-closed 变化。
- 采用一次性 `archive` 调用参数，而不把可复用授权预先写入 active Spec；后者会在制品继续变化后产生陈旧或可重放许可，除非再引入摘要绑定、失效和消费协议。
- 授权校验必须先于创建 archive 目录、读取后写入目标制品或任何其他文件系统变更；`--force` 只处理目标覆盖，不能绕过授权。

## Innovate Options
<!-- Compare at least two options. Write the option analysis in Chinese. -->

### Option A: archive 调用时一次性授权（Selected）

`sdd archive` 强制要求 `--authorized-by human:<name>` 与 `--authorization-evidence <text>`。授权在本次调用中校验，成功后由 CLI 生成时间并把三项记录写入归档 Spec。中央状态只表达 `request_archive_authorization`，不持久化可复用许可。

优点：授权与不可逆副作用在同一调用中绑定；active 制品变化不会造成陈旧授权；失败可在任何写入前拒绝；实现与审计边界清晰。缺点：CLI 只能审计声明，不能证明调用者确为人类，必须依赖 Agent 协议禁止伪造。

### Option B: 先执行 authorize-archive，再执行 archive

新增命令把授权写入 active Spec，后续 `archive` 读取。优点是 Console 可以展示已授权等待执行。缺点是授权后 Spec/Design/Log 仍可变化，必须引入内容摘要、授权失效、一次消费与并发语义；否则许可可陈旧或重放。当前需求不值得引入这套状态机。

### Option C: archive 交互式确认

`archive` 在 TTY 中询问 yes/no。优点是人工体验直观。缺点是自动化和 Agent 环境未必有交互 TTY，确认结果难以结构化审计，且 Agent 仍可能自动输入确认。不能作为统一门禁。

Selected Option: Option A。它以最小状态面实现一次性、显式、可审计授权，并把真实身份认证的能力边界如实留在协议层。

## 目标摘要
Execute 与 Completion Verification 已完成：完成就绪、等待授权和归档副作用已拆分。

## 最终方案
ADR-3.2：采用 archive 调用时一次性授权。`archive` 必须同时收到 `--authorized-by human:<name>` 与 `--authorization-evidence <single-line-text>`；不增加持久化 authorize 命令，不把授权写入 active Spec。完成后由 CLI 生成授权时间并把授权记录写入归档 Spec。

## 关键约束
继续以 Spec 为控制面，以中央 evaluator 为唯一完成事实源；保留“完成条件满足”的独立事实，但不得把它命名或投影为立即归档动作；归档授权仅接受一次性人类声明，不复用 Plan/Challenge；CLI 不提供真实身份认证，因此 Agent 协议也是信任边界的一部分；保持 Console 只读；不迁移历史 archive。

## 坑点与风险
参数可被恶意 Agent 伪造，这是无身份系统的固有限制；通过稳定门禁、不可伪装为自动推导的协议措辞和归档审计记录降低风险。一次性授权避免陈旧许可，但调用者每次重试都必须重新确认其仍持有当前用户授权。改变 phase/action 是破坏性接口变更，但比保留歧义 alias 更纯粹、可审计。
