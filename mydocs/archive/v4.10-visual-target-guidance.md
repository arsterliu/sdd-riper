## Summary

澄清现有视觉验证中的 baseline 语义：它是当前 Spec 冻结并经人工认可的目标 UI PNG，而不是需要跨版本维护的历史基线库。更新人类指南与 Agent 引导，使 Agent 能根据材料是否可直接与浏览器截图比较，解释并推荐 `direction` 或 `fidelity`，同时保持现有视觉验证实现与安全边界不变。

## Intake
requirement: 统一视觉指南与 Agent 引导：将 baseline 明确定义为当前 Spec 冻结且经人工认可的目标 UI PNG；新 Spec 可直接采用最新 UI 设计图作为目标，不要求旧页面截图，也不建设长期 baseline 管理、自动生成、版本历史或回滚能力；AI 根据材料可比性引导选择 direction 或 fidelity。
goal: 让用户和 Agent 准确理解现有视觉验证模型，降低 baseline 概念负担，同时保持严格视觉证据与审计边界。
constraints: 优先调整当前文档、Skill/托管指令及必要测试；不改变现有像素比较、Visual Run、Provider、安全门禁和历史归档；不新增 baseline 管理系统。

## Requirement Review

用户确认当前实现与期望方向本质一致：每个 UI 迭代都可以把最新设计图作为当前 Spec 的目标图，开发完成后的页面截图与该目标图比较；旧页面截图只是可选的现状理解材料，不是视觉验收的必需输入。本任务不是重做视觉验证，而是消除“baseline 必须长期维护”的误解，并让 AI 用材料可比性而不是术语负担引导用户。

## Findings

1. 当前 fidelity 合同已经要求每个 scenario 引用 Context 内的 baseline，并且 baseline 必须为 `approved`；文件路径同时经过词法 containment、存在性和 realpath containment 校验。因此它天然可以承载“当前 Spec 的目标 UI PNG”。
2. Visual Run 以 baseline 内容摘要判断证据是否过期；目标图被替换后旧 Run 变为 `stale`。这是单个 Spec 内的审计冻结机制，不是跨 Spec 的版本管理。
3. 当前文档把 baseline 描述为需要人工创建、更新和批准，但没有优先解释“它就是本次 Spec 认可的目标 UI 图”，容易让用户误解为需要维护独立的长期 baseline 资产。
4. 当前 `direction` 允许 baseline 保持 `pending` 并进入 Plan；`fidelity` 才要求 approved baseline 并支持后续像素验证。两者的选择应由设计材料能否形成确定的页面状态、视口和可比较 PNG 决定。
5. 旧页面截图不属于 fidelity 合同的必需字段。Agent 可以从代码理解现状，并且仅在环境可用、所需平台权限已获授权时读取运行页面；最新设计图可以直接承担目标定义。只有用户需要解释改动前后差异时，旧截图才作为辅助 Context。
6. 现有像素比较、Visual Run、Provider、静态映射、安全 containment、人工批准与 stale 规则均可复用，无需新增 baseline 自动生成、候选、替换、版本历史或回滚能力。

## Open Questions

## Assumptions

- “最新 UI 图”指当前 Spec 中由用户认可、能够代表目标页面状态的可解码本地 PNG。选择 `fidelity` 时，它必须与 scenario viewport/current screenshot 尺寸一致，并且 route、state、测试数据、字体和资源足够稳定；如材料只是风格、布局方向或无法与浏览器截图直接对齐，则由 Agent 推荐 `direction`。
- `fidelity` 的目标图仍需满足现有 scenario、route、state、viewport、sourceId、人工批准和 Provider 约束，不能因为改称“目标 UI 图”而绕过严格合同。
- 文档可在人话叙述中优先使用“目标 UI 图”，但精确协议、JSON 字段、CLI 输出和错误码继续使用 `baseline`，避免生产协议与历史制品迁移。
- 本任务只影响当前指南、Agent 真源及其受控投影和治理测试；历史归档保持只读。

### Option A: 只调整人类指南

- 修改 README、GUIDE、REFERENCE、TEAM-GUIDE，把 baseline 解释为“当前 Spec 的目标 UI 图”，补充旧页面截图可选以及 `direction` / `fidelity` 的判断方式。
- 优点：范围最小，不触及 Agent 真源。
- 缺点：AI 实际加载的 SKILL 与托管指令仍可能继续使用抽象 baseline 术语，指南与行为存在再次漂移的风险。

### Option B: 人类指南与 Agent 真源同步（Recommended）

- 在 Option A 基础上，同步 SKILL、Agent 配置生成源、必要协议投影及治理测试；通过受控生成入口刷新托管区块。

- 优点：用户说明与 AI 实际行为一致，不改变 runtime/schema，也不引入 baseline 管理。
- 缺点：涉及多个已有未提交改动的文件，Execute 必须采用窄增量补丁并验证受控区块外内容不变。

### Option C: 重命名运行时协议

- 将 schema、CLI 和 Run 中的 `baseline` 改成 `targetImage` 或 `designReference`。
- 优点：字段名更直观。
- 缺点：会引入 schema、历史兼容和迁移成本，与“当前实现已经符合方向”的结论相悖，因此不推荐。

Selected Option: Option B。同步人类指南与 Agent 真源，但保持运行时协议和 `baseline` 字段不变。
