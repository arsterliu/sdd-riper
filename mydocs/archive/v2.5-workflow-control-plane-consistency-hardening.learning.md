## Learning Record

Source Spec: mydocs/specs/v2.5-workflow-control-plane-consistency-hardening.md
Trigger: Step 4 分类优先级 BUGFIX，以及七轮独立 Challenge `FAIL_CODE` 连续暴露中央 evaluator、lightweight Acceptance、direct AC Coverage、多步骤 Coverage、L3、full-only gate 与位置/状态分歧。
Observed Problem: 一方面，`Learning Record is required because: Execute Log deviation` 被宽泛来源词误分为 FAIL_LOG；另一方面，validate、status、spec-index/console 分别计算 gate，使合法 PASS 携带错误 Evidence 时出现 validate 阻断、展示层却显示 OK 的分歧。
Root Cause: 控制决策依赖自由文本匹配和多处重复 predicate，所谓 evaluator 没有直接拥有原始 artifact facts，只在下游重新包装其他组件的结论。
Decision Rule: 控制面的权威 evaluator 必须从规范化原始 snapshot 直接产出结构化 gate/blocker/phase；消费者只适配结构化结果，不重新解析 Markdown 或 message。当诊断文本仍作为补充输入时，明确 gate 语义必须优先于上下文来源词。
Applies When: 状态机、CLI 路由、日志分类或告警聚合需要从复合诊断文本确定唯一 gate、phase 或 backtrack target 时。
Does Not Apply When: 文本只用于展示且不参与任何控制决策，或调用方已经获得稳定的结构化 gate/blocker code 时。
Recommended Action: 为明确 gate 建立优先级表和冲突回归测试；把 message 限制为展示字段，逐步让所有消费者只读结构化 `blocker.gate` 与 `blocker.target`。
Evidence: 首轮全量测试 184/185 暴露 Learning→Execute 误路由；Challenge iteration 1 复现 PASS+错误 Evidence 的跨消费者分歧；iteration 2 发现 lightweight/project-indexer 绕过详细 Acceptance；iteration 3 发现 direct completion 未逐项核对声明 AC；iteration 4 发现标准 SKIPPED 字段被 `Scenarios:` 截断，且历史 PASS 可掩盖最新 FAIL/SKIPPED；iteration 5 发现 L3 只在 full validate 生效；iteration 6 发现 placeholder、diff-base、Innovate 与 micro Plan 仍是 full-only gate；iteration 7 发现 active 文件可用 archived 状态隐藏。补齐 pure evaluator、mode-specific/Git、位置/状态、Acceptance、AC Coverage、最新结果、L3 与 status blocker 状态矩阵后，全量测试 197/197 通过。
