## Technical Design

Selected Option / ADR:
ADR-QP-001：采用“内建版本化 Policy Catalog + 纯 Quality Planner”，并以显式只读命令 sdd quality plan <project-dir> 暴露结果。

Decision: Catalog 只定义技术栈中立的质量关注点、证据 capability 与 role/relation 的贡献规则；Planner 只读取选定 Spec、该 Spec 绑定的精确 Profile revision、affected-units、AC 与既有 e2e readiness，生成一次性输出。它不写入 Spec、Profile、Provider、Run 或业务工程，不触发 next、resume、Plan、Execute、Archive、verify init 或 verify run。

Rationale: 该方案把 Profile 工程事实、质量策略和 Provider/Adapter 执行合同分离，同时能以稳定、可测试的规则解释前端、后端、契约、库和工具改动的证据关注点。CLI 置于 quality 命令组而非 verify 命令组，避免把解释性规划误解为验证执行。

Rejected: 任务 Spec 内可编辑 Policy 区块会与 AC 竞争控制面；从 frameworks、commandRefs 或 Provider 配置启发式推断会把事实或执行配置误升格为质量要求。两者均不采用。

Requirement Traceability:

下表将已确认的产品边界逐项约束到可实现、可测试的设计决策，任何后续 Plan 步骤都必须回链这些决策。

| Requirement | Design response |
| :--- | :--- |
| AC 是唯一验收真相 | Planner 只投影 AC 到 Verification Capability；不保存 coverage、通过/失败、审批或状态，不把 policy focus 标为“已覆盖”。 |
| Profile 必须是精确历史事实 | 只用 Spec 的 project-profile-revision 与 project-profile-digest 调用既有 resolveRevision；绝不读取或回退到 profiles/current.json。 |
| 前后端、契约和跨单元均可解释 | Catalog 以 role 与 depends-on relation 生成稳定的 policy focus 及原因，不依赖框架名或目录启发式。 |
| Provider/readiness 不能形成第二状态机 | 仅所有 e2e AC 都绑定 Provider 时，原样嵌入一次既有 required/configured/blocked/ready 聚合快照；其他 capability 不伪装为 Provider 就绪。 |
| fail-closed、无自动动作 | 缺精确 Profile、范围歧义或引用损坏以诊断和 exit 2 终止投影；不 detect/review/confirm Profile，不安装、init、run、联网或执行项目命令。 |

Impact Scope:

影响只限于 SDD-RIPER 的只读 CLI、内部规划模块、测试和使用文档；既有执行合同与用户业务工程均不在本次变更范围内。

In Scope:

- 新增 quality CLI 命令组及 quality plan 子命令。
- 新增纯 Catalog、scope 归一化、AC 映射与 Planner 模块，以及只读命令适配层。
- 复用既有 Spec 选择、Profile revision 解析与 e2e readiness 读取。
- 新增 node:test 覆盖，并更新 README.md、GUIDE.md 的使用边界与命令说明。

Out of Scope:

- 新 Adapter、Playwright MCP、Custom Adapter Registry、Provider Schema 变更、Console UI、visual/a11y/performance runner。
- 项目级可编辑 Policy 配置、Quality Plan 制品、审批、状态迁移、归档门禁、自动修改 AC 或 Plan。
- Profile detector/confirm 行为、verify init/run、Provider 安装/解析预检、业务工程命令和任何网络调用。

Context / Boundary:

输入由四层组成，且依赖只沿单向流动：不可变 Profile facts → 内建 Policy Catalog → 活动 Spec 的 AC/affected-units → 已有 Provider/Run readiness。Catalog 不能反向修改 facts；Planner 不能反向修改 AC；readiness 只能解释既有 e2e Provider/Run 事实，不能触发执行。

命令对活动 Spec 的选择沿用现有语义：--spec 指定路径、--name 按 Spec 引用解析、两者都省略时选择确定性的最新活动 Spec；同时传入两者属于 usage error。词法 `<docs-root>/specs` 与其项目内 realpath root 必须分开校验，因此指向项目内目标的 docs root/specs 链接仍可用。无论 --spec 使用相对还是绝对路径，它的词法路径与存在时的 realpath 都必须位于相应的根内；外部路径、目录自身和符号链接逃逸均以 spec_path_escape / exit 2 拒绝。默认选择在读取任何候选的 stat 或 frontmatter 前，先逐项执行这两层 containment；发现逃逸候选即 fail-closed，绝不读取其外部内容。命令从一次读取的安全 Spec 文本构建快照，之后所有派生计算只使用该快照与精确 Profile revision。它不会把任何输出写回输入。

AC Input Rule: Planner 的 AC reader 必须先忽略 HTML 注释，再识别 AC-### 区块；模板中的注释示例不能成为 acFacts、capability mapping 或 diagnostic。该清洗只服务 Quality Plan 自身的解释输入，不改写 Spec，也不改变既有 readiness 的实现或语义。

Domain Model:

- Profile Fact：已确认 revision 中的 unit、roles、relation、framework、manifest 与 evidence；本功能只消费 unit id、roles 和 relation 的 from/to/kind。
- Quality Policy：内建、版本化的规则目录；只表达“某类变更值得关注哪些证据”，不是验收条件、命令或 Provider 配置。
- Policy Focus：由有效范围内的 role 或双端 relation 产生的质量关注点，附带来源理由与建议 capability。
- Verification Capability：unit-evidence、integration-evidence、e2e-evidence、manual-evidence，是证据语义，不是 Adapter、命令或通过结论。
- AC Mapping：已有 AC 的 Verification 原义映射到恰好一个 capability；因为 AC 不携带 unit，映射不得声称某个 Policy Focus 已被覆盖。
- Provider Readiness：仅 e2e Provider 路线的既有聚合快照；configured 只表示配置存在，绝不解释为可执行。

Architecture View:

~~~text
调用者
  │ sdd quality plan <project-dir> [selector] [format]
  ▼
Quality Command Adapter（只读、格式化、exit 语义）
  ├─ Spec Resolver ────────────────> 活动 Spec 文本与前置元数据
  ├─ Exact Profile Resolver ───────> store.resolveRevision(digest)
  ├─ Scope Normalizer ─────────────> declared/effective units + diagnostics
  ├─ Policy Catalog v1 ────────────> policy focus / capability 规则
  ├─ AC Mapper ────────────────────> AC facts / Verification Capability
  └─ Existing Readiness Adapter ───> 仅全部 e2e AC 有 Provider 时的既有快照
                                      （其 fresh Run 路线可间接使用既有固定 Git 读取）
  ▼
临时 text / JSON Quality Plan
~~~

Planner 是纯函数边界：接收已解析的 Spec、Profile、Catalog 和可注入的 readiness reader，返回普通对象；它不导入 workflow、archive、verify command 或 child_process。Command Adapter 才能读文件和调用现有 readiness，但也不写文件。

Data Model / Schema:

首版输出 Schema 固定为 schemaVersion: 1，内建目录固定标记 policyVersion: "1"。两个版本独立演进：输出字段不兼容时提升 schemaVersion；规则语义变化时提升 policyVersion。所有数组按显式稳定规则排序，诊断不包含时间戳或机器相关路径以外的易变数据。

~~~json
{
  "schemaVersion": 1,
  "policyVersion": "1",
  "source": {
    "specPath": "mydocs/specs/v3.5-task.md",
    "taskName": "task",
    "profile": {
      "revision": "profiles/revisions/sha256-<digest>.json",
      "digest": "sha256:<digest>"
    },
    "declaredAffectedUnits": ["web", "api"],
    "effectiveAffectedUnits": ["web", "api"]
  },
  "acFacts": [
    { "acId": "AC-001", "verification": "unit", "provider": "", "manualEvidence": "" }
  ],
  "policyFocus": [
    {
      "id": "frontend-behavior",
      "recommendedCapabilities": ["unit-evidence", "e2e-evidence"],
      "reasons": [{ "kind": "role", "unitId": "web", "role": "frontend" }]
    }
  ],
  "acMappings": [
    {
      "acId": "AC-001",
      "verification": "unit",
      "verificationCapability": "unit-evidence"
    }
  ],
  "e2eReadiness": {
    "state": "required",
    "requiredProviders": ["web-e2e"],
    "missingProviders": ["web-e2e"],
    "issues": ["Verification Provider is not configured: web-e2e."]
  },
  "diagnostics": [
    { "code": "role-unknown", "severity": "attention", "message": "..." }
  ]
}
~~~

source.profile、effectiveAffectedUnits、policyFocus、acMappings 与 e2eReadiness 在无法建立可靠输入时分别为 null 或空数组；acFacts 仍保留从 Spec 读到的原始 AC 事实，帮助用户恢复输入但不形成质量结论。e2eReadiness 只有存在 e2e AC 且每个 e2e AC 都声明 Provider 时才出现；它是整个 e2e 集合的一次既有快照，不能被误读为任一 Provider 或 AC 的单独“ready”证明。

Catalog v1 的固定映射如下：

| Source | Policy Focus | Recommended Capabilities |
| :--- | :--- | :--- |
| frontend role | frontend-behavior | unit-evidence, e2e-evidence |
| backend role | backend-behavior | unit-evidence, integration-evidence |
| contract role | contract-compatibility | integration-evidence |
| library role | consumer-compatibility | unit-evidence, integration-evidence |
| tool role | tool-behavior | unit-evidence, manual-evidence |
| 有效范围内双端均命中的 depends-on | cross-unit-boundary | integration-evidence |

既有 Verification: unit | integration | e2e | manual 分别且唯一映射为 unit-evidence | integration-evidence | e2e-evidence | manual-evidence。unknown role 与未映射 relation 不推断 capability，只生成诊断。

Scope Normalization:

1. affected-units: project 单独出现时，以精确 Profile 的全部 unit id 按字典序稳定展开。
2. 显式 unit id 按声明顺序首次出现稳定去重，并必须存在于该精确 Profile。
3. project 与任意显式 id 混用生成 scope-ambiguous，不合并、不扩范围，投影以 exit 2 结束。
4. 一个 unit 的 known roles 按 Catalog 顺序合并 capability，并保留每个 role/policy reason；unknown 只产生 role-unknown。
5. relation 不扩大范围：双端均在有效范围内才加入跨单元 focus；仅一端在范围内生成 related-unit-out-of-scope；触及有效范围但未被 Catalog 映射的 relation kind 生成 relation-kind-unmapped。

Data Migration / Backfill:

无。Quality Plan 不持久化，没有待迁移数据、历史记录回填或 current pointer 更新。

Interface Contract:

~~~text
sdd quality plan <project-dir> [--spec <path> | --name <slug>] [--format text|json]
~~~

--format 默认为 text。text 输出按固定字段顺序展示 source、policy focus、AC mapping、可出现的 e2e readiness 和 diagnostics；JSON 严格输出上述临时 Schema。两种格式都不得输出 PHASE_HINT、NEXT_ACTION、任务通过/失败、Plan/Archive eligibility 或任何可被 Agent 当作执行指令的文本。

Exit Semantics:

- exit 0：已形成可审阅投影；Provider 缺失、configured、blocked、role-unknown、relation 关注点等均作为事实性 gap/diagnostic 输出，不改变 SDD workflow。
- exit 2：无法建立可靠输入，例如 profile-required、scope-ambiguous、不完整或损坏的精确 Profile 引用、未知 affected unit、Spec 不可读，或实际 e2e freshness 快照无法读取。JSON 仍输出结构化 diagnostics；text 明确给出恢复指引。
- exit 3：命令用法错误，例如非法 --format 或同时提供 --spec 与 --name，并以 [SDD_QUALITY_USAGE] 标识。

API Protocol:

这是本地 CLI 合同，不引入 HTTP、MCP 或外部协议。quality 命令组单独设置 usage 错误处理，遵循 profile/verify 的现有 exit 3 习惯，但不复用 Provider 初始化或运行参数。实现文件拟分为 src/commands/quality.js、src/quality/catalog.js、src/quality/planner.js、src/quality/input.js 与相应测试；最终文件粒度由 Plan 保持在这些模块边界内。

State / Concurrency:

本命令没有配置或制品写入，因而没有锁、合并、重试或并发成功语义。每次调用以读取到的 Spec/Profile/配置/Run 快照独立计算；并发外部写入导致的不可读或不一致输入按 fail-closed 诊断处理，调用者可在输入稳定后重新执行。不可变 Profile revision 消除了对 current.json 竞争的依赖。

Planner 在解析 AC 后才决定是否读取 readiness：无 e2e AC 时绝不调用它，也绝不把现有“无 e2e 时 ready”传播为 Provider 结论；任一 e2e AC 缺少 Provider 时只报告未绑定 gap，并抑制聚合 readiness 快照，避免把全局状态错误归因给已绑定路线。只有全部 e2e AC 已 Provider-bound 时，才原样读取一次既有 readiness.inspect 结果。

Failure Modes:

| Condition | Output / Recovery |
| :--- | :--- |
| Spec 未绑定 confirmed Profile | profile-required、已有 acFacts 和“先完成 detect/review/confirm，再新建或重新绑定任务”的恢复指引；exit 2；不自动调用 Profile 命令。 |
| Profile revision/digest/affected-units 不完整、损坏或 unit 不存在 | 精确输入诊断；exit 2；不使用 current pointer 或近似 Profile。 |
| project 与显式 unit 混用 | scope-ambiguous；exit 2；要求用户在 Spec 中显式修正范围。 |
| unknown role、单端 relation 或未映射 relation | 保留可形成的其余投影，输出 attention diagnostic；exit 0；不猜测 role 或扩大范围。 |
| e2e AC 无 Provider | 输出 e2e 未绑定 gap；不生成 Provider readiness。 |
| e2e Provider 未配置、配置损坏、Run 缺失或过期 | 原样展示既有 required、configured 或 blocked 快照；不 init、run、安装或自动降级。 |
| 既有 freshness 的固定 Git 读取不可用 | 不能可靠形成该 e2e 快照，输出 readiness-unavailable；exit 2；不尝试任意 Git 或项目命令。 |

Security / Permission:

该命令只读项目内已有输入，且所有选定 Spec 必须通过 `<docs-root>/specs` 的 lexical + realpath containment；两个根分开计算，允许 docs root/specs 链接解析到项目内目标，但拒绝解析到项目外。无 selector 的候选枚举也必须在读取 stat 或 frontmatter 前完成 containment，发现任一逃逸候选即 fail-closed；它不读取项目外伪造 Spec 或链接目标。它不执行 commandRefs、npm/pnpm/yarn、Provider/Adapter、浏览器、网络、安装程序或项目脚本，也不创建锁、临时文件或配置。唯一允许的子进程路径是当且仅当既有 readiness.inspect 为 fresh Run 检查而间接触发的、固定 argv 的本地 git rev-parse、git diff、git ls-files；Quality 模块自身不得导入或调用 child_process，不得新增、参数化或扩展该例外。

Observability:

每个 policy focus 保留 role 或 relation 的 reason，每个 AC mapping 保留原始 Verification 和唯一 capability，e2e 输出保留原 readiness 的 state/requiredProviders/missingProviders/issues。source 同时打印 exact revision/digest、声明范围和有效范围，使调用者能复现解释。诊断使用稳定 code、severity、message 和必要的恢复指引；不产生遥测、日志文件或 Run。

Performance / Capacity:

除可选的一次既有 e2e readiness 读取外，计算复杂度为 O(unit + relation + AC)，内存仅保留单次投影。Profile/Spec 读取不扫描业务工程；不触发 detector。Run 较多时的读取成本沿用现有 readiness 行为，不在 v3.5 新增缓存或后台刷新。

Compatibility / Rollback:

这是加法式 CLI 与内部模块变更：不改写现有 Spec frontmatter、AC Verification 取值、Provider Contract、Adapter Registry、Run Schema、workflow 路由或 archive 规则。未调用 sdd quality plan 的项目行为完全不变。回滚只需移除 quality 命令、模块和文档；因为没有持久化 Policy/Plan 数据，不需要数据回滚。未来若扩 Catalog 或输出，必须用 policyVersion/schemaVersion 明示兼容边界，且不得追溯重解释历史 AC。

Test Strategy:

- tests/quality-planner.test.js：Catalog v1 的 role/relation 贡献、capability 唯一映射、稳定去重与排序、project 展开、范围混用、unknown role、relation 边界及 exact revision 而非 current pointer。
- tests/quality-cli.test.js：quality plan 的 selector、text/JSON 合同、exit 0/2/3、profile-required、损坏引用、无副作用和帮助/usage；覆盖相对/绝对越界、显式文件链接逃逸、默认选择在读取外部内容前拒绝逃逸候选，以及项目内 docs root 链接的合法解析。
- readiness 集成夹具：覆盖 named e2e Provider 的 required/configured/blocked/ready 原样投影、e2e 未绑定 Provider、manual-only、无 e2e 和 unit/integration；断言 manual/unbound/无 e2e 从不输出 Provider ready。
- 安全回归：以依赖注入或子进程监视证明无 e2e 时不调用 readiness；质量模块不引入 child_process；仅有 fresh e2e 路径可经过既有固定 Git freshness 读取，禁止 Provider/项目命令、网络与写入。
- 读取前后比较夹具文件树与关键 Spec/Provider/Profile/Run 字节，证明命令不写入；最后执行 npm test 覆盖既有 Profile、verify、workflow、archive 与新增测试。

Risks / Trade-offs:

首版故意不提供项目级策略覆盖，因此少数团队的特殊质量要求只能先通过 AC/Plan 显式表达；这是用可审计、技术栈中立的核心边界换取可预测性。Policy focus 与 AC 不建立自动覆盖关系，意味着输出不能替代人工审阅 AC 是否充分；这是避免第二验收真相的必要代价。现有 readiness 是聚合状态，首版不伪造 per-Provider/per-AC readiness；未来若真实需求出现，应先扩展既有 Verification Contract，而不是在 Quality Planner 内部复制状态机。
