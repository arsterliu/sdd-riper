## Summary
当前处于 Innovate，目标是把只控制 Plan Gate 的半自动策略改为语义一致的 `auto | supervised | human` 三档模式。
现状证据表明 Plan 审批、Cruise 开关、风险停机、reviewer 授权和归档授权分别由不同规则控制，导致配置名与真实体验不一致。
本任务将统一配置、状态投影、CLI/Console 输出、Agent 指令和测试，同时保留独立审查、防伪、失败回退及不可委托安全边界。
旧配置的处理方式与 human 模式的审批粒度尚待方案阶段确认；Research 不预设静默兼容。

## Intake

### Requirement
requirement: 将现有仅控制 Plan Gate 的 APPROVAL_POLICY 半自动混合模式，收敛为语义清晰的 auto、supervised 与 human 三档模式：auto 在任务范围授权后自动推进；supervised 在 Research 阶段按需授权，并在 Plan 获得人工批准及同次明确的后续自动推进授权后自动推进；human 在关键治理门禁由当前用户逐次审批。自动路径覆盖计划内实现、验证、Challenge 与有界修复，正常停在最终归档授权；三档均保留审计证据、独立审查、防伪、失败回退与不可委托安全边界，并明确旧配置的兼容或迁移策略。
goal: 让配置名称、运行行为和用户体验一致，避免 agent 模式下仍频繁索要无必要批准。

### Constraints
constraints: 不削弱归档授权、不可逆操作、范围扩张、Profile digest 和独立审查真实性等安全边界；不得静默重写历史制品；ui-impact=no。

### Scope

- 定义一个项目级 `auto | supervised | human` 工作流治理策略，并让 Plan Gate、阶段路由、Cruise、reviewer 调度提示和人类文档使用同一语义。
- `auto` 在 Spec 范围确认并完成一次任务级授权后，自动启动 Research reviewer，并在 Plan 未越界时推进 Execute、验证、Challenge、计划内修复与 Learning Check，正常停在归档授权。
- `supervised` 在 Research 阶段按需取得 reviewer 授权，Plan 完成后由用户一次批准并授权后续计划内自动推进；`human` 在每个关键治理阶段转换前要求当前用户批准。
- 明确不可委托停机点：最终归档、不可逆或高风险操作、计划外范围扩张、Profile digest 确认，以及无法由项目策略安全预授权的外部能力。
- 覆盖 `.sdd-config`、治理默认值/读取、workflow 状态、CLI/Console/Run ledger 投影、生成的 Agent 指令、人类文档和回归测试。
- 提供 AI 优先的模式选择与切换引导：创建 Spec 时说明项目默认值和三档差异；迁移或活动任务切换时解释影响、失效授权、Scope/digest 校验及下一步所需确认。
- 只迁移项目配置和当前权威说明；已归档 Spec、Execute Log、Learning、Run ledger 保持只读，不做历史重写。

### Risks

- 若把旧 `agent` 值静默映射为 `auto`，会把“仅可自批 Plan”扩大为“可自动调度后续阶段”，形成隐式授权升级。
- 若把缺失或无效配置静默回退为自动模式，会延续当前 fail-open 行为并掩盖拼写错误。
- 若 human 模式只改 Plan Gate，则新名称仍然名不副实；若把每个机械步骤都变成人工确认，又会制造无价值的审批噪声。
- 自动化不能破坏 Research/Challenge reviewer 的角色独立、只读边界与可审计身份，也不能把 PASS、Plan Approval 或旧授权推断为归档许可。
- `approvalPolicy` 已进入 Console API、artifact snapshot、project index 和 Cruise ledger；直接删除字段可能造成公开投影或账本消费者破坏。
- 若项目配置被当作当前任务授权，仓库中的静态文件会错误替代当前用户意图；若运行中直接重读配置，任务还可能在无审计记录的情况下改变模式。
- 若保留独立的 `CRUISE_ENABLED` 行为开关，三档模式之外仍会出现“auto 但 Cruise 关闭”等额外混合状态。

### Initial Acceptance Hints

- 同一配置值必须在 `next`、`challenge`、`cruise`、Console API、Web Console 和生成的 Agent 指令中投影为同一模式与停机规则。
- `auto` 的计划内路径不再为 Plan Approval 或内部只读 reviewer 重复询问用户；仍在不可委托边界 fail-closed。
- `supervised` 允许在同一次用户交互中同时批准 Plan，并明确授权当前任务在该 Plan/Scope 内自动使用计划内 worker 与只读 Challenge reviewer；两项事实必须分别审计，不能从普通 Plan Approval 推导自动权限。
- `human` 必须产生可观察的人工等待状态，且没有对应 `human:<name>` 审计证据时不得越过受控阶段。
- 缺失、无效和旧配置必须具有明确且被测试冻结的迁移/报错行为，不能静默扩大权限。
- 当前任务进入 auto 必须有一次绑定任务、范围和时间的明确授权；配置只提供默认策略，不能单独充当授权证据。
- workflow 必须区分 `policy_wait`、`risk_stop`、`scope_change`、`budget_exhausted`、`platform_permission` 与 `archive_authorization` 等停机原因，不能全部压缩成含糊的 `human_required`。
- CLI/Console 必须提供结构化 effective mode、来源、授权状态、stop reason 与下一步；生成的 Agent 指令和人类文档必须把这些事实转成可理解的 AI 导航，不要求用户自行拼命令或猜测确认内容。
- 历史归档制品继续可读；Challenge Evidence 只能由记录命令生成，AC Coverage、失败回退与归档授权回归不得弱化。

## Research

### Requirement Review

用户指出当前 `APPROVAL_POLICY=agent` 的产品含义与体验不匹配：它只允许 Agent 自批 Plan，却没有把后续执行、验证、独立审查和修复连接成一致的自动路径，因此用户仍频繁收到“批准/授权”请求。经澄清，用户确认需要三种可理解场景：`auto` 在任务范围授权后从 Research 起自动推进；`supervised` 在 Plan 完成并由用户批准后自动推进；`human` 的关键治理门禁均由人工控制。Plan Approval 继续作为执行契约和质量检查存在，在 supervised 中同时承担后续自动驾驶的开工许可。

### Findings

1. `lib/common.js:42-45` 只读取 `APPROVAL_POLICY=agent|human`，缺失或无效值都回退到 `src/core/governance-contract.js:1-5` 的 `agent`；当前无独立的配置合法性诊断，因此拼写错误会静默进入 Agent Plan 自批模式。
2. `src/core/workflow-gate-facts.js:58-71` 与 `src/core/spec-state.js:342-347` 证明该策略只判断 `Plan Approved By`：`human` 强制 `human:<name>`，`agent` 允许带时间和 Gate Evidence 的 `agent:<id>`。它不控制 Execute、reviewer 调度或归档。
3. `CRUISE_ENABLED` 与 `CRUISE_MAX_ITERATIONS` 是另一组独立开关；`src/commands/cruise.js:58-119` 只输出修复循环提示，明确 orchestrator 不执行阶段修复。因而 `APPROVAL_POLICY=agent`、Cruise 已启用也不等于宿主会连续执行。
4. `src/core/cruise-run.js:17-22` 把任意 risk flag 和归档动作都标为 `human_required`；`src/core/reviewer-guidance.js:1-26` 又无条件要求使用自动 reviewer 前暂停请求授权。多个互不关联的停机源共同形成当前“半自动”体验。
5. Research/Challenge 的价值来自独立 reviewer 身份和只读职责，而不是反复弹窗。`src/core/spec-state.js:287-293,363-365` 和治理合同要求 standard/lite 使用可审计 reviewer；新 auto 模式可以改变调度授权来源，但不得放宽身份 grammar、时间戳、Challenge 记录命令或只读边界。
6. 最终归档已经是独立、不可推导的当前用户授权：状态恒定路由到 `request_archive_authorization`，CLI 需要 `human:<name>` 与本次 evidence。该边界不应被 auto 吸收。
7. `approvalPolicy` 不只存在于配置读取，还公开在 artifact snapshot、workflow state、project index、Console API/Web Console 和 Cruise JSONL。重命名需要同时处理字段投影与消费者，不能只改 `.sdd-config` 文案。
8. 初始化测试固定写入 `APPROVAL_POLICY="agent"`，Plan Gate、Cruise、生成配置和人类文档均有精确回归。实现必须以新合同的失败/通过矩阵替换这些断言，并保留 state matrix、workflow gate facts、Challenge 防伪和 AC Coverage 的既有保护。
9. 已归档 v4.7 Learning 明确：Plan 后新增持久化治理配置必须回写 Plan 范围和验证边界；人类文档与 Agent 权威协议应分层表达，不能为了逐字复用再次牺牲可读性。
10. 当前 `.sdd-config` 是静态项目文件，不能证明当前用户对某个 active Spec 的授权。若 auto 要覆盖 Research/Challenge 自动 reviewer 与计划内 worker，必须另有任务级、可审计且会因范围变化失效的授权事实。
11. 旧模型实际由 `APPROVAL_POLICY` 与 `CRUISE_ENABLED` 两个开关组合而成；只迁移前者会保留混合状态。历史 v2.2 已废弃 `GATE_POLICY/CRUISE_POLICY`，本任务不得复活这些更老入口。
12. `src/core/cruise-run.js:17-22` 当前把任意 risk flag 都折叠成 `human_required`。新策略必须区分模式等待与安全停机，并判断由治理术语或内部 Console API 触发的 `security/public-api` 是否真代表不可委托业务风险。
13. `src/core/artifact-snapshot.js:89` 每次从当前项目配置读取策略；若运行中修改 `.sdd-config`，active Spec 会被重新解释。新模型需要在任务创建或任务授权时冻结 effective mode、授权范围和证据，历史 archive 仍保持只读。

### Open Questions

None. 以下均为用户已确认的决策：

1. 已确认：采用新的单一配置 `AUTONOMY_MODE=auto|supervised|human`，不再扩大 `APPROVAL_POLICY` 的含义。`auto` 对应 Intake 后一次任务授权，`supervised` 对应 Plan 后一次开工授权，`human` 对应关键治理阶段逐次批准。
2. 已确认：采用严格迁移。升级后的活动项目若缺少 `AUTONOMY_MODE`、值非法，或仍存在 `APPROVAL_POLICY/CRUISE_ENABLED`，工作流返回明确的 `MIGRATION_REQUIRED` 并停止，由用户显式选择三档之一；不兼容读取、不静默映射，也不复活 `GATE_POLICY/CRUISE_POLICY`。历史归档制品与旧 ledger 继续只读可见，不要求改写。
3. 已确认 human 的人工门禁粒度：Research 结论、Innovate 选型、Plan→Execute、Completion Verification、Challenge/`FAIL_*` 回退及最终归档需要人工决策；阶段内部的文档填写、测试和计划内 debug 不逐次批准。Challenge reviewer 可由独立自动角色执行，但必须先有人类批准调度。supervised 的 Plan 交互可以同时收集 Plan Approval 与后续自动推进授权，但必须分别记录，普通 Plan Approval 不得被推导成 reviewer/worker 授权。
4. 已确认 auto 的任务级授权生命周期：在 Spec 创建/Intake 后由当前用户授权一次，绑定 task id、Intake Scope 上限和已知风险，使 Plan 前的 Research reviewer 可以启动；Plan 形成后由 Agent 证明其未超出已授权 Scope，并把 Plan digest/范围快照写入审计链完成激活，不再次请求用户。若 Plan 超范围、发生重大偏差或策略改变，原授权失效。授权不覆盖归档、Profile exact digest、E2E SKIPPED、高风险/不可逆操作、平台权限或外部写操作。
5. 已确认 effective autonomy mode 在 discover 时写入 Spec，并冻结模式与范围；`.sdd-config` 后续变化不重解释 active Spec。活动任务只能通过受控 mode change 事件切换。
6. 已确认采用风险快照：任务授权时向用户展示并冻结当前已知、属于 Scope 的 risk flags；这些已授权风险不再重复打断 auto。执行中新发现的风险、不可逆动作、范围扩大或授权风险集合不匹配时，持续授权失效并输出精确 stop reason。仅因治理说明或内部 Console API 字样产生的分类信号不得在无结构化事实时误报为硬停。
7. 已确认：新项目初始化默认写入 `AUTONOMY_MODE=supervised`；项目配置只作为新 Spec 的默认选择，不直接改变已存在 Spec 的 effective mode。
8. 已确认：采用“项目默认 + Spec 冻结覆盖 + 活动任务受控切换”。`discover` 可显式覆盖默认模式并写入 Spec；活动 Spec 通过受控 autonomy 命令切换。收紧模式立即取消持续授权；扩大为 auto 必须重新取得任务级授权并校验 Scope/Plan digest；归档 Spec 不可原地修改。
9. 已确认需要 AI 引导，并保持现有自然语言引导风格：AI 在创建、严格迁移、模式切换和人工停机点主动说明当前状态、推荐选择、影响与用户具体要确认的事项；CLI 保持非交互、确定性输出，为 AI 提供结构化事实，不新增第二套 CLI 问答向导，也不把用户入口退化为命令手册。
10. 已确认 Innovate 决策按模式分层：auto 保留多方案、比较和选择证据，在不改变 Requirement、Scope 与已授权风险时由 AI 自动选择推荐方案；supervised 展示推荐方案并允许用户在 Design/Plan 确认时改选；human 必须由用户明确选择。任何模式下若方案改变需求、扩大范围或引入未授权风险，都必须暂停并使原持续授权失效。
11. 已确认彻底移除旧运行时治理字段：新配置、实现、状态投影、CLI/Console、Run ledger 新记录、Agent 指令和文档不再产生或消费 `APPROVAL_POLICY`、`approvalPolicy`、`CRUISE_ENABLED`；发现旧字段只返回 `MIGRATION_REQUIRED`。`CRUISE_MAX_ITERATIONS` 作为有界修复预算保留。历史归档与旧 JSONL 中已有字段不删除、不重写，继续作为只读审计事实。

### Assumptions

- `auto` 表示有边界地自动推进至归档授权前，不表示 Agent 可扩大 Plan、执行不可逆操作、伪造 reviewer、跳过验证或自行归档。
- Plan Approval 继续保留为结构化执行合同：auto 下由 Agent 基于 Gate Evidence 完成；supervised 下由当前用户批准，并在同一次交互中另行明确授予当前任务在该 Plan/Scope 内使用计划内 worker 与只读 Challenge reviewer 的持续权限；human 下由当前用户批准但不授予后续阶段持续自动权限。不得从普通 Plan Approval 推导自动授权。
- 项目级配置只表达默认运行策略，不是当前用户授权；auto 的实际启用依赖 active Spec 中绑定 task id 与 Confirmed Requirement/Scope Boundary 上限的可审计授权，Plan 形成后再以 digest/范围快照证明未越界并激活后续自动执行。
- Research/Challenge 的独立性由 reviewer 身份、上下文分离、只读行为和记录证据保证，不以“每次弹窗”本身保证。
- 历史制品不迁移；本任务只决定新运行时如何解释项目配置，以及升级项目是否必须显式修改 `.sdd-config`。
- 已确认对活动项目执行严格配置迁移：新运行时只接受显式合法的 `AUTONOMY_MODE`，旧治理开关不参与兼容计算；历史 archive/ledger 仍按历史事实读取。
- 新运行合同彻底移除 `APPROVAL_POLICY/approvalPolicy` 与 `CRUISE_ENABLED`；仅保留 `CRUISE_MAX_ITERATIONS` 预算。任何兼容仅限历史文件作为原始事实被展示，不进入新状态计算。
- 已确认新项目默认 `supervised`；每个 Spec 在创建时冻结 effective autonomy mode，可显式覆盖项目默认值。
- active Spec 的 effective mode 与任务级授权被冻结并进入审计链，配置中途变化不静默改变正在执行的任务。
- auto/supervised 的持续授权同时冻结已知风险集合；已授权风险不重复询问，新增风险或风险集合变化必须 fail-closed 并重新授权。
- UI 不受影响；Web Console 仅更新文字和工作流状态投影，不引入新的视觉交互设计。
- AI 导航是主要使用入口，CLI 保持非交互、确定性控制面；文档同时提供自然语言示例和精确命令参考。
- Innovate 的多方案证据始终保留，但是否打断用户由 effective autonomy mode 决定；auto 的 AI 选型不能越过 Confirmed Requirement、Scope 或风险快照。

用户只需在 AI 引导下理解并选择 `auto`、`supervised` 或 `human`：auto 在 Intake 后取得绑定 task id 与 Scope 上限的一次授权，正常连续推进至归档授权前；supervised 在 Research 阶段按需授权 reviewer，并在同一次 Plan 交互中分别取得 Plan Approval 与绑定该 Plan/Scope 的后续自动推进授权后连续推进至归档授权前，不能从前者推导后者；human 在定义清楚的关键阶段等待人工证据。每个 Spec 冻结 effective mode，可覆盖项目默认并受控切换。所有 CLI、Console、Agent 指令和文档输出一致的模式来源、授权状态、精确 stop reason 与下一步，让 AI 能明确说明用户正在确认什么。任何模式都不得旁路归档、Profile exact digest、E2E skip、不可逆/高风险、范围扩张或平台权限门禁，也不得静默提权。

## Innovate Options
<!-- Compare at least two options. Write the option analysis in Chinese. -->

### Option A: 单一三档自治模式（Selected）

- Summary: 使用 `AUTONOMY_MODE=auto|supervised|human` 作为唯一协作模式；彻底移除新运行合同中的 `APPROVAL_POLICY/CRUISE_ENABLED`；任务级授权与冻结事实写入 Spec 审计链，运行时输出精确等待/停机原因。
- Pros: 用户心智模型直接；消除 Approval 与 Cruise 两轴组合出的混合状态；能够表达“任务开始即自动”“看完 Plan 再自动”“关键门禁全人工”三种真实场景。
- Cons: 需要迁移现有配置、状态投影、生成指令与测试；需新增任务授权和阶段批准事实。
- Risks: 若迁移或授权绑定不严谨，可能造成静默提权；通过显式迁移、Scope/digest 校验和硬停矩阵控制。
- Requirement Fit: 完整满足用户确认的三档需求，并让 Plan Approval 在 supervised 中获得清晰的开工语义。

### Option B: 保留 APPROVAL_POLICY 与 CRUISE_ENABLED 组合

- Summary: 继续用审批人和 Cruise 开关排列出三种体验。
- Pros: 表面改动较少，部分旧字段可继续使用。
- Cons: 同一用户意图仍需理解两个正交开关；冲突组合继续存在，无法自然表达任务级 reviewer 授权与 effective mode 冻结。
- Risks: 延续当前“配置看似 agent、体验却频繁暂停”的根因。
- Rejected Rationale: 用户明确要求从场景出发，而不是继续维护技术开关组合。

### Option C: 只在每个 Spec 内设置模式

- Summary: 删除项目默认值，每个任务创建时都选择 auto、supervised 或 human。
- Pros: 每次选择都接近当前用户意图，不会把仓库配置误当授权。
- Cons: 每个任务重复询问；团队无法表达默认协作方式；仍需单独设计任务授权事实。
- Risks: 增加入口摩擦，且不能替代 A 中的授权与审计设计。
- Rejected Rationale: 项目默认策略仍有价值，但只能作为默认值，不能作为当前任务授权本身。

## 目标摘要
当前处于 Innovate，目标是把只控制 Plan Gate 的半自动策略改为语义一致的 `auto | supervised | human` 三档模式。

## 最终方案
采用单一三档自治模式 `AUTONOMY_MODE=auto|supervised|human`，取代 `APPROVAL_POLICY` 与 `CRUISE_ENABLED` 的组合。项目配置只提供新 Spec 的默认值；每个 Spec 冻结 effective mode，并通过 Spec 内受控、追加式 Autonomy Events 记录任务授权、Plan 激活、人工 Gate、模式切换和失效事实。CLI 只维护确定性状态与审计事实，宿主 AI 根据这些事实执行连续编排和子 Agent 调度。

## 关键约束
依赖现有 Spec/Design/Execute Log/Challenge 审计链、`agent:<id>|human:<name>` 身份格式和当前归档授权协议；必须新增任务级 auto 授权事实与 effective mode 冻结，保留独立 reviewer、Challenge 防伪、AC Coverage、Provider/path 安全及历史归档可读性。活动项目只接受显式合法的 `AUTONOMY_MODE`；缺失、非法或遗留 `APPROVAL_POLICY/CRUISE_ENABLED` 均以 `MIGRATION_REQUIRED` fail-closed，不提供兼容映射。

## 坑点与风险
- 新事件模型和三档矩阵增加实现量，但换来单一、可解释且可审计的协作合同。
