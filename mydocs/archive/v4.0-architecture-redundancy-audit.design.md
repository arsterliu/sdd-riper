# Technical Design

## Technical Design

Selected Option / ADR: ADR-001 选择 Contract-First Phased Simplification。v4.0 仅完成架构冗余审计、分类模型、优先级和后续任务依赖路线，不修改产品代码。拒绝一次性全量重构，因为其同时跨越公共 CLI、工作流 gate、安全路径、Verification/Visual 证据模型和测试基础设施，无法形成清晰回滚边界；也拒绝仅做局部去重作为总体策略，因为它不能解决分布式治理契约和多权威状态事实这一根因。

Requirement Traceability:
- 用户要求“完整梳理项目”：Architecture View 覆盖 CLI、核心状态、Profile、Quality、Verification、Visual、Console、文档/模板/AI 配置与测试。
- 用户要求“看看当前是否有冗余设计”：Domain Model 定义六类冗余/必要复杂度；Spec Findings 给出 file:line、优先级、置信度和风险。
- 用户确认“审计后拆分”：本 Design 不定义产品代码改动，只定义审计交付与五个后续 Spec 的依赖顺序。
- 当前工作区约束：将未提交 Visual Verification 标为候选实现；不以隔离 worktree 的 HEAD 视图替代主工作区事实。

Impact Scope:
- 本任务允许修改：`mydocs/specs/v4.0-architecture-redundancy-audit.md`、本 Design、引用的 Execute Log，以及满足条件时生成的 Learning Record。
- 本任务只读检查：`bin/`、`lib/`、`src/`、`tests/`、`templates/`、治理文档、AI 配置、项目配置、历史制品和 Git 状态。
- 本任务禁止修改：产品实现、测试、模板、README/GUIDE/SKILL/AI 配置和当前未提交 Visual 候选代码。
- 后续影响范围由独立 Specs 重新确认，v4.0 不授权实施。

Context / Boundary: 系统边界是当前主工作区 `D:\workspace\personal\sdd-riper`。外部 context 为 none。审计把 HEAD 稳定架构、当前已跟踪增量、未跟踪 Visual 候选、历史 ADR/Learning 分开标识。Reviewer worktree 只能用于独立阅读；涉及未提交文件的结论必须回到主工作区复核。

Domain Model:
- `Authority Duplication`：同一 gate、状态或合同由多个实现独立决定；默认 P0，收敛权威事实。
- `Exact Algorithm Duplication`：输入、输出和失败语义相同；默认 P1，提取共享实现。
- `Workflow Skeleton Duplication`：流程相似但领域结果不同；默认 P2，只抽基础设施。
- `Audience Projection`：同一事实面向 CLI、Console、Skill、文档或模板；保留投影，禁止各自重算硬规则。
- `Defensive Complexity`：allowlist、realpath、fingerprint、immutable commit 等安全/审计边界；保留领域策略，只共享底层原语。
- `Domain Separation`：普通 AC Run 与 Visual Scenario Run 等结果模型不同；保留独立 schema 和 namespace。
- `Low-value Boilerplate`：格式化、Commander action、包装函数；默认 P3，需求驱动整理。

Architecture View:
```text
Current Workspace Evidence
├─ source/call-chain facts
├─ test health baseline
├─ historical ADR/Learning intent
└─ uncommitted candidate boundary
          |
          v
Redundancy Classification
├─ authority duplication
├─ exact algorithm duplication
├─ workflow skeleton duplication
├─ audience projection
├─ defensive complexity
└─ domain separation
          |
          v
Audit Deliverables
├─ P0-P3 findings
├─ keep-boundary list
├─ prohibited mega-abstractions
└─ follow-up Spec dependency map
```

后续任务依赖：
```text
governance-contract-consistency
  -> workflow-gate-facts-unification
      -> structured-readiness-projections

workflow-gate-facts-unification
  -> visual-verification-boundary-cleanup
     （仅在当前 Visual 候选行为稳定后）

前四项完成或稳定后
  -> test-fixture-consolidation
```

Data Model / Schema: 本任务不修改运行时数据模型。审计 Findings 使用稳定字段：`Id`、`Category`、`Priority`、`Confidence`、`Evidence`、`Assessment`、`Keep Boundary`、`Follow-up Spec`。后续任务路线使用：`Suggested Task Name`、`Purpose`、`Dependencies`、`Compatibility Boundary`。这些字段保存在 Markdown 制品，不新增 JSON schema、Run schema 或配置格式。

Data Migration / Backfill: 无运行时数据迁移。历史 Spec、Design、Execute Log、Learning、Verification Run 和 Visual Run 均保持原样。后续任务不得从 v4.0 推导需要重写历史制品；若要取消历史 `Review (Verdict|Summary)` reader，必须另行确认兼容策略。

Interface Contract:
- v4.0 对外输出是 Spec、Design、Execute Log、Challenge Evidence 和可选 Learning Record。
- Findings 中的 `file:line` 必须指向主工作区实际证据；行号失效时回到 Research 修正。
- 优先级含义：P0 为权威性/语义漂移风险；P1 为高收益明确重复；P2 为需先冻结契约的基础设施复用；P3 为低价值样板。
- “Selected Option”只选择后续路线，不授权创建或执行后续 Specs。
- 当前工作区测试基线只证明行为健康，不证明架构无冗余。

API Protocol: 不新增或修改 CLI、HTTP、Provider、Reporter、Run 或配置协议。后续建议任务名不是 CLI/API 合同。

State / Concurrency: v4.0 仅串行完善 Markdown 审计制品，不引入并发状态或共享运行时写入。独立 reviewer 只读。若 reviewer worktree 与主工作区内容不一致，主 Agent 在主工作区复核后记录差异，不合并 reviewer worktree。

Failure Modes:
- 证据路径或行号失效：回到 Research 修正，不进入 Challenge。
- Reviewer 只看到 HEAD 而漏掉未提交候选：将其结论标为隔离视图限制，并用主工作区证据覆盖。
- 将必要安全层判为冗余：回到 Design，补充信任边界和失败关闭依据。
- 全量测试失败：先执行 `sdd debug` 确认根因，再决定是否修复审计制品或标记 BLOCKED；不得归档。
- Windows symlink 测试 SKIP：如实记录环境限制，不宣称对应安全路径 PASS。
- 后续范围被静默扩大：停止并回到 Research/Innovate 重新确认，不由 v4.0 自动创建新任务。

Security / Permission:
- 保留 Registry allowlist、Workspace Resolver、Process Gateway、Attachment Store、Fingerprint/Freshness、lexical/realpath containment 和 immutable Run 作为必要复杂度。
- 任何 path helper 建议只共享原语，不统一各领域的信任根、existence、realpath 时机和错误码。
- Research/Challenge reviewer 保持只读并使用可审计身份；Challenge Evidence 必须由 CLI 记录。
- Archive 必须在 `validate --archive-ready` 通过后再次取得当前用户明确授权。

Observability:
- Spec Findings 是审计事实主投影；Design 记录分类与路线决策；Execute Log 记录每一步证据复核、测试结果、偏差和 AC Coverage。
- 当前基线：`npm test` 为 421 tests、416 PASS、0 FAIL、5 SKIP、约 54.3 秒；SKIP 原因为 Windows 文件 symlink 权限。
- `sdd next` 用于观察阶段门禁；`git diff --check` 用于制品格式检查。

Performance / Capacity: 本任务无运行时容量影响。审计识别到单次 `spec-state.evaluate()` 重复 readiness、多个 parser 重复读盘和重复 assessment，但这些仅作为后续任务输入，不在 v4.0 优化。后续重构应先度量语义一致性，性能收益为次要目标。

Compatibility / Rollback:
- v4.0 不改运行时行为，因此兼容性风险限于审计制品内容。
- 若审计结论被证据推翻，可回到 Research 修订对应 Finding；不需要代码回滚。
- 后续 Specs 必须分别保证 CLI 标签、error codes、历史 Spec/Run 可读性、Provider allowlist、path/realpath fail-closed 和 Run schema/namespace。
- 禁止在后续设计中建立语义不透明的 `SafePath`、`ConfigFramework`、`UniversalRun` 或 `CommandBase` 大一统抽象。

Test Strategy:
- Manual/evidence：逐项检查 Architecture Map、F-001 至 F-010、Necessary Complexity、Priority Summary 和五个后续任务是否具有主工作区证据及一致分类。
- Automated health：归档前重新运行 `npm test`，要求 0 FAIL；SKIP 必须逐项披露，不自动视为 PASS。
- Artifact structure：运行 `sdd next`、`sdd validate --archive-ready`；前者验证阶段路由，后者验证 Spec/Design/Execute Log/AC Coverage/Challenge/Learning 门禁。
- Format：运行 `git diff --check`。
- Scope：运行 `git diff --name-only`，确认 v4.0 Execute 新增变更仅限本任务制品；用户原有工作区变更需与本任务新增 diff 分开解释。
- Independent review：standard 模式 Challenge 由独立只读 subagent 执行，重点反证完整性、误报、安全边界与拆分可执行性。

Risks / Trade-offs:
- 分批路线耗时更长，并会暂时保留适配层；换取清晰的兼容、回滚和验证边界。
- Contract Registry 若范围过大可能成为新的中心化“上帝模块”；应只承载稳定 hard facts，不承载文档叙事、CLI 文案或领域执行逻辑。
- Parser 统一可能改变历史 Markdown 语义；必须先建立兼容矩阵。
- Visual 候选尚未提交，过早抽象会冻结未经稳定验证的接口；应先完成其当前行为确认。
- 测试 fixture 收敛放在最后会暂时保留测试重复；这是避免协议变化期间 helper 反复分叉的有意取舍。
