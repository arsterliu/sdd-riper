## Summary
当前处于 Research 阶段，目标是消除 auto 模式正常路径中针对 Plan 与 reviewer 的重复人工确认。
已确认采用保留任务授权、Plan 激活和摘要校验的方案 A。
本任务不改变归档、范围/风险变化、不可逆操作、平台权限、Profile 摘要与 E2E SKIPPED 的人工门禁。
尚待对 Research 结论执行独立审查，并将当前用户的首次 auto 授权写成可审计记录。

## Intake

### Requirement
requirement: 优化 auto 模式的授权与停机策略：首次范围确认应可明确授权主 Agent 与独立 reviewer 在范围不变、风险不变且 Plan 摘要未变时持续推进；auto 模式不应为 Plan 的人工批准或 reviewer 的重复授权而停机；仍保留归档、范围扩大、新风险、不可逆操作、平台权限、Profile 精确摘要确认和 E2E SKIPPED 等必须人工授权的停机点。
goal: 消除 auto 模式正常路径中的重复确认，同时保留可审计授权边界与强制人类治理点。

### Constraints
constraints: 不削弱 archive、风险、范围、不可逆操作、平台权限、Profile 与 E2E SKIPPED 的人工门禁；授权必须可审计且与当前任务范围、风险和 Plan 摘要绑定；同时更新生成的 Agent 规则与 CLI 行为，不只修改 SKILL.md。

### Scope
- 授权状态模型、`autonomy authorize` 与 `autonomy activate-plan` 的时序。
- auto 模式下的状态推导、下一步提示、Cruise 可继续条件和生成的 Agent 规则。
- 相关 CLI / 核心单元测试与使用文档。

### Risks
- 若错误放宽授权条件，可能在范围或风险变化后继续执行。
- 若移除 Plan 摘要的独立绑定，可能降低批准对象漂移的可检测性。
- 若只调整单一 Skill 文案，CLI、控制台与其他 Agent 配置会继续产生不一致行为。

### Initial Acceptance Hints
- auto 的首次人类确认可授权主 Agent 和本任务所有只读独立 reviewer，直至归档授权前。
- Plan 获 Agent 批准后自动写入与当前摘要匹配的 Plan 激活事件，不向用户二次询问。
- Scope、风险或 Plan 摘要变化仍会使授权失效；既有专属人工停机点保持不变。

## Research

### Requirement Review
当前 auto 实现已经区分 task_authorization 和 plan_activation，也在任务授权中声明了 main、worker、research-reviewer、challenge-reviewer 四类角色。
但 task_authorization 仅覆盖 Plan 前，Plan 审批后 resolver 强制要求 plan_activation；若 host Agent 未自动执行授权 / 激活命令，就会向用户重复询问批准 Plan 或授权 reviewer。
本任务要修复的是授权编排与状态提示，不是移除治理门禁，也不是把 auto 变成无条件自治。

### Findings
- `src/commands/autonomy.js` 的 `authorize()` 已把 `main,worker,research-reviewer,challenge-reviewer` 写入 auto 任务授权。
- 同文件的 `activatePlan()` 已允许 `agent:<id>` 写入可审计的 Plan 激活事件，并校验 scope、risk 和 Plan 摘要。
- `src/core/autonomy-state.js` 在 auto 的 Plan 已获批但尚无匹配激活记录时返回 `plan_activation_required`，从而使流程停下。
- `tests/autonomy-workflow.test.js` 已覆盖该停机状态、摘要失效和风险失效；需将测试扩展到“自动编排但不放宽摘要校验”的行为。
- `src/core/ai-config-rules.js` 是 `SKILL.md` 与生成 Agent 规则的单一来源，不能只改生成后的 Skill。

### Open Questions
- 初始 auto 授权的审计身份由当前用户确认后写为 `human:<name>`。

### Assumptions
- 被授权的 reviewer 均保持只读，实际 Challenge 结果仍须记录可审计的执行者身份。
- Plan 激活保留为独立事件，以便在 Plan 写成后才绑定精确摘要；该事件可由主 Agent 自动创建。
- 不涉及面向最终用户的 Web / 桌面界面变更，`ui-impact: no`。

## Innovate Options
### Option A: 保留双事件并自动编排（Selected）
- 保留 task_authorization 与 plan_activation；首次确认自动写入前者，Plan 获 Agent 批准后自动写入后者。
- 优点：保留 Plan 摘要在生成后独立绑定的审计边界，与现有存储模型和旧制品最兼容。
- 风险：必须保证自动编排只在既有 scope / risk 授权仍新鲜时运行。

### Option B: 合并为单一授权事件
- 用一条事件同时代表任务授权和 Plan 授权。
- 优点：状态模型表面更简单。
- 缺点：Plan 在创建前没有可绑定摘要，事件语义不清晰，旧记录兼容和迁移成本较高。

### Option C: 让任务授权隐含 Plan 授权
- 删除自动模式对 plan_activation 的要求。
- 优点：改动最少。
- 缺点：弱化摘要的独立激活边界，不能明确证明 Agent 曾核对具体 Plan。

## 目标摘要
当前处于 Research 阶段，目标是消除 auto 模式正常路径中针对 Plan 与 reviewer 的重复人工确认。

## 最终方案
选择方案 A：保留 task_authorization 与 plan_activation 两个事件。首次人类确认 auto 时，主 Agent 自动建立覆盖 main、worker、research-reviewer、challenge-reviewer 的任务授权；Plan 经 Agent 审批后，主 Agent 自动建立绑定当前 Plan 摘要的 plan_activation。该方案消除正常路径的二次人工确认，同时保留 Plan 生成后才可绑定精确摘要的审计边界。

## 关键约束
必须保留 scope、风险和 Plan 摘要三重一致性检查；初始用户授权必须可审计并明确覆盖 reviewer 角色；归档及所有既定专属人工门禁不得被自动化绕过。

## 坑点与风险
自动编排减少一次人工询问，但依赖宿主 Agent 严格遵守指引。保留独立激活事件增加少量记录开销，却换取明确的摘要绑定证据与更低的兼容风险。
