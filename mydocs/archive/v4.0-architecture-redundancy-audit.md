## Summary
当前阶段为 Research，任务仅审计当前工作区架构与实现，不修改产品代码。
项目整体边界基本合理，但存在中高程度的实现冗余；主要风险不是文件数量，而是同一治理事实在状态机、validator、模板、Skill、文档和 UI 中多处手写后产生语义漂移。
高优先级方向是建立可执行的治理合同单一来源、统一状态事实与结构化投影；安全边界、领域模型和多受众投影应保留。
当前工作区全量测试基线为 421 tests、416 PASS、0 FAIL、5 SKIP；未提交视觉验证增量单独按候选实现审计。

## Intake

### Requirement
requirement: 完整梳理当前工作区全量项目架构与实现，识别冗余设计、重复抽象、重复流程、过度复杂性和可合并模块，形成有证据、分优先级且区分必要复杂度与可删除复杂度的只读审计结论；本阶段不修改产品代码。
goal: 建立当前架构、调用链和职责边界全景，给出冗余候选、保留理由、简化方向、影响范围与风险排序。

### Constraints
constraints: 以当前工作区（含未提交修改）为基线；结合代码、测试、文档、历史 Spec 与 Learning；不得把进行中的实现误判为稳定架构；只读审计，不进入 Execute。

### Scope
- In Scope: `bin/`、`lib/`、`src/`、`tests/`、`templates/`、治理文档、AI 配置、项目配置、历史 Spec/Design/Learning，以及当前工作区未提交视觉验证增量。
- In Scope: 模块职责、调用链、状态事实来源、解析与投影、验证/视觉证据模型、安全边界、测试结构和契约漂移。
- Out of Scope: 修改产品代码、删除模块、设计最终迁移 API、进入 Plan/Execute、对外兼容承诺。

### Risks
- 把不同领域模型或安全信任边界误判为冗余，简化后破坏 fail-closed 行为。
- 把 CLI、Console、文档、模板的必要受众投影误判为重复源。
- 隔离 worktree 无法观察主工作区未提交文件，导致把 v3.8/v3.9 候选实现误判为不存在；本审计以主工作区事实覆盖该类结论。
- 仅依据通过的测试推断架构合理；测试证明行为健康，不证明维护成本合理。

### Initial Acceptance Hints
- 给出当前架构主链和模块职责地图。
- 每个冗余候选包含证据、差异、风险、置信度和优先级。
- 显式列出必要复杂度与禁止粗暴合并的边界。
- 区分当前 HEAD 与未提交视觉验证增量。
- 使用当前工作区全量测试建立行为基线。

## Research

### Requirement Review
用户要判断项目“当前是否有冗余设计”，核心不是统计文件数，而是回答：同一事实是否有多个权威实现、抽象层是否承载独立职责、重复是否服务安全/兼容/受众投影，以及简化后是否降低可审计性。审计采用“权威事实、领域边界、基础设施复用、投影职责、安全信任边界、历史意图”六个维度。结论必须区分可直接收敛、需先冻结契约再收敛、应保留三类，避免以代码行数作为删除依据。

### Findings

#### Architecture Map
1. CLI 入口：`bin/cli.js` 注册命令；`src/commands/**` 负责参数策略、副作用和文本/JSON 输出。
2. 工作流事实链：`src/core/artifact-snapshot.js` 读取 Spec/Design/Execute Log/Learning → `src/core/spec-state.js` 推导 gate、phase、action、challenge target → `src/core/workflow.js` 增加风险、设计方法、Profile/Visual 投影 → `next/status/resume/challenge/cruise/spec-index/console` 消费。
3. Profile 链：`src/profile/**` 负责候选探测、规范化、摘要、确认、revision/current 存储、漂移和路径边界。
4. Quality 链：`src/quality/**` 根据 Profile、affected units、关系和 AC 类型生成建议能力；它不声明执行覆盖。
5. Verification 链：Provider config → Registry allowlist/Adapter manifest → Workspace trust resolution → Process Gateway → Reporter/normalize/result contract → Fingerprint/Evidence/Readiness → immutable Run/attachments。
6. Visual 链：Visual Context discovery/selection → Visual Evidence Contract → Visual execution config → `playwright-visual` Provider → PNG comparator → 独立 Visual Run；当前后半链包含未提交候选实现。
7. Console 链：project/spec index → console projection → versioned API → Web render；Console 是只读、脱敏的状态投影，不应重新定义领域事实。

#### F-001 — Distributed Governance Contract Drift
Priority: P0
Confidence: High
Evidence:
- micro 模板列出 `Scope/Touched Files/Change/Impact Scope/Data Impact/Interface Impact/Acceptance/Verification/Blast Radius`：`templates/spec-micro.md:32-41`；机器只强制后五项：`src/commands/validate.js:104-109,401-405`、`src/core/spec-state.js:461`。
- E2E `Provider` 在模板和 readiness/state gate 中是硬要求：`templates/spec-standard.md:78`、`templates/spec-lite.md:56`、`templates/spec-micro.md:40`、`src/verification/readiness.js:45-64`、`src/core/spec-state.js:442-454`；核心 Skill 的 AC 说明只明确 `Test/Manual Evidence`：`SKILL.md:285`。
- `package.json:4` 仍描述旧的 `Research, Innovate, Plan, Execute, Review`，与当前 Completion Verification + Challenge + Learning/Archive 模型不符。
- `.sdd-config:2` 的 `SDD_VERSION="1.0"` 无生产读取点；`:3` 的本仓 Cruise 预算 20 与新项目/文档默认 5 不同且未标注意图。
- 根 AI 配置与 `_gen-ai-configs.js:13-37` 的 Profile/Archive 最新硬规则未保持同一 managed source。
Assessment: 项目当前最核心的冗余是“手工复制的分布式契约”。README、GUIDE、SKILL、模板、生成器和 validator 面向不同受众，应保留；硬枚举、必填字段、身份 grammar、默认值和路由映射应来自可执行 Contract Registry 或至少由一致性测试约束。

#### F-008 — Path Containment Primitive Is Copied, Security Policies Are Not Redundant
Priority: P1 foundation
Confidence: High
Evidence: `src/commands/visual.js:10-17`、`src/commands/verify.js:104`、`src/visual-evidence/contract.js:79-85`、`src/visual-evidence/discovery.js:27-34`、`src/visual-verification/config.js:17`、`src/verification/workspace.js:8-17`、两个 Run Store 等均实现 `path.relative`/realpath containment。
Assessment: 可共享 `isPathInside/assertLexicallyContained/assertExistingRealpathContained` 等原语；每个领域必须继续决定 root 是否允许、目标是否可不存在、文件/目录类型、realpath 时机、错误码和信任根。禁止建立自动行为不透明的“大一统 SafePath 服务”。

#### F-009 — Test Fixtures Duplicate Protocol Construction
Priority: P2
Confidence: High
Evidence: `tests/commands.test.js:95,136,157,282` 与 `tests/helpers/sdd-fixtures.js:55,71,84,108` 同时维护 Challenge、Design、Completion Verification、archive-ready standard 构造；Profile/Quality/Console/Visual fixture 还重复 temp project、write、config skeleton。
Assessment: 应复用无业务含义的 fixture builders 和 temp-project factory；状态机完整错误矩阵、安全/symlink、Challenge 防伪、AC Coverage 和 Provider fail-closed 回归必须保留。测试基线为 421 tests、416 PASS、0 FAIL、5 个 Windows symlink 权限相关 SKIP，耗时约 54.3 秒。

#### F-010 — Low-Value Command and Formatting Repetition
Priority: P3
Confidence: High
Evidence: `next.js:6-62` 与 `cruise.js:48-119` 重复 workflow snapshot/blockers/archive guidance；`challenge.js:29-35` 与 `validate.js:409-419` 重复普通 Spec 选择；Profile 子命令重复 JSON/format 样板。

#### Necessary Complexity / Keep Boundaries
- 保留 `spec-state`（权威 gate/router）与 `workflow`（风险、设计方法、视觉/Profile enrichment）的职责分离。
- 保留 Quality Planner 与 Verification Readiness；前者给策略建议，后者判断实际可执行证据。
- 保留 Visual Context、Evidence Contract、Execution Config、Provider、Visual Run 五层，以及普通 E2E Run 与 Visual Run 的独立 schema/namespace。
- 保留 Registry allowlist、Workspace trust resolver、Process Gateway、Attachment Store、Fingerprint/Freshness；这些是 config-to-execution 和 evidence 信任边界。
- 保留 README/GUIDE/SKILL/Templates/Generator/Validator 的受众投影，但硬规则必须有单一来源或自动一致性检查。
- 保留 `next/status/resume/cruise/challenge` 的命令语义；只共享底层 facts 和格式片段。
- 保留历史 `Review (Verdict|Summary)` reader 兼容，除非单独确认不再读取历史 Spec；当前用户-facing `package.json` 描述和非兼容提示中的旧 Review 术语应另行清理。

## Innovate Options

### Option A — Monolithic Simplification
Option Summary: 在一个后续实现任务中同时引入 Governance Contract Registry、统一 gate evaluator、共享 parser/assessment、重构 Visual/Verification 基础设施并整理测试。
Pros: 最终形态一次到位；减少临时适配层；理论上可一次消除大部分重复。
Cons: 变更跨越公共 CLI、状态机、安全路径、证据 schema、未提交视觉候选和测试基础设施，评审与回滚边界不清。
Risks: 任一 parser、gate 或 freshness 语义变化都可能与其他重构交叉，难以定位回归；历史 Spec/Run 兼容和 fail-closed 保护容易在“大一统抽象”中被削弱。
Requirement Fit: 能覆盖全部 Findings，但不符合本 Spec 已确认的只读范围，也不符合逐项证据化和可逆性要求。
Rejected Rationale: 拒绝。收益不足以抵消爆炸半径和验证复杂度，不应由 v4.0 承载。

### Option B — Local Deduplication Only
Option Summary: 不引入新的治理模型，只做局部去重，例如合并两个 `result-contract`、复用 readiness、提取 parser/path/helper 和测试 fixture。
Pros: 每次改动小、容易验证、对外行为变化少；可以快速减少明显重复代码。
Cons: 无法解决最关键的分布式契约和多权威 gate；局部 helper 可能在没有统一语义前固化现有漂移；模块数量下降但维护决策仍分散。
Risks: 形成更多“共享工具 + 多套规则”的中间层，技术重复减少而语义重复继续存在。
Requirement Fit: 适合 P1/P2 的部分候选，不足以解决 P0。
Rejected Rationale: 不作为总体策略；仅作为分批迁移中的低风险起步动作。

### Option C — Contract-First Phased Simplification
Option Summary: v4.0 只交付审计和拆分路线；后续独立 Specs 按“契约一致性 → 结构化事实/投影 → Verification/Visual 基础设施 → 测试与低价值样板”分批实施。每批先冻结现有外部行为，再迁移共享内核。
Pros: 先解决权威事实和语义漂移，再做代码去重；每批有清晰 gate、测试、兼容和回滚边界；未提交 Visual 候选可与稳定控制面分开处理。
Cons: 需要多个 Spec；一段时间内存在兼容适配层；总历时比一次重构长。
Risks: 若拆分边界不严格，后续任务可能重复扫描；若只完成第一批而停止，部分实现重复仍会保留。
Requirement Fit: 完整满足只读审计范围、风险排序、必要复杂度保护和后续可执行性要求。
Selected Option: Option C — Contract-First Phased Simplification。
Selection Rationale: 用户已确认 v4.0“审计后拆分”。先收敛治理合同和结构化事实，能从根因上减少后续重复；分批执行可保持 CLI/error codes、历史制品、安全 containment、Provider allowlist 和 Run schema 的可验证兼容。
