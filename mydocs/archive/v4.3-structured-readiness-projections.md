## Summary

当前处于 Execute 偏差修正：独立 Research、Option A、设计与原 Plan 均已完成；用户已明确取消历史 Execute Log Coverage 格式兼容。
目标是在单次 Console detail 请求内共享 readiness assessment，并以追加、版本化、脱敏的 AC Coverage DTO 取代 Web 对 validation 英文文案的反解析。
实现必须冻结 Quality CLI、既有 Console 字段、Provider/Adapter allowlist、Run schema、freshness 与路径/Visual 边界；不新增公开命令或跨请求缓存。
Coverage 仅接受新的正式 `Step → AC Coverage → 直接 AC 记录/字段` 语法；旧 `AC Coverage Summary`、嵌套 Notes/代码块和其它非规范历史写法不再作为证据。该范围变更须重新批准 Plan 后才继续修复。

## Intake

### Requirement
requirement: 收敛 Verification readiness assessment、Quality 输入组装与服务端 AC Coverage DTO，移除 Console 从人类可读 validation 文本反解析领域状态；保持 CLI、Console API、Provider allowlist、Run schema 和脱敏边界兼容。
goal: 建立供 Quality、CLI 和 Console 各自投影的结构化就绪度事实，减少重复计算与文案耦合，同时保持现有公开契约稳定。

### Constraints
constraints: 沿用 v4.0 审计；不改动 Provider 执行、Run Store schema、Visual 验证边界或路径信任策略；Console 继续只读和脱敏；不得新增公开 CLI 命令、改变错误码或依赖文本解析；Coverage 只接受新的正式 Execute Log 语法，不兼容历史或歧义记录格式。

### Scope

- In Scope: 为单次 CLI/Console 请求收敛内部 Verification readiness assessment，使 Quality、Verification projection 和 workflow 消费同一份短生命周期事实，并保留各自的输出投影。
- In Scope: 将现有 AC declaration / Execute Log coverage record 事实以版本化、追加式的服务端 DTO 提供给 Console，移除 Web 对 `validate.issues` 英文文本的正则反解析。
- In Scope: 将 Coverage evidence grammar 收敛为新的规范 `Step → AC Coverage → 直接 AC 记录 → 直接字段/Scenario`；以共享的严格 Markdown 结构扫描器同时服务完成验证、Coverage gate 和 DTO，忽略 HTML 注释/代码块并在顶层非 Step 边界关闭上下文；格式不符的数据一律不作为证明，gate/DTO 均 fail-closed。
- In Scope: 固化 Quality 的只读、AC 派生规划语义和 CLI 的 `e2e-provider-unbound` 行为，并为 CLI、Console API/Web 与脱敏边界补充回归。
- Out of Scope: Provider 执行/Adapter 编排、Provider allowlist、Run Store schema 或持久化、Visual 链、路径信任策略、任何历史 Execute Log Coverage 格式的兼容/迁移/回填、公开 CLI 命令/错误码变更，以及 v4.4/v4.5 的基础设施与 fixture 收敛；测试 fixture 仅可改为生成新的规范格式。

### Risks

- 将跨请求缓存当作共享 assessment，会使 Provider 配置、Run、fingerprint 或 freshness 变化后得到过期结论；共享只能限定在同一次请求上下文。
- 将 Console 需要的展示 DTO 直接暴露为原始 Provider/Run 数据，可能绕过白名单、二次脱敏、受控附件或“仅被 Spec 引用的 Provider”边界。
- 为消除重复而统一 CLI 与 Console 的全部文字、JSON 或异常策略，可能破坏既有 CLI 的 `e2e-provider-unbound`、退出码和 API 兼容性。
- 把非规范历史记录当作有效证据会造成 Coverage 假阳性；反之，历史数据不再兼容是用户已确认的产品边界，必须以明确缺失/无效状态 fail-closed，而不是猜测通过。

### Initial Acceptance Hints

- 相同请求中的 Quality 与 Verification projection 至多执行一次 readiness assessment；新的请求仍会重新计算 freshness，不保留跨请求缓存。
- Console API 以追加、版本化且脱敏的结构化 AC Coverage DTO 提供缺失、PASS/FAIL/SKIPPED 与审批事实；Web 不再匹配 `validate.issues` 的英文内容。
- Quality CLI 的文本、JSON、退出码及未绑定 E2E Provider 时的 `e2e-provider-unbound` 路径保持不变；Console 继续只读、仅展示被当前 Spec 引用的 Provider。
- Provider ID/config 约束、Registry allowlist、Run `schemaVersion: 1` 和读取筛选规则保持不变；归档 Spec 继续不生成当前 Quality Plan。
- 只有新的 `Step → AC Coverage` 结构可产生 Coverage evidence；`AC Coverage Summary`、Notes、代码块或其它嵌套文本均不得影响 gate 或 DTO。

## Research

### Requirement Review

本任务处理 v4.0 F-004 所列“领域事实由多个投影重复计算”的根因，不把 Quality Planner、Verification readiness、Console/Web 或 workflow 合并成单体。v4.2 已提供当次 workflow gate 的共享事实，其中包含 AC declaration、coverage record 和 Provider readiness；v4.3 应在其基础上为 Verification、Quality 与 Console 建立最小的结构化 assessment/projection 边界。CLI、Console API 和 Web 只消费适合其职责与安全级别的投影：CLI 保留现有文本、JSON、退出码和未绑定 Provider 行为，Console 保持只读、脱敏与白名单；UI 不再从人类可读 validation 文本恢复领域状态。

### Findings

#### F-001 — Verification readiness 与 Console evidence 各自构建 assessment

`src/verification/readiness.js:11-45,47-94` 解析 AC、读取 Provider 配置和 Run，并计算 freshness/coverage；`src/verification/evidence.js:138-194` 的 Console projection 再次完成同类入口组装，虽复用了 `evaluateProviderEvidence()`（`:63-105`），但没有共享 assessment。应提取短生命周期的领域 assessment，而不是缓存其结果到后续请求。

#### F-002 — Quality 的 CLI 与 Console 组装和异常策略不一致

`src/quality/input.js:12-43` 具有另一套 AC/frontmatter 输入解析；Quality CLI 在 `src/commands/quality.js:214-230` 先从 `acFacts` 判断未绑定 Provider，维持“不调用 readiness、输出 `e2e-provider-unbound`”的既有路径（`tests/quality-cli.test.js:477-520`）。Console 的 Quality projection 则在 `src/console/projection.js:192-235` 直接执行“input → readiness → planner”，且详情请求还并列执行 Verification 与 Quality projection（`src/commands/console.js:353-367`）。共享 assessment 不得抹平 CLI 的公开语义；Console 策略须在 Design 中明确并回归保护。

#### F-003 — Web 从 validation 文案重建 AC Coverage 状态

`src/web/console.js:825-897` 以英文前缀和正则从 `validate.issues` 推断缺失、失败与 SKIPPED 的 AC Coverage；这些 issues 来自服务端 Spec index 的 archive-ready validate 结果（`src/core/spec-index.js:253-256`）。而 v4.2 的 `src/core/workflow-gate-facts.js:125-172,205-314` 已在当次检查中提供 AC declarations/records，`spec-state` 尚未将其投影到 Console API（`src/core/spec-state.js:446-459`）。应复用既有事实生成追加、版本化 Coverage DTO，并让 Web 直接渲染。

#### F-004 — 安全与兼容边界不是冗余

Provider ID/config 契约（`src/verification/contract.js:3-4,48-60`）、Adapter Registry allowlist（`src/verification/registry.js:7-17`）、Run `schemaVersion: 1` 和读取筛选（`src/verification/run-store.js:16-50,155-172`）必须保持不变。Console projection 还必须保留严格白名单、二次脱敏、受控附件和“仅当前 Spec 引用的 Provider”原则（`src/verification/evidence.js:13-39`；`tests/verification-console-projection.test.js:54-103`）；归档 Spec 继续不生成当前 Quality Plan（`src/console/projection.js:192-210`）。

### Open Questions

1. Coverage DTO 应放入既有 `workflow.facts`，还是作为 Console detail response 的新增字段；二者都必须是追加且版本化，不能删除已有 `validate` 字段。
2. Console 的未绑定 E2E 诊断是否同步采用 CLI 的 `e2e-provider-unbound`，还是显式保持当前 Console 投影；需要在 Design 锁定兼容选择与测试基线。
3. 同一 Console detail 请求共享一次 assessment 时，内部原始 assessment 与对前端暴露的脱敏 DTO 应如何分层，避免 Provider/Run 原始数据越过安全投影。

### Requirement Revision

2026-08-08：用户明确决定“要简单，不用兼容历史数据，保证新数据的合法即可”。Coverage evidence 因此只接受新的正式 `Step → AC Coverage` 语法；`AC Coverage Summary` 与任何嵌套/历史文本均不再兼容。此决定优先于原先为历史 completion summary 保留的兼容尝试，并要求 gate、DTO、Web 测试 fixture 统一按新语法 fail-closed。

### Assumptions

- v4.2 的 `workflow-gate-facts` 继续是 AC declaration、coverage record 与 workflow Provider readiness 的既有共享事实来源；v4.3 不重复建设 gate/coverage parser。
- assessment 只在单次 CLI 或 Console detail 请求内复用；每个新请求均重新读取可变配置/Run 并计算 freshness。
- 对外兼容以既有 CLI 文本、JSON、退出码和 `e2e-provider-unbound` 为硬约束；Console API 只作向后兼容的追加投影，Web 可迁移为消费该投影。
- Console 只读、脱敏、Provider 白名单/Registry、Run schema、archive Quality 不适用与路径信任边界均为不可变约束。
- 历史 Execute Log 的 Coverage summary/嵌套文本不是新数据合同的一部分；没有新的正式 Coverage block 时，系统必须报告缺失或 unavailable，不能从文本恢复状态。

## Innovate Options

### Option A — Versioned Console DTO with Request-Scoped Assessment

Option Summary: 新增内部、单请求生命周期的 Verification readiness assessment，由 Quality 与 Verification projection 按职责消费；Console detail response 以新增、版本化、脱敏的 AC Coverage DTO 暴露展示所需事实，Web 直接渲染该 DTO。CLI 保持既有文本、JSON、退出码和 `e2e-provider-unbound` 分支。
Pros: 消除主要重复与文本耦合；保留 workflow facts、CLI 与 Console view contract 的边界；DTO 为追加字段，回滚与兼容范围清晰；assessment 不跨请求缓存 freshness。
Cons: 需要定义内部 assessment、Console DTO 与不同消费者的适配边界，并为同次 detail 请求的复用补充测试。
Risks: 若原始 assessment 与 DTO 不严格隔离，可能扩大 Console 可见数据；若错误统一未绑定 Provider 策略，可能改变 CLI 行为。
Requirement Fit: 完整满足 v4.0 F-004、v4.3 安全/兼容约束和用户确认的 API 位置选择。

### Option B — Coverage DTO Only

Option Summary: 仅为 Console detail 新增 Coverage DTO，Web 停止文本反解析；Quality 和 Verification 继续分别执行 readiness/input 组装。
Pros: 改动最小，能消除 Web 对英文文案的耦合。
Cons: 保留同次请求内的 readiness 重算及 Quality/Console 语义分叉，未解决 F-004 的主要重复。
Risks: 后续仍需重复扫描这些入口，DTO 又会成为额外适配层。
Requirement Fit: 部分满足。

### Option C — Expand `workflow.facts` into a Universal View Model

Option Summary: 将 Coverage DTO、Quality 与 Console 所需的全部展示事实都放入通用 `workflow.facts`。
Pros: 单一顶层读取入口。
Cons: 混合工作流路由事实、领域 assessment 和脱敏视图数据，扩大所有 workflow 消费者的稳定契约。
Risks: API/schema 迁移面大，容易将 Console 专用数据暴露给不相关调用方。
Requirement Fit: 覆盖需求但不符合最小边界与风险控制原则。

Selected Option: Option A — Versioned Console DTO with Request-Scoped Assessment
Selection Rationale: 用户已确认新增、版本化的 Console detail 字段而非扩展通用 `workflow.facts`，并选择 Option A。该方案以最小内部共享消除重复计算和文本解析，同时冻结 CLI 的公开语义与 Console 的只读脱敏边界。

## Plan

### Step 1 — 建立 assessment、CLI 和 detail API 的失败回归

Target: `tests/verification-console-projection.test.js`；`tests/quality-cli.test.js`；`tests/console-api.test.js`。
Change: 先为内部 readiness assessment 建立最小 fixture 与可计数依赖：同一 Console detail 请求中配置读取、`runsForProvider` 和 freshness evaluator 各只触发一次；第二次请求必须重新触发。补充 Quality CLI 的 text/JSON、exit code 与未绑定 Provider 短路回归，并在 API 测试中断言既有字段仍存在而 `acCoverage` 尚不存在，从而使新断言先失败。
