## Intake

### Requirement

建立可检测、可确认、可继承并可检查漂移的 Project Engineering Profile，以 Workspace Units 表达前端、后端、共享契约及其关系。

### Constraints

- 保持 Core 技术栈中立，不能绑定 React、Spring、Playwright 或特定工程框架。
- 自动检测只生成候选事实并提供来源证据与置信度；取得当前用户明确授权并记录授权证据后，才能成为项目级工程合同。
- 首版不生成应用、不安装依赖、不自动创建 Verification Provider、不新增框架专属模板或第二个 Verification Adapter。
- Profile 与 `.sdd-config` 分离：前者描述工程事实，后者继续只承载 SDD 治理配置。已确认 Profile 使用不可变、内容寻址 revision 保存，当前指针与历史 revision 分离。
- 已有项目与空白项目都必须有明确路径；`sdd init` 继续只创建 SDD 制品，空项目由 `profile detect` 返回明确的 bootstrap Spec 引导，不创建虚构 Profile，也不静默选型。
- Profile 中发现的命令只作为工程事实和验证建议保存，不能因为检测或继承而自动执行任意命令。

### Scope

In Scope：定义版本化 Project Profile Schema；表达 workspace units、roles、root、语言/运行时/框架候选、manifest、工程命令引用、验证工具、单元关系、证据和置信度；提供只读检测、候选文件 review/人工修正、带人类授权证据的确认、不可变 revision/当前指针持久化、查看与漂移检查；让 `discover` 引用确切 revision，并允许任务声明 `affected-units`；让空白目录的 `profile detect` 输出创建 bootstrap Spec 的引导；同步 CLI、状态提示、校验、文档和测试。

Out of Scope：生成或修改业务工程；安装包、浏览器或运行时；执行探测到的任意工程命令；自动创建/修改 `.sdd-verification.json`；实现 Frontend/Backend Quality Profile；实现 visual/a11y/performance runner、后端 integration Adapter、`playwright-mcp` 或 Custom Adapter；完整 AST/运行时架构分析；跨仓库集中控制面；Profile Console UI。

### Risks

- 启发式检测可能产生误报，若没有证据、置信度和人工确认会把错误事实扩散到后续任务。
- 项目当前 Profile 会演进，而 Spec 需要可复现；若没有不可变 revision 和安全的当前指针更新，历史任务会被新 Profile 反向解释，或在多文件写入失败时指向不完整状态。
- monorepo 中嵌套 manifest、hoist、共享包和多语言服务会放大根目录归属与关系推断复杂度。
- 将检测到的 scripts 当成可执行输入会引入命令注入和意外副作用；首版必须保持检测/展示只读。
- Profile Schema 未来扩展前端和后端质量能力时需要兼容演进，不能让首版字段变成框架枚举集合。

### Initial Acceptance Hints

- 对已有 monorepo，检测结果稳定列出前端、后端和共享单元，每条推断包含来源证据与置信度，且检测过程零写入。
- 未确认的候选结果不能被 `discover` 继承；`profile confirm` 缺少当前人类授权身份或授权证据时必须零写入失败。
- 确认后生成不可变、内容寻址 revision，并以原子方式更新当前指针；相同内容重复确认不得制造语义不同的 revision。
- 新 Spec 引用确认后的确切 revision、Schema 版本和 digest，并可声明 `affected-units`；Profile 后续变化不能静默改变历史任务的上下文语义，旧 revision 必须仍可读取。
- `profile check` 能区分无漂移、可确认漂移和结构/路径失效，不自动覆盖 Profile。
- SDD 已初始化但尚无工程单元的空白项目执行 `profile detect` 时不写 Profile，返回 empty 状态和创建 bootstrap standard Spec 的明确引导；`sdd init` 行为保持不变。
- Profile 检测不得安装依赖、执行 package scripts、创建 Provider 或修改业务文件。

## Research

### Requirement Review

本任务解决的不是“给 SDD 增加前端模式或后端模式”，而是补齐项目级工程上下文层。SDD 应继续作为技术栈中立的控制协议，但需要稳定知道仓库由哪些工程单元组成、各单元承担什么角色、使用哪些工程工具以及单元之间如何依赖。任务级 Spec 再基于 `affected-units` 决定应关注前端、后端或跨边界契约，避免把整个项目压缩成单一 `frontend`、`backend` 或 `fullstack` 标签。

### Findings

1. 当前 `sdd init` 只创建 docs root、`.sdd-config` 和宿主 Agent 配置，不扫描或分类工程技术栈；默认 mode 为 micro，不能承担新项目技术选型。
2. 当前 `sdd discover` 创建 Spec、Design、Execute Log，记录 Git 基线并自动绑定同名 context 目录，但不会继承结构化工程画像。
3. 当前规范要求 Agent 在 Research 中读取 eslint、tsconfig、测试框架、CI gate 等项目惯例。这形成了“每个任务重新研究”的软继承，但没有稳定、可复用、可检查漂移的项目合同。
4. `sdd codemap` 是只读按需视图，能扫描常见源码扩展、JS/TS import/require 和根 `package.json` 依赖；它不识别完整 workspace topology，不持久化，也不适合作为 Project Profile 真相源。
5. 现有 workflow `riskFlags` 识别 security、billing、migration、public API、irreversible 等任务风险，并路由 Design focus；它不识别 frontend/backend/shared 单元，也不知道任务是否跨单元。
6. v3.0 Verification Provider 已支持 `workspaceRoot`/`packageRoot`，但 Provider 必须显式初始化。Project Profile 可以发现并建议既有验证工具，不能自动创建 Provider 或改变 fail-closed 语义。
7. 对同仓库共同发布的前后端，应使用一个 SDD 根和多个 Workspace Units；只有独立仓库、独立发布生命周期才分别初始化 SDD。跨仓库控制不属于首版范围。
8. v3.2 已证明“命令可调用”不等于“用户已授权”。Profile 确认会改变后续任务继承的项目级事实，因此必须拥有独立的人类授权门禁，不能把命令名或 Agent 自主调用当成授权。
9. 当前已安装的 Codex SDD skill 与仓库源码存在漂移，这是独立的交付同步问题；Profile 功能不应借机扩大到 skill 安装修复。

### Assumptions

- 首版在 docs root 下保存一个轻量当前指针和不可变、内容寻址、可提交的 JSON revisions。`confirm` 先完整写入并校验 revision，再原子更新当前指针；Spec 直接引用 revision 路径、Schema 版本和 digest，而不是只引用可变当前文件。最终路径、canonicalization 和故障恢复协议在 Design 中固定。
- 每个 Unit 使用稳定 ID 和项目相对 `root`；`roles` 是受约束数组，覆盖 frontend、backend、contract、library、tool、unknown，同一 Unit 可具有多个 roles，不把具体框架写进 role。
- 检测器只读取受项目根 containment 约束的 manifest、配置、目录和 CI 文件；所有推断记录 evidence，未知事实保持 unknown，不猜测。
- `detect` 将候选 JSON 输出到 stdout；用户可将其保存并修正，`review --candidate` 负责严格校验、canonicalize 和输出待授权 digest。`confirm` 是唯一允许写入 Profile 的入口，并要求 candidate 文件、expected digest、`human:<name>` 授权身份和非空单行授权证据；缺失、格式非法、source stale 或 digest 不一致时，在任何 revision/指针写入前失败。Agent 必须暂停并取得当前用户明确授权，不能自行构造授权字段。`detect`、`review`、`show`、`check` 保持只读。
- Spec 通过不可变 revision 路径、Schema 版本和 digest 固定创建时语义；后续漂移通过显式检查暴露，不回写历史 Spec，也不删除仍被 Spec 引用的 revision。
- 空白项目入口固定为：先执行现有 `sdd init`，再执行 `sdd profile detect`；若没有可验证工程单元，命令返回 `PROFILE_STATE: empty` 和 `NEXT_ACTION: create_bootstrap_spec`，并给出 standard `sdd discover` 建议。产品意图进入 bootstrap Spec，待工程事实产生后再 detect/confirm Profile。
- `affected-units` 首版用于校验引用和输出 advisory 提示，不自动修改 mode，也不自动执行单元命令。

### Confirmed Requirement

Scope Boundary: 新增项目级工程上下文能力，覆盖 Profile Schema、Workspace Unit/Relation 表达、只读检测、人类授权确认、不可变 revision/当前指针持久化、查看、漂移检查、Spec 精确 revision 引用与 `affected-units` 校验、空项目 bootstrap 引导，以及相应 CLI/文档/测试；不进入工程生成、依赖安装、命令执行、Provider 自动配置或领域质量 Profile。
Irreversibility: 功能本身可回滚；Profile revision 是新增且可审计的项目制品。确认必须先安全提交不可变 revision，再原子更新当前指针；失败不得损坏旧指针或既有 revision。Schema 一旦发布会形成兼容承诺，因此必须从 v1 开始版本化并拒绝未知破坏性版本；仍被 Spec 引用的 revision 不得自动清理。
Impact Radius: CLI 命令注册、项目扫描与 containment、Profile Schema/存储、`discover` frontmatter/模板、workflow advisory、validate/status/next、install-skill 文档与测试夹具；不修改 Console UI、Verification Contract、Adapter Registry 或业务代码生成。
Dependencies & Constraints: 仅使用 Node.js Core 与现有依赖；支持从仓库内 manifest/config/CI 静态读取事实，禁止执行项目脚本和网络探测；Profile 与治理配置分离；自动检测必须可解释、可重复、fail-closed；确认写入必须取得当前人类授权并保存审计证据，禁止 Agent 自行授权。
Acceptance Intent: 用多类 fixture 验证已有单包、前后端 monorepo、混合语言和空白目录；证明候选检测零写入、未授权 confirm 零写入、授权确认生成可复用不可变 revision、指针失败不破坏既有状态、Spec 可读取历史 revision、漂移可观察且不自动覆盖、空目录返回 bootstrap 引导、路径逃逸和恶意 manifest 内容被安全处理，同时保证现有 init/discover/codemap/verify 行为不回归。

## Innovate Options

Option A（已由用户选择并固化于 Technical Design）：持久化 Project Engineering Profile + Workspace Topology，提供 `detect → review → human-authorized confirm → immutable revision/current pointer → inherit → check` 闭环；空项目由 detect 明确路由到 bootstrap Spec。优点是一次确认、多任务复用、历史可复现、可审计且能支撑后续前端/后端质量路由；代价是引入 Schema 版本、canonical digest、两阶段文件提交、授权审计和漂移语义。

Option B（拒绝）：只增强 `codemap` 或 Research prompt，每次任务动态检测，不持久化 Profile。改动较小，但继续依赖 Agent 重复研究，无法稳定继承、比较漂移或验证 `affected-units`，不能解决核心问题。

Option C（拒绝）：增加 frontend/backend/fullstack 模式和框架专属模板。短期引导直观，但会把 SDD Core 与具体技术栈绑定，无法表达同仓库多单元和共享契约，也会造成模板组合膨胀。

Verification: integration

### AC-003: 候选可人工修正并绑定确切 digest

### AC-005: 不可变 Revision 与 Current Pointer 安全提交
Requirement: 历史可复现与失败恢复
Type: functional
Verification: integration
Automated: yes
Test: tests/profile-store.test.js

Scenario: revision 先于 current pointer 提交
  Given 一个 fresh、已授权 candidate
  When confirm 执行完整事务
  Then 先创建 `sha256-<digest>.json` immutable revision，再原子更新 current pointer，并仅在成功解锁后输出 confirmed/exit 0

Scenario: current 写入失败不破坏旧状态
  Given 旧 current pointer 有效
  When 新 revision 已写入但 current 原子替换失败
  Then 旧 current 保持可读，新 revision 只作为安全 orphan 保留，命令失败且后续重试可以复用 revision

Scenario: 相同事实幂等确认
  Given 相同 profile facts 已存在有效 revision 并为 current
  When 以相同 digest 再次获得授权确认
  Then 不创建语义重复 revision，不修改 immutable 文件，返回稳定 unchanged/confirmed 结果

### AC-006: Confirm 并发与解锁保持单锁 fail-closed
Requirement: 项目级单写者
Type: compatibility
Verification: integration
Automated: yes
Test: tests/profile-store.test.js

Scenario: 锁存在时立即失败
  Given `.sdd-project-profile.lock` 已存在
  When 执行 confirm
  Then 返回 `SDD_PROFILE_CONFIRM_LOCKED`、exit 2，不等待、不合并、不自动重试且不改变 revision/current

Scenario: 解锁失败优先报告
  Given 主事务成功或失败后发生解锁失败
  When confirm 返回
  Then 以 `SDD_PROFILE_CONFIRM_UNLOCK_FAILED`、exit 2 为控制结果，保留原始事务诊断并提示先检查 current/revision

### AC-007: 漂移检查只报告且不覆盖
Requirement: Profile 生命周期
Type: functional
Verification: integration
Automated: yes
Test: tests/profile-drift.test.js

Scenario: 当前工程事实未变化
  Given current revision 的 source snapshot 与重新检测结果一致
  When 执行 `sdd profile check`
  Then 返回 `PROFILE_STATE: clean`、exit 0，不写入任何文件

Scenario: 工程单元或来源发生变化
  Given manifest、unit 或 relation 相对 current revision 已新增、删除或改变
  When 执行 profile check
  Then 返回 `PROFILE_STATE: drifted`、分类差异和下一行动、exit 2，不自动 confirm 或覆盖 current

Scenario: 人工确认事实不会产生永久误报
  Given current revision 包含 detector 无法推断但已由 human evidence 确认的 role 或 relation，且对应 unit root 仍有效
  When 执行 profile check
  Then 不因自动检测仍为 unknown 而报告该人工事实丢失；若新静态证据与人工事实冲突，则报告 review-required 且不自动覆盖

### AC-009: 空白项目进入 Bootstrap Spec 而非伪造技术栈
Requirement: 新项目引导
Type: functional
Verification: integration

仅使用 Node.js Core 与现有依赖；支持从仓库内 manifest/config/CI 静态读取事实，禁止执行项目脚本和网络探测；Profile 与治理配置分离；自动检测必须可解释、可重复、fail-closed；确认写入必须取得当前人类授权并保存审计证据，禁止 Agent 自行授权。

## 坑点与风险
Candidate 文件让用户可以纠正启发式结果，但比全自动确认多一步；这是防止误判进入长期项目合同的必要成本。内容寻址 revision + current pointer 比单一可变 JSON 复杂，但解决历史可复现、幂等和失败恢复。多语言 v1 以 manifest 级识别为主，非 Node 依赖关系可能保持 unknown；宁可显式 unknown/human evidence，也不做低质量猜测。CLI 人类身份字段只能审计声明，不能认证真实操作者；真正身份认证不在本地 SDD Core 范围。v1 不做 Console 和领域质量路由，换取可控的 Schema/存储/继承基础。
