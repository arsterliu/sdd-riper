## Learning Record

Source Spec: mydocs/specs/v4.3-structured-readiness-projections.md
Trigger: Execute Log 出现 DEVIATED_MAJOR（用户明确取消历史 Coverage 兼容）和 BUGFIX；独立 Challenge 先后发现 Spec 完成验证注释遗留 Summary 语义、以及 append-only 日志中 completion-verification 未位于末尾。
Observed Problem: 代码、扫描器和模板已只接受新的正式 Step/AC Coverage 语法，但控制面的一句旧说明仍要求 Summary；修正该说明后，新增的完成验证又因追加位置错误而未覆盖最新 Step。
Root Cause: 将“数据语法收敛”误当作解析器改动，没有把 Spec 完成门禁、用户文档、模板和 Execute Log 的物理顺序一起作为同一份审计契约复核。
Decision Rule: 当审计证据的正式语法发生不兼容收敛时，必须以单一共享扫描器定义合法输入，并同步核对 Spec、Design、Plan、模板、指南和 Web DTO；所有旧 Summary/Notes/注释/代码块只能 fail-closed。每次追加执行事实后，最后一个正式 Step 必须是完整的 completion-verification，且它覆盖此前全部修正。
Applies When: 新增、替换或收紧 Execute Log、验收证据、Completion Verification、gate、validate 或投影 DTO 的结构化语法时。
Does Not Apply When: 仅阅读已归档的历史制品，且用户未要求其重新满足当前 archive-ready 或 Coverage evidence 合约时；该场景保持只读，不迁移或回填。
Recommended Action: 先在受控 fixture 中写出新语法的通过与旧语法 fail-closed 的测试；变更前后搜索 `Summary` 及语义同义表述；在 Challenge 前检查 Execute Log 的末尾 formal Step 和 completion contract；由独立只读审查同时核对代码行为与控制面文本。
Evidence: `npm.cmd test` 为 483 PASS、5 SKIP、0 FAIL；严格扫描器与治理回归为 42 PASS、0 SKIP、0 FAIL；`git diff --check` 通过。`subagent:challenge_review_43` 记录 FAIL_SPEC 后定位旧 Summary 注释；`subagent:challenge_recheck_43` 记录 FAIL_LOG 后定位 completion 顺序，最终复核 PASS。
