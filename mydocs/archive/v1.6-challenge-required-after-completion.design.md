## Technical Design

Selected Option / ADR:
选择在现有 validation / workflow / resume 上增加显式 Challenge-required 状态。拒绝让 CLI 自动记录 Challenge，因为当前 CLI 不具备独立模型执行器，自动记录会破坏 Challenge Evidence 的可信边界。
Requirement Traceability:
AC-001 由 `resume` 阶段推导覆盖；AC-002 由 `workflow.analyzeSpec` / `next` 输出覆盖；AC-003 由 `validateChallengeEvidence` 文案覆盖；AC-004 由已记录 PASS 的兼容路径覆盖。
Impact Scope:
影响 CLI 工作流提示与归档门禁问题文案，不改变 Spec 模板结构、不改变 Challenge evidence 字段、不改变 archive 移动行为。
Context / Boundary:
SDD CLI 负责状态路由和门禁校验；宿主 agent 负责派发 subagent 执行真实 Challenge；`sdd challenge --record-result` 负责写回结果。边界内不包含模型调用或自动审查执行。
Domain Model:
新增概念是“Challenge required”：Plan 已批准且 Completion Verification 已存在，但 Challenge Executed By / Challenge Executed At / Challenge Evidence 任一字段尚未填充，或 Challenge Executed At 早于 Execute Log 的最新 Timestamp。该状态位于 Execute 完成之后、Learning/Archive 之前。
Architecture View:
`resume` 从 latest spec 读取 Plan approval、Completion Verification、Challenge evidence 与 Execute Log 最新 Timestamp，输出 `PHASE_HINT: challenge`。`workflow.analyzeSpec` 读取 archive-ready validation issues，若缺失或过期 Challenge evidence，则输出 `NEXT_ACTION: run_challenge` 与 `BACKTRACK_TARGET: Challenge`。`validate` 在 archive-ready 模式下继续阻止归档，并输出可执行命令。
Data Model / Schema:
不新增持久化字段。复用 Spec 中的 `Challenge Verdict`、`Challenge Executed By`、`Challenge Evidence` 等现有字段。
Data Migration / Backfill:
无需迁移。旧 Spec 若缺 Challenge evidence，在 archive-ready 时会收到更明确的问题提示。
Interface Contract:
`sdd resume <dir>` 在待 Challenge 时输出 `PHASE_HINT: challenge`。`sdd next <dir>` 在待 Challenge 时输出 `NEXT_ACTION: run_challenge`。`sdd validate <dir> --archive-ready` 在待 Challenge 时失败，并包含 `sdd challenge` 与 `sdd challenge --record-result` 指引。
API Protocol:
无网络 API 或外部协议变化。CLI 输出文本是本次行为契约。
State / Concurrency:
无并发状态变更。状态由当前 Spec 和 Execute Log 静态推导。
Failure Modes:
若 Challenge 已记录 FAIL_* 且 evidence 完整、没有新的执行日志，仍按现有失败 verdict 回退。若 Challenge 已 PASS 但存在 Learning 或 AC Coverage blocker，仍由 validation blocker 决定后续修复路径。若 Challenge 缺失、evidence 不完整，或 Challenge Executed At 早于最新 Execute Log Timestamp，则明确要求 run_challenge，避免继续信任无效 verdict。
Security / Permission:
不降低 standard/lite 必须 subagent Challenge 的约束；不允许 auto-gate 或手工字段替代 `sdd challenge --record-result`。
Observability:
通过 `resume`、`next`、`validate` 的可见 CLI 输出暴露状态；测试断言这些输出。
Performance / Capacity:
仅增加少量字符串判断和已有文件读取，不影响性能。
Compatibility / Rollback:
兼容既有命令参数和 Spec 字段。回滚方式是恢复 `resume` / `workflow` / `validate` 的旧判断与文案。
Test Strategy:
使用 node:test 的 CLI 集成测试。先构造缺 Challenge evidence 的 standard spec，验证 RED；再实现最小逻辑并跑 `node --test tests\commands.test.js` 与全量 `node --test tests\*.test.js`。第三轮回归新增 stale Challenge evidence 场景：先记录 Challenge PASS 或 FAIL_CODE，再追加 BUGFIX 与新的 completion-verification DONE，断言 resume/next/validate 都要求重新 Challenge，不能继续沿用旧 verdict 的回退路径。第四轮回归新增 partial evidence 场景：verdict 存在但 Executed At 缺失时，resume/next/validate 仍要求重新 Challenge 并提示 `--record-result`。
Implementation Notes:
completion-verification 的状态解析必须先剔除 HTML 注释，再读取真实执行块中的 `Step: completion-verification` 与 `Status:`。否则 Execute Log 模板注释里的示例会被误判为已完成执行，导致 Challenge 在实际未完成时被提前要求或允许进入后续门禁。stale Challenge 的重跑判断不能只覆盖旧 verdict 为 FAIL_CODE 的情况；只要 `Challenge Executed At` 不晚于最新 Execute Log `Timestamp`，无论旧 verdict 是 PASS 还是任意 `FAIL_*`，都必须优先路由到 `run_challenge`。

Risks / Trade-offs:
该方案保障“不会漏掉应执行的 Challenge”，但不自动运行独立 reviewer。这个取舍保留了 Challenge Evidence 的真实性；代价是宿主 agent 仍需按提示派发 subagent 并记录结果。
