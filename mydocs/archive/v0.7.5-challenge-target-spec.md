## Summary

为 `sdd challenge` 补齐可审计的目标 Spec 选择：生成审查提示和记录审查结果必须使用同一份、项目内且未归档的活动 Spec，避免多个活动任务并存时的证据串写。

## Intake
requirement: 为 sdd challenge 提供安全且明确的目标 Spec 选择能力，使生成提示与 --record-result 都能绑定到同一活动 Spec，避免多活动 Spec 时误写。
goal: 支持以 --spec 或 --name 指定项目内活动 Spec，并保持未指定时的既有默认选择行为。
constraints: 仅限当前项目 docs root 的 specs 目录；拒绝归档、缺失和越界目标；--spec 与 --name 互斥；不放宽其他自治写入规则。

## Requirement Review

用户需要的是可显式指定 Challenge 证据归属的能力，而非仅调整默认“最新活动 Spec”选择。现有参数表面存在，但必须把生成与写入的选择语义、路径边界和活动状态收敛为同一契约，才能消除误写风险。

## Findings

- `bin/cli.js` 已声明 `challenge --spec` 与 `--name`；现有实现缺口不在命令行参数注册。
- `src/commands/challenge.js` 的记录路径自行解析目标；生成路径经 `workflow.analyzeProject()` 和 `validate.resolveSpec()` 重新选择，二者不保证指向同一文件。
- 现有 `--spec` 仅做 `path.resolve()`，未校验是否位于当前项目 docs root 的 `specs/`，也未拒绝 `status: archived`。
- `common.findLatestSpec()` 对正常场景按确定规则选取最新非归档 Spec；`--name` 的裸 slug 现有语义是选择同名最高版本，应保持兼容。
- 现有命令测试已覆盖显式 `--name` 与 `--spec` 的成功记录，但未证明未选中 Spec 不变，也未覆盖互斥参数、越界路径、归档目标或生成/记录一致性。

## Open Questions

无。用户已确认裸 `--name` 保持“同名最新活动版本”的兼容语义；带版本名称和 `--spec` 必须精确定位。

## Assumptions

- 当前任务只改变 Challenge 的 Spec 选择与其帮助/文档、测试，不改变 archive、reopen、validate 或自治写入的目标选择规则。
- 归档 Spec 永不作为 Challenge 生成或结果记录的目标；没有活动 Spec 时应失败而不是回退写入归档文件。
- 不引入跨项目目标、归档回写或新的浏览器/外部 Provider 依赖。

## Innovate Options

### Option A: 在 Challenge 命令内统一并校验 selector（Selected）

- Summary: 由 `src/commands/challenge.js` 解析 `--spec`/`--name`，返回已验证的活动 Spec 路径；生成和记录两个分支复用该结果，生成提示携带规范化 selector。
- Pros: 直接解决证据归属问题；改变范围局限于 Challenge；可保持其他命令的既有 selector 兼容性。
- Cons: 与其他命令的宽松 resolver 并存，未来若需要通用安全 selector 仍须单独提炼。
- Risks: 必须同时校验词法路径和 realpath，且测试所有失败路径零写入。
- Requirement Fit: 完整满足精确选择、默认兼容和误写保护。

### Option B: 收紧 `validate.resolveSpec()` 并由 Challenge 间接复用

- Summary: 在通用 validate resolver 中添加活动状态、目录边界与互斥检查，让生成路径自然获得一致逻辑。
- Pros: 更少的 selector 实现位置。
- Cons: 会无差别改变 `validate`、`next` 等命令的历史行为，超出用户要求并引入兼容性风险。
- Risks: 可能阻断针对历史或归档制品的只读检查。
- Requirement Fit: 仅部分满足，影响范围过大。

### Option C: 只修正 `--record-result`，保持生成提示默认最新 Spec

- Summary: 记录模式支持显式目标，但生成 prompt 不携带目标。
- Pros: 代码改动最小。
- Cons: reviewer 仍会看到/复制不含目标的回写命令，不能保证同一轮审查的证据归属。
- Risks: 多活动 Spec 场景仍可能人为误写。
- Requirement Fit: 不满足“生成与记录绑定同一活动 Spec”。

Selected Option: Option A。
Selected Rationale: 用户问题的根源是 Challenge 两条路径不一致；局部统一 selector 既能使提示与结果绑定，又不扩大到其他命令的行为变更。Option B 的共用性不足以抵消兼容风险，Option C 留下核心误写路径。

为 `sdd challenge` 补齐可审计的目标 Spec 选择：生成审查提示和记录审查结果必须使用同一份、项目内且未归档的活动 Spec，避免多个活动任务并存时的证据串写。

## 关键约束
