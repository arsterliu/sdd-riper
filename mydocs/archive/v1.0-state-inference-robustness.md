## Summary
用 standard 流程加固 SDD 的默认 spec 解析（`findLatestSpec` / `resolveSpec`）。当前以文件 mtime 为主轴选「最新活跃 spec」，git checkout / clone / touch 重置 mtime 后会选错，影响 resume / next / challenge / cruise / review-execute 全链路。目标：去除对 mtime 的主依赖，改为基于 status + 版本号 + frontmatter date 的确定性判定。当前阶段：Research / Innovate 完成，待方案确认后进入 Technical Design。

## Intake

### Requirement
requirement: 提升 SDD 状态推断的鲁棒性：当前 findLatestSpec 用文件 mtime 选『最新活跃 spec』，git checkout / clone / touch 会重置 mtime，导致 resume / next / challenge / cruise / review-execute 选错 spec。改为不依赖文件系统 mtime 的可靠『活跃 spec』判定。
goal: 让默认 spec 解析在 git 操作后仍稳定正确，不再因 mtime 漂移选错任务。

### Constraints
<!-- SDD_CONSTRAINTS -->

### Scope
范围内：`common.findLatestSpec`、`validate.resolveSpec` 及其调用方的默认 spec 解析逻辑。范围外：显式 `--spec` / `--name` 传参路径（已可靠，不改）；spec 阶段推断（completionState / inferPhase）；verdict / risk 文本正则（属同主题但本 spec 不含，避免范围膨胀）。

### Risks
改默认 spec 解析会影响 resume / next / challenge / cruise / review-execute / debug / new-learning / validate 全部依赖方；必须向后兼容（常见场景行为不回退）并有充分测试。

### Initial Acceptance Hints
git checkout 重置 mtime 后仍选中正确的活跃 spec；单一非归档 spec 时零 mtime 依赖；多非归档时按确定性规则；无非归档时回退兼容。

## Research

### Requirement Review
- 歧义：「活跃 spec」定义——本次定义为「status != archived 的、版本最高/最近的 spec」。
- 隐含假设：归档 spec 已被 archive 移出 specs 目录（位于 archive/），specs 目录主要是非归档；但 reopen 可能留多个非归档。
- 风险：见 Intake Risks（影响面广，需兼容 + 测试）。
- 外部依赖：无新增。

### Findings
- `findLatestSpec`（lib/common.js）是默认 spec 解析的单点：`resolveSpec`（validate.js / workflow.analyzeProject）与 debug / new-learning / resume / review-execute 直接调用它。
- 现算法：按 task 分组取每 task mtime 最大的文件 → 跨 task 选 mtime 最大者 → task 内选最高版本。主轴是 mtime。
- 它不读 status（依赖「归档已移出 specs」的隐含前提）；版本号只在 task 内 tie-break，跨 task 不参与。
- dogfood 实测：next / validate 靠「刚编辑过 → mtime 最新」恰好选中目标 spec，但这等价于「git checkout 后必然失效」。

### Open Questions
- 多个非归档 spec 并存（如 reopen 后旧 spec 未归档）时谁是「活跃」？本次用 版本号 + date 排序；显式 active 指针留作后续。
- frontmatter `date` 是创建日期（discover 写入），非「最后活动时间」；多 spec 同日时回退版本号 + mtime。

### Assumptions
- 绝大多数项目同一时刻只有一个非归档 spec → 该场景应完全不依赖 mtime。
- frontmatter `date` 与文件名版本号可稳定解析（已有 parseFileName / getFrontmatterField）。

### Confirmed Requirement
将 `findLatestSpec` / `resolveSpec` 的默认解析改为：
1. 仅在 status != archived 的 spec 中选取；
2. 若非归档 spec 唯一 → 直接返回，不读取 mtime；
3. 多个非归档 → 排序优先级：frontmatter date（新→旧）> 文件名版本号（高→低）> mtime（仅最后 tie-break）；
4. 无非归档 spec → 回退到现有全量逻辑（向后兼容）；
5. 不引入新配置 / 新状态 / 新元数据字段。

## Innovate Options
<!-- Compare at least two options. Write the option analysis in Chinese. -->
- 选项 1 — 显式 active 指针（`.sdd-config` 或 `specs/.active` 记录活跃 slug）。优点：语义最明确、最可靠。缺点：引入新状态，切任务 / reopen 时要维护，漏更新即失准，违背 SDD「少状态、产物自描述」。requirement fit：高，但成本高。
- 选项 2（推荐）— 分层确定性排序（status 过滤 + 单一即定 + 版本/date 排序 + mtime 仅兜底）。优点：低风险、零新状态、向后兼容；彻底解决最常见「单活跃 spec + git checkout」场景。缺点：多非归档并存时仍依赖 date/版本启发式（但不再是 mtime）。requirement fit：高。
- 选项 3 — git 时间（`git log` 最近涉及的 spec）。优点：git checkout 后准确。缺点：依赖 git、需 spawn 进程、非 git 仓库失效、复杂。requirement fit：中，成本高。
- Rejected：选项 1（状态负担，留作多活跃场景的后续增强）、选项 3（依赖与复杂度）。
- Selected（待你确认）：选项 2。
