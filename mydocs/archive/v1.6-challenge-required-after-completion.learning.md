## Learning Record

Source Spec:
mydocs/specs/v1.6-challenge-required-after-completion.md
Trigger:
Execute Log 出现多次 BUGFIX；Challenge 发现 stale evidence、partial evidence、模板注释误判和失败 verdict 复用等门禁边界问题。
Observed Problem:
流程曾把“存在 Challenge Verdict”误当成“Challenge 已经有效触发”，也曾把 Execute Log 模板注释里的 completion-verification 示例误当成真实 DONE。结果是 agent 可能跳过本应重新执行的 Challenge，或者在执行未完成时提前进入 Challenge/Archive 判断。
Root Cause:
门禁状态只检查字段存在性或旧 verdict，没有把证据完整性、证据时间新鲜度、执行日志真实块解析合并成一个统一判定。测试夹具也使用了普通 `Step 1: DONE` 或替换首个 `Status: DONE` 的写法，容易掩盖 completion-verification 的真实语义。
Decision Rule:
判断 Challenge 是否有效时，必须同时满足三项：`Challenge Executed By`、`Challenge Executed At`、`Challenge Evidence` 都非空；`Challenge Executed At` 是有效 ISO 时间；且该时间晚于 Execute Log 中最新真实 `Timestamp`。解析 Execute Log 前必须剔除 HTML 注释，只有真实 `Step: completion-verification` 且最新状态为 `DONE` 才允许进入 Challenge evidence 校验。若 evidence 缺失、不完整或过期，优先路由到 `run_challenge`，不得沿用旧 `PASS` 或任意旧 `FAIL_*` verdict。
Applies When:
standard/lite 任务完成 Execute 后进入 Challenge、Archive-ready 校验、resume/next 阶段推导，或任何基于日志时间戳判断制品 freshness 的门禁。
Does Not Apply When:
任务仍未完成 completion-verification DONE；micro 任务允许 inline Challenge 但仍应遵守 evidence 完整性和 freshness；仅展示历史 verdict 而不用于归档门禁的只读 UI 可保留旧结果但必须标注 blocker。
Recommended Action:
为每个“完成后门禁”建立专用解析函数和回归夹具：真实完成块、BLOCKED 后 DONE、缺 evidence、partial evidence、stale PASS、stale FAIL_CODE、stale 非代码 FAIL、模板注释-only 日志。归档前先运行 `resume`、`next`、`validate --archive-ready` 三类真实命令确认路由一致。
Evidence:
`node --test tests\commands.test.js` 通过 107 项；`node --test tests\*.test.js` 通过 141 项。真实命令显示 `resume` 为 `PHASE_HINT: challenge`，`next` 为 `BACKTRACK_TARGET: Challenge` / `NEXT_ACTION: run_challenge`，`validate --archive-ready` 因旧 Challenge 过期和 Learning 缺失阻止归档。
