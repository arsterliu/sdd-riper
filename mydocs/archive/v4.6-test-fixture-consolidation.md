## Summary
<!-- 3-5 lines in Chinese: current phase, goal, key constraints, latest progress. -->

当前任务承接 v4.0 的第五项、也是 Contract-First 路线的最后阶段。目标是只收敛无业务含义的测试搭建重复，例如嵌套文件写入、临时目录、显式基础配置和 CLI 子进程结果整形。状态矩阵、路径/符号链接、Provider fail-closed、Visual/Verification Run 及其领域断言继续保留在原测试中。本任务只改测试基础设施，不涉及产品界面，未启用视觉证据合同。

## Intake

### Requirement
requirement: 完成 v4.0 Contract-First 路线的最后阶段：收敛测试中无业务含义的 fixture、临时项目与配置样板，减少重复搭建代码，同时保留状态矩阵、安全路径、符号链接、Provider fail-closed 与工作流审计回归。
goal: 在不改变生产行为、CLI、Spec/Run 制品语义或测试覆盖边界的前提下，建立受控可复用的测试 fixture 基础设施，并以回归证明测试语义不被弱化。

### Constraints
constraints: 参考已归档 v4.0 至 v4.5 制品；仅共享无业务含义的测试搭建和断言辅助；不得抽象或合并状态矩阵、安全/符号链接、Provider、Visual/Verification 领域断言；不迁移或改写历史制品；Research 与 Challenge 的独立审核须经用户明确授权。

### Scope

- In Scope: 新增或完善只负责文件写入、临时目录、JSON 写入、最小 SDD 文档目录和 CLI 输出捕获的测试 helper；迁移经等价性回归证明的重复搭建代码。
- In Scope: 为 helper 的嵌套写入、字节写入、JSON、唯一临时目录及受控 CLI 输出建立单测，并回归迁移测试与全量测试。
- Out of Scope: 改动 `src/` 生产逻辑、CLI 行为、Spec/Run schema、历史制品、状态矩阵、Challenge Evidence 防伪、AC Coverage 完整性、Provider/readiness、路径/realpath/symlink 策略、Visual/Verification 领域模型或真实 Playwright 项目。

### Risks

- 将“便利的完整项目生成器”作为默认 fixture，可能隐藏 malformed/legacy/缺 Provider 等 fail-closed 分支。
- 共享 helper 若自动 realpath、自动清理任意路径或构造领域配置，可能弱化路径/符号链接安全测试。
- 将 Visual/Verification 的 Run、baseline、AC×project 或 scenario/pixel 断言混入通用 fixture，会破坏已冻结的双域边界。

### Initial Acceptance Hints

- 共享 helper 只能完成明确、无业务含义的目录/文件/JSON/临时目录与子进程结果机械操作，不推断路径信任、Provider、Spec、Run 或领域状态。
- 迁移后的测试继续覆盖原状态矩阵、安全/符号链接、Provider fail-closed 和双 Run 隔离语义；不得以默认“合法项目”掩盖失败路径。
- Challenge Evidence 必须继续由原有状态矩阵/命令回归证明不可伪造，AC Coverage 的缺失、不匹配与失败路径必须继续可观察；不得以 archive-ready 或合法 Spec 默认模板替代这些分支。
- 生产源代码、公开 CLI/error code、历史制品和领域断言保持不变；全量回归维持现有通过基线。

## Research

### Requirement Review

v4.0 F-009 将测试 fixture 的协议构造重复列为 P2 问题：`commands.test.js` 与 `tests/helpers/sdd-fixtures.js` 并行维护 Challenge、Design、completion-verification 和 archive-ready 构造，Profile、Quality、Console、Visual fixture 还各自重复临时项目、写文件和配置骨架。v4.0 同时明确该阶段只统一无业务 fixture/temp-project 样板，并保留状态矩阵和安全回归。v4.1 至 v4.5 已先后冻结治理/Provider、工作流路由、Readiness 投影和 Visual/Verification 双域边界；因此本期不能借测试去重改写任何生产或领域语义。

### Findings

- `write(filePath, content)` 的“创建父目录再写入”机械操作在多组 Visual/Verification 测试中重复出现，例如 `tests/visual-context-discovery.test.js:9`、`tests/visual-evidence-contract.test.js:9`、`tests/visual-verification-cli.test.js:9`、`tests/visual-verification-boundary.test.js:15` 与 `tests/visual-verification-readiness.test.js:14`；可抽为显式编码的 `writeText`、`writeBuffer`、`writeJson`。
- 临时根目录创建在 `tests/helpers/profile-fixtures.js:20`、`tests/helpers/quality-fixtures.js:15`、`tests/console-api.test.js:17` 和多组 Visual 测试中重复；可抽只接受固定测试 prefix 的 `makeTempDir`，但每个测试必须继续显式构造业务目录与文件。
- `tests/helpers/sdd-fixtures.js:7` 与 `tests/helpers/profile-fixtures.js:33` 的 Node CLI 子进程输出整形可共享；`tests/commands.test.js` 的 shell 字符串执行、argv、cwd、env 和故障注入则必须保留原地。
- `tests/helpers/sdd-fixtures.js` 与 `tests/commands.test.js` 都有部分 SDD 最小初始化/制品写入重复；只能共享字段定位、固定时间戳、基础 config 写入等中性构件，`createArchiveReadyStandard/Lite/Micro` 等状态矩阵 fixture 不得泛化。
- Profile、Quality 与 Commands 的 tree snapshot 分别观察 symlink target/base64、SHA-256、UTF-8 内容与 stat，不能合并为单一 snapshot helper；安全语义不同。
- `tests/state-matrix.test.js`、`tests/workflow-gate-facts.test.js`、`tests/profile-security.test.js`、Challenge Evidence 防伪、AC Coverage 完整性、Verification/Visual run-store、workspace、config、baseline 和真实 Playwright 测试均是不可弱化的领域或安全回归。

### Open Questions

无。用户已确认按 v4.0 最后阶段继续，参考材料为 v4.0；Research 已将共享边界收敛到纯测试搭建，未发现需要改变范围的阻塞项。

### Assumptions

- `tests/helpers/test-fs.js` 可作为纯 I/O helper，且只导出 `makeTempDir`、`writeText`、`writeBuffer`、`writeJson` 等明确操作；不做 realpath、自动 cleanup、外部路径信任、领域 schema、Challenge Evidence 或 AC Coverage 推断。
- 若新增最小 SDD 项目 helper，只能接受显式 docs 子目录和 config 值；不得生成“完整合法 Spec/Run”或默认 Provider。
- 每个迁移文件都应先证明 helper 自身行为，再运行该文件原有回归；全量测试在 Windows 继续使用已记录的仅测试进程 LF 归一化前置条件。

## Innovate Options
<!-- Compare at least two options. Write the option analysis in Chinese. -->

### Option A — 窄横向基础层（推荐，已选）

Option Summary: 只新增临时目录、文本/字节/JSON 写入与 Node CLI 输出捕获等纯机械 helper；按测试文件逐批替换已证明完全等价的样板。每个测试继续自行构造业务目录、Provider、Spec、Run、路径异常和领域断言。
Pros: 边界最小；不引入“默认合法项目”；可逐文件验证和回滚；直接消除 v4.0 F-009 中最稳定的重复。
Cons: 保留部分 SDD 基础 config 与项目搭建重复，短期去重幅度有限。
Risks: 若 helper 悄然增加 realpath、cleanup、默认 config 或路径推断，仍可能扩大信任边界；须以小接口和负向测试限制。
Requirement Fit: 完整符合“只共享无业务样板、保留状态矩阵与安全回归”的约束。

### Option B — 加入最小 SDD 项目 helper

Option Summary: 在 Option A 之外，提供显式 docs 目录和基础 `.sdd-config` 写入 helper。
Pros: 可进一步减少 commands 与 sdd-fixtures 的项目骨架重复。
Cons: 容易被扩展成生成完整合法 Spec/Run/Provider 的万能 fixture。
Risks: 默认值可能掩盖 Challenge Evidence、AC Coverage、Provider 或 malformed/legacy 分支。
Requirement Fit: 部分符合；需要额外边界和更高验证成本，适合在 A 的结果稳定后另立任务评估。
Rejected Rationale: 当前不选，避免将“无业务搭建”扩张为状态语义生成器。

### Option C — 一次性统一所有 fixture

Option Summary: 同时统一 Profile、Quality、Commands、Visual 和 Verification 的项目构造、snapshot 与领域配置。
Pros: 表面上减少最多重复。
Cons: 将 symlink target/base64、SHA-256、UTF-8/stat、baseline、Provider 和双 Run 领域语义混入同一抽象。
Risks: 容易弱化安全或状态矩阵断言，回滚和定位范围过大。
Requirement Fit: 不符合 v4.0 的保留边界。
Rejected Rationale: 拒绝，不能以文件数减少换取被测语义不透明。

Selected Option: Option A — 窄横向基础层
Selection Rationale: 用户明确选择 A。它以最小、可验证的共享接口消除稳定机械重复，同时让所有业务状态、失败路径与安全策略继续显式留在各自测试中。
