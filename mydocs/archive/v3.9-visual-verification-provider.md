## Summary
当前处于 Research 阶段。本任务为已启用严格视觉合同的前端 Spec 增加可重复的截图、基线比较和 diff 运行证据。
复用现有 Playwright Verification Provider 的受控进程、运行存储与附件安全边界；不把普通前端任务或无视觉材料任务变为阻塞。
Figma、网络抓取、自动批准、通用浏览器操作、a11y 与性能验证均不在本期范围内。

## Intake

### Requirement
requirement: 为已启用严格视觉验收合同的前端任务提供基于 Playwright 的截图采集、受控基线比较、视觉 diff 结果与可审计运行证据；未启用严格合同或缺少视觉材料的任务不得因此阻塞。
goal: 补齐从视觉 Context/合同到可重复视觉验收结果的闭环。

### Constraints
constraints: 仅支持本地受控 Provider 与项目内基线；不接入 Figma MCP/API 或网络抓取；不自动批准视觉结果；不实现通用浏览器控制、a11y 或性能门禁；应复用现有 Verification Provider 的安全边界。

### Scope
为 `visual-evidence: required` 且合同已就绪的 Spec 提供受控的视觉验证入口、场景截图、批准基线读取、差异判定和运行证据投影；将结果接入既有验证运行与就绪状态，而不是另建不可审计的旁路。

### Risks
- 像素差异容易受浏览器版本、字体、动画、时间和网络内容影响，必须固定受控运行条件并将不确定结果表示为 BLOCKED 或 FAIL，不能伪造 PASS。
- 基线是人工批准的证据，Provider 只能读取和比较，不能创建“已批准”状态或自动替换基线。
- 将任意浏览器命令、页面 URL 或输出路径暴露给 Provider 会破坏现有受控执行和路径边界。
- 视觉合同现有 schema v1 已被 v3.8 使用；若需要扩展，必须显式处理兼容、迁移和回滚。

### Initial Acceptance Hints
- fidelity 合同中每个 route/state/viewport 场景都能生成当前截图，并只与该场景已批准、位于受控边界内的基线比较。
- Provider 将 PASS、FAIL 与 BLOCKED 连同截图、diff 附件和脱敏诊断写入不可变运行记录；方向模式或未启用视觉合同不触发视觉验证门禁。
- 基线路径越界、缺少浏览器、缺少批准、未声明场景或工作树变化必须失败关闭或阻塞，不能静默跳过。

## Research

### Requirement Review
v3.8 已将视觉材料、一次性意图选择和严格视觉合同分层：只有用户明确选择并启用 direction/fidelity 合同时，视觉材料与基线才具备门禁意义。用户现在要求补齐 fidelity 的“运行时验收闭环”，但保持 Figma 只是 Context 来源而非前置条件，并保留人工对基线/批准的最终控制权。

### Findings
- `src/visual-evidence/contract.js` 已验证 `visual-evidence.json` schema v1：fidelity 场景必须含来源、route、state、viewport 与位于 Context realpath 边界内且人工批准的 baseline；合同就绪时 diff 状态仍固定为 `not-run`。
- `src/commands/visual.js` 仅创建和检查严格视觉合同；它没有执行浏览器、截图或 diff。
- `src/commands/verify.js` 与 `src/verification/*` 已实现受控 Provider 配置、运行前安全检查、临时 staging、不可变 run store、工作树变更检测和附件投影。
- 唯一已注册的 `playwright-test` adapter 只有 `gate` capability，面向带 Provider 的 e2e AC；Reporter 能采集测试及附件，但不会解释视觉基线或像素差异。
- 现有合同的 `route/state/viewport` 是人工验收描述，不是可执行浏览器脚本；`verify` 当前只从 e2e AC 的 Provider 分组启动受控 Playwright 测试，尚无 scenario id 到测试文件、fixture、认证/数据准备和页面稳定条件的静态映射。
- 当前无 Context 材料，因此本期必须允许“Provider 能力已配置但没有启用视觉合同”的正常状态；真正的视觉执行只由已批准的 fidelity 合同和显式场景触发。
- 现有运行模型在可识别的浏览器缺失路径会写入 BLOCKED 证据；更早发生的进程或 Reporter 握手失败仍是独立故障，不能一概归类为浏览器缺失。

### Open Questions
- Decision Question：视觉执行应扩展 `playwright-test` adapter 的 capability，还是新增一个同样受控但职责独立的 visual adapter；选择必须保持当前 gate adapter 的兼容性。
- Decision Question：scenario id 如何静态映射到项目内 Playwright 测试、fixture、认证/数据准备及稳定等待条件；不得把合同 route/state 直接当作任意 URL 或命令传入执行器。
- Decision Question：视觉结果、阈值、掩码和附件的 schema 应如何版本化；基线生命周期仍由人工控制，Provider 只读。
- Decision Question：浏览器缺失、启动失败、Reporter 握手失败、截图失败和 diff 失败的 BLOCKED/FAIL 分类优先级及其最小证据落盘条件。
以上是 Innovate/Design 必须解决的架构决策，不需要用户在本轮额外提供设计材料。

### Assumptions
- 视觉验证的目标是项目内本地前端测试环境；场景路由和状态由严格视觉合同的人工填写内容定义，不从外部 URL 自动发现。
- 已批准基线继续由人保存在合同允许的 Context 边界内；运行截图和 diff 作为不可变验证附件保存，不回写或替换基线。
- 初期只支持 Playwright 可复现的 Chromium 流程，浏览器安装、字体或外部依赖不满足时输出可审计 BLOCKED，而不是引入网络下载或环境修复副作用。
- 视觉执行只允许引用经校验的 scenario id 与项目内静态映射；认证、seed 和等待稳定条件应由受控 Playwright fixture 提供，不能由 Spec、合同或 CLI 透传任意脚本、URL、环境变量或选择器。

## Innovate Options
### Option A: 扩展现有 playwright-test adapter
Summary: 为现有 adapter 增加 visual-gate capability，并在同一 Provider 中处理普通 e2e 和视觉结果。
Pros: 复用现有配置与启动路径，新增文件较少。
Cons: 普通 e2e 成败和视觉差异的合同、基线、附件及 BLOCKED 语义混在一起，Provider 配置和后续排障难以区分。
Risks: 可能改变既有 gate 行为或让普通 e2e 不必要地依赖视觉合同。
Requirement Fit: 部分满足，但隔离与兼容成本偏高。

### Option B: 新增独立 playwright-visual adapter（Selected）
Summary: 新增只处理 fidelity 合同的 visual adapter，复用已有受控进程、run store、附件安全和工作树检测；普通 playwright-test 保持不变。
Pros: 视觉生命周期、差异 schema 和故障分类可独立演进；不影响普通 e2e；能明确限制为静态场景映射而非浏览器控制入口。
Cons: 需要新增 Provider capability、项目内配置、fixture/附件约定和结果投影。
Risks: 初期需要项目为视觉场景补充固定测试/fixture 映射；Chromium 环境不一致可能产生 BLOCKED 或 diff 失败。
Requirement Fit: 满足严格合同闭环、人工批准、离线、可审计和兼容性边界。

### Option C: 仅推荐项目直接使用 Playwright toHaveScreenshot
Summary: 不新增 SDD Provider，仅把快照断言留在项目测试中。
Pros: 接入速度最快，Playwright 原生支持。
Cons: 无法把人工批准的视觉合同、基线摘要、阈值、diff 附件和 SDD Run 统一为可审计证据。
Risks: 快照更新容易绕过人工批准，普通测试 PASS 也无法说明视觉合同已满足。
Requirement Fit: 不满足本任务的证据和门禁要求。

Selected Rationale: 选择 Option B。它将视觉验收作为受控 Provider 的独立能力，同时复用既有安全运行基础设施，避免扩大普通 e2e 的职责和攻击面。

## 目标摘要
当前处于 Research 阶段。本任务为已启用严格视觉合同的前端 Spec 增加可重复的截图、基线比较和 diff 运行证据。

## 最终方案
ADR-001：新增独立 `playwright-visual` adapter 和独立视觉 Run 命名空间，而不扩展既有 `playwright-test` 或 e2e Run schema。前者仅处理已批准 fidelity 合同的截图/diff；两类 Provider 共享受控进程、附件复制、路径校验和工作树检测等基础设施。选择理由是视觉结论以场景而非 AC 为单位，不能伪装为现有 e2e Run；独立存储保持既有 gate 行为和历史 Run 完全兼容。

## 关键约束
复用 Node 18+、当前已批准的 `playwright-test` 运行时和现有 process gateway；仅允许项目内工作区、Context realpath 内基线、固定声明场景、经校验的 scenario→fixture/test 映射和白名单附件。不得执行合同外命令、访问外部 URL、安装浏览器、下载资源或把视觉结果自动视为人工批准。

## 坑点与风险
独立 adapter 增加了配置和 fixture 接入成本，但换来 e2e 与视觉语义隔离、可审计阈值和安全执行边界。像素 diff 的环境敏感性通过固定 Chromium、静态 fixture、显式掩码/阈值和 BLOCKED 语义控制；不以放宽阈值、自动更新快照或下载运行环境来掩盖不稳定。
