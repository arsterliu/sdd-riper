## Summary
<!-- 3-5 lines in Chinese: current phase, goal, key constraints, latest progress. -->
Research 阶段：建立 Project Engineering Profile 与 Verification Provider/Adapter 之间的质量策略解释与验证规划投影。
AC 是唯一验收真相；Quality Plan 只从任务 Spec、Profile 与既有 Provider 证据派生可审阅的解释和 readiness 缺口，不拥有独立门禁、通过结论或状态流转；为保留既有 freshness 语义，仅允许其调用既有受限的本地只读 Git 检查。
当前项目没有已确认的 Project Profile，本任务 Spec 不绑定虚构 revision 或 affected-units；历史 v3.0/v3.4 制品仅作为内部研究证据。
范围已收敛为技术栈中立、显式调用的 sdd quality plan <project-dir> 只读投影；v3.5 不新增 Adapter、MCP、Console UI、安装行为或自动降级。

## Intake

### Requirement
requirement: 新增独立的质量策略与验证规划层，基于已确认的 Project Engineering Profile、affected-units 与 Acceptance Criteria，生成可审阅、可追踪的 AC 到 Verification Capability 再到 Provider readiness 映射，回答前端、后端及共享契约改动需要哪些验证证据。
goal: 在 Project Engineering Profile 的工程事实与 Provider/Adapter 的执行机制之间建立技术栈中立、可审计、fail-closed 的质量决策层，使 SDD 能系统化引导前端、后端和全栈任务的验证要求。

### Constraints
constraints: 严格区分 Profile 事实、Quality Policy 质量要求和 Provider/Adapter 执行；AC 是唯一验收真相，Quality Plan 为只读派生物，不新增确认、状态迁移、归档门禁或通过/失败权威；若其揭示需要修改 AC 或 Plan，修改仍必须通过既有 SDD 门禁确认；缺少 Provider 时报告 readiness gap；不得自动安装依赖、初始化 Provider、运行验证、项目脚本或降级。为原样复用既有 readiness freshness，唯一允许的子进程是当前 fingerprint 已限定的本地只读 Git 状态读取；不得扩展为任意 Git、Provider 或项目命令。v3.5 不新增 Adapter、Playwright MCP、Custom Adapter Registry、Console UI 或 visual/a11y/performance runner；沿用 v3.0 与 v3.4 的不可变引用和显式授权原则。

### Scope
研究并定义质量策略、验证能力词汇、任务级 Quality Plan 只读投影及 readiness 投影的职责边界；明确其与 Profile facts、Acceptance Criteria、Provider/Adapter 和 Run evidence 的接口。Quality Plan 不作为独立任务制品或第二套工作流持久化、确认或归档；实现入口收敛为 sdd quality plan <project-dir>，临时输出采用版本化 text/JSON 合同。

### Risks
- 若把检测到的工具直接提升为质量要求，会混淆“项目事实”和“治理策略”，并把启发式误报扩散为任务门禁。
- 若验证规划隐式初始化或执行 Provider，会破坏 v3.0 的显式配置、无自动降级和 fail-closed 语义。
- 若 capability 词汇直接绑定 React、Playwright 或具体后端框架，Core 会失去技术栈中立性并造成策略组合膨胀。
- 若规划不绑定任务上下文和 AC，后续 Profile、Policy 或 Provider 变化可能反向改变历史任务语义。
- 若把 Quality Plan 的建议、缺口或 freshness 解释成新的验收结论，会形成与 AC 竞争的第二套工作流，并可能绕过既有 Plan/Archive 门禁。

### Initial Acceptance Hints
- 相同的已确认工程事实、任务影响范围、AC 与策略输入必须得到确定、可解释的验证规划候选。
- 规划必须能区分 required capability、已就绪 Provider、缺失 Provider 和仅能人工提供的证据，不得把缺口自动降级为通过。
- 规划生成和 readiness 检查必须保持只读，不安装依赖、不创建 Provider、不运行测试或任意项目命令；仅可复用既有、固定参数的本地 Git freshness 读取，不能借此扩展为通用子进程能力。
- 前端、后端、共享契约和跨单元任务应通过通用角色与 capability 表达，而不是新增 frontend/backend/fullstack 工作流模式。
- Quality Plan 不得写回 AC、改变 AC 覆盖结果、单独获得批准或决定任务是否可执行、完成或归档；其建议只有在既有 Spec/Acceptance/Plan 被显式修改并经过相应门禁后才可能改变任务契约。

### Assumptions
质量能力是“所需证据的语义类别”，不等同于某个 Adapter、命令或测试框架；例如 e2e、contract、integration 可以由不同 Provider 实现。
Profile 中的 roles、relations、verification tool facts 和 commandRefs 仅是输入事实；未确认 Profile、unknown role 或未配置 Provider 必须保留为显式不确定性/缺口。
Confirmed Decision — AC / Capability Relationship: 现有 AC 的 `Verification: unit | integration | e2e | manual` 保持原义和兼容入口；Quality Plan 以独立的 capability 映射补充“为什么需要何种证据、现有 Provider 是否能产生证据”的解释，不替换、扩展或写回该字段。
Confirmed Decision — AC Authority / Quality Plan: AC 是唯一验收真相。Quality Plan 是基于确切任务 Spec（含 AC）、已绑定的不可变 Profile revision、内建策略版本和既有 Provider/Run 证据动态计算的只读投影；它不拥有独立生命周期、批准、状态迁移、通过/失败判定或归档门禁，也不能写回 AC。其建议或缺口若要求改变任务契约，只能通过既有 Spec、Acceptance 与 Plan 门禁显式处理。
Confirmed Decision — Readiness Projection: Quality Plan 不定义 `adapter-available`、`workspace-ready` 等新预检层，也不形成第二套 readiness 状态机。只有存在 `Verification: e2e` 且引用 Provider 的 capability 路线才能原样嵌入既有只读 readiness 快照 `required | configured | blocked | ready`；它绝不把“没有 e2e AC”时既有 inspect 返回的 `ready` 传播为 manual 或 unbound 路线的 Provider 就绪结论，其中 `configured` 也不能被解释为实际可执行。人工证据路线仅显示 `Manual Evidence` 要求，未绑定 Provider 的能力仅显示明确缺口，均不得伪装成 readiness 通过。缺 Profile 时仍优先返回 `profile-required`。为保持已有 `ready` 的 freshness 语义，生成允许复用 fingerprint 中固定、项目根目录内、只读的 Git 状态读取；除此之外不调用 detect、init、run、Provider、项目脚本或任意新子进程，且该快照不改变现有任何 SDD 门禁。
Confirmed Decision — Scope Routing: `affected-units: project` 在绑定的确切 Profile revision 内稳定展开为全部 unit，且必须单独出现；它与显式 unit 混用时返回 `scope-ambiguous` 缺口而不静默扩展或覆盖。重复显式 unit 按稳定顺序去重；显式 unit 则只使用其自身已知 roles。一个 unit 的多个 known roles 贡献 capability 的稳定去重并集，并保留每项 capability 的 role/policy 原因；v3.5 不引入 capability 的否定、优先级或用户覆盖规则。`unknown` role 不触发 role 推断，Quality Plan 仍列出已有 AC 事实但必须报告 `role-unknown` 缺口，不能暗示覆盖完整。relation 永不自动扩大 affected-units：双端均在有效范围内时才追加跨单元/契约能力原因；仅一端在范围内时只报告 `related-unit-out-of-scope` 建议，不替相邻 unit 生成要求。
Confirmed Decision — Missing Profile: 当 Spec 未绑定 confirmed Project Profile 时，planner 返回状态为 `profile-required` 的阻断候选。候选只列出缺失的精确 Profile 输入、任务已有 AC 事实和恢复指引，不执行 role/relation 到 capability 的推断，不形成可通过的 Verification Plan，也不自动调用 Profile detect/review/confirm；用户确认 Profile 后必须重新生成。

## Innovate Options
### Option A — 内建版本化 Policy Catalog + 纯 Quality Planner（推荐）
将 capability、role/relation 贡献规则和 AC evidence route 映射放入独立、版本化的内建 Catalog；Planner 只解析活动 Spec 的 exact Profile/AC、执行稳定 scope 归一化、组合 capability 理由，并只在实际 e2e Provider 路线上复用现有 readiness。通过显式只读 CLI 输出临时 Quality Plan（文本/JSON），不写入 Spec 或创建新的任务制品。

Pros: Profile 事实、策略和 Provider 执行严格分层；输出确定、易于 node:test 覆盖；Policy 版本与输出输入可追踪；未来可增加 Provider/Adapter 或 Catalog 规则而不改变 AC/Workflow 合同。
Cons: 首版策略变更需要代码发布；项目级定制不在 v3.5 范围。
Risks: 必须严格限制 Catalog 只表达证据建议，不能把它误接入 Plan/Archive Gate；必须为 Git freshness 例外建立负向测试。
Requirement Fit: 高，直接满足 AC 唯一权威、只读派生、exact Profile、技术栈中立和 fail-closed 缺口语义。

### Option B — 在任务 Spec 中新增可编辑 Policy 区块
把 role/capability 映射或本任务覆盖规则写入 Spec，由 Planner 读取该区块并输出结果。

Pros: 每个任务可以局部定制；初期实现表面上较直接。
Cons: 策略与 AC 同处控制面，容易被误解为第二验收来源；需要定义编辑、审核、版本和兼容规则；历史 Spec 的策略差异会削弱项目级一致性。
Risks: 用户或 Agent 可能把 Policy 区块当成新的确认门禁，违背“AC 为唯一验收真相”。
Requirement Fit: 中低，不符合保持 Quality Plan 单纯派生物的边界。

### Option C — 从 Profile 工具事实或 Provider 配置直接启发式推断
不引入独立 Policy Catalog，而从 frameworks、commandRefs、已配置 Provider 和 Adapter capability 直接推导所需验证。

Pros: 初始代码量较小；对已有 Playwright 配置可快速给出 e2e 提示。
Cons: 将工程事实或执行配置错误提升为质量要求；无 Provider 时无法给出完整前后端/契约建议；策略随工具检测漂移。
Risks: 违反事实/策略/执行分层，扩大启发式误报，并可能诱导自动执行或框架绑定。
Requirement Fit: 低，和 v3.0/v3.4 的边界冲突。

Selected Option: Option A。用户已确认采用内建版本化 Policy Catalog + 纯 Quality Planner。Catalog 只表达技术栈中立的 capability 与 evidence route 建议；Planner 只读取活动 Spec、exact Profile、Provider 配置/Run/readiness 并输出临时投影。它不持久化、不写回 AC、不触发 SDD workflow，也不引入项目级可编辑策略配置。Option B 因可能把策略提升为第二验收来源而拒绝；Option C 因混淆工程事实、Provider 执行与质量要求而拒绝。

## 目标摘要
Research 阶段：建立 Project Engineering Profile 与 Verification Provider/Adapter 之间的质量策略解释与验证规划投影。

## 最终方案
ADR-QP-001：采用“内建版本化 Policy Catalog + 纯 Quality Planner”，并以显式只读命令 sdd quality plan <project-dir> 暴露结果。

## 关键约束
仅依赖 Node.js 18+、现有 Core 依赖和仓库内制品；任何 Profile 输入必须经由 Spec 绑定的 exact revision/digest 读取，绝不以 current pointer 替代。Policy 只能消费事实，不能把 frameworks、commandRefs 或检测到的工具当成自动执行授权。缺 Profile、scope-ambiguous、unknown role、未绑定 capability 或不具备 Provider 证据时必须显式保留缺口；生成过程不得调用 profile detect/review/confirm、verify init/run、安装依赖、下载、网络、Provider 或项目脚本。唯一例外是复用既有 fingerprint 的固定本地只读 Git freshness 调用，以保持 `ready` 的既有含义；不得新增或参数化其他子进程。Quality Plan 的建议只有通过既有 Spec/Acceptance/Plan 明确变更后才能影响任务契约。

## 坑点与风险
首版故意不提供项目级策略覆盖，因此少数团队的特殊质量要求只能先通过 AC/Plan 显式表达；这是用可审计、技术栈中立的核心边界换取可预测性。Policy focus 与 AC 不建立自动覆盖关系，意味着输出不能替代人工审阅 AC 是否充分；这是避免第二验收真相的必要代价。现有 readiness 是聚合状态，首版不伪造 per-Provider/per-AC readiness；未来若真实需求出现，应先扩展既有 Verification Contract，而不是在 Quality Planner 内部复制状态机。
