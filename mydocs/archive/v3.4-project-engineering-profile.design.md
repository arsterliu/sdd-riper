# Technical Design

## Technical Design

Selected Option / ADR: 采用 Option A：新增独立的 Project Engineering Profile 子系统，以严格 Schema、纯只读 Detector Registry、可人工修正的候选文件、digest 绑定的人类授权确认、不可变内容寻址 revision、原子 current pointer、Spec 精确 revision 引用和只读 drift check 形成闭环。拒绝只增强 CodeMap/Research prompt，因为不能跨任务稳定继承；拒绝 frontend/backend/fullstack 模式，因为单标签无法表达 monorepo 多单元且会把 Core 绑定到技术栈。ADR 状态为 Accepted，依据是用户在本任务创建前确认推荐方案，Research Gate 由 `subagent:v34_research_review` PASS。

Requirement Traceability: R1“识别已有项目”由 Manifest Discovery、Detector Registry、Candidate Schema 和 evidence/confidence 覆盖；R2“人工确认”由 `profile review/confirm`、expected digest 与 human authorization gate 覆盖；R3“稳定继承”由 immutable revision、current pointer 和 Spec frontmatter 精确引用覆盖；R4“前后端共存”由 `units[].roles`、relations 与 `affected-units` 覆盖；R5“新项目引导”由 empty detection state 和 `create_bootstrap_spec` 路由覆盖；R6“漂移检查”由 source snapshot 与重新检测比较覆盖；R7“技术栈中立和无副作用”由只读 detector、无脚本执行、无网络/安装/Provider mutation 边界覆盖。

Impact Scope: 新增 `src/profile/` 下的 schema/canonicalization、detector registry、candidate、store、drift evaluator 和 error 模块；新增 `src/commands/profile.js` 并在 `bin/cli.js` 注册 `profile` 子命令；扩展 `_spec-creator.js`、spec templates、frontmatter 读取/校验、workflow/status/next 提示和 Agent 文档；`init` 只增加 profiles 目录骨架，不检测或创建 Profile。新增 profile fixtures 和 unit/integration tests。v1 不修改 Console UI、Verification Contract、Adapter Registry、`.sdd-verification.json` 或业务工程文件。

Context / Boundary: Project Profile 位于 SDD 项目控制面与具体工程之间：它读取项目内静态事实并生成可审计的工程上下文，但不拥有技术选型、脚手架、依赖安装、构建执行或测试执行。`.sdd-config` 继续只保存治理设置；CodeMap 继续是临时架构视图；Verification Provider 继续是独立、显式的验证配置。Profile 只为 Agent/Spec 提供已确认事实和 advisory，不把 detected 等同于 approved，也不把 `human:<name>` 声明误称为 CLI 身份认证。

Domain Model: `ProfileCandidate` 是检测或人工修正后等待确认的可变输入；`Evidence` 是相对路径和推断声明，不包含原文秘密；`WorkspaceUnit` 是具有稳定 ID、相对 root 和一个或多个 roles 的工程单元；`Relation` 表达单元间静态可证实关系；`ProfileRevision` 是已授权确认且不可修改的事实快照；`CurrentPointer` 指向当前 revision；`ProfileReference` 是 Spec 对确切 revision 的引用；`AffectedUnits` 是任务声明的作用范围；`DriftReport` 是当前工作区与当前 revision 的只读差异。roles 使用数组而非单值，以表达 Next.js 等同时具有 frontend/backend 能力的单元；允许值 v1 为 `frontend | backend | contract | library | tool | unknown`，框架名称单独保存在 frameworks，不进入 role 枚举。

Architecture View: C4 Context：用户/主 Agent 调用 SDD Profile CLI；Profile CLI 读取仓库静态文件，在用户确认前只输出 candidate；确认后的 revision 被 `discover`、workflow、validate 和 Agent skill 消费。Container/Component 调用链为：`profile command -> Candidate Service -> Detector Registry -> bounded filesystem readers -> canonicalizer/schema`；确认路径为 `profile confirm -> authorization/digest validation -> project lock -> candidate freshness validation -> Revision Store -> Current Pointer`；继承路径为 `discover -> Profile Resolver -> exact revision -> affected-units validator -> Spec writer`；检查路径为 `profile check -> current revision + Detector Registry -> Drift Evaluator -> report`。Detector 与 Store 通过纯数据 Contract 交互，任何 detector 都没有写文件、执行进程或访问网络的能力。

Data Model / Schema: docs root 新增 `profiles/current.json` 和 `profiles/revisions/sha256-<64hex>.json`。Candidate/Revision 使用 `schemaVersion: 1`。规范化 `profile` 包含 `detectorVersion`、`sourceSnapshot[]`、`units[]`、`relations[]`；所有数组按稳定键排序、对象键按字典序 canonicalize，UTF-8 + LF，digest 为 canonical `profile` 的 SHA-256。`sourceSnapshot` 只保存项目相对 path、kind、size 和 sha256。`units[]` 包含 `id`、相对 `root`、`roles[]`、`languages[]`、`runtimes[]`、`frameworks[]`、`manifests[]`、`commandRefs[]` 和 `evidence[]`；`commandRefs` 只保存 package manager/build tool、script/task 名和来源，不复制或执行脚本正文。`evidence[]` 包含稳定 id、相对 path、kind、claim、`confidence: high|medium|low|human`，禁止绝对路径和原文件片段。`relations[]` 包含 from/to/kind/evidenceIds/confidence。Revision envelope 额外保存 `profileDigest` 与首次 `confirmation { confirmedBy, confirmedAt, evidence }`；确认元数据不参与 profileDigest，因此相同事实复用同一 revision。`current.json` 只保存 schemaVersion、revision 相对路径和 profileDigest。Spec frontmatter 新增标量 `project-profile-revision`、`project-profile-digest`、`affected-units`；多个 unit ID 使用逗号分隔，避免引入当前 frontmatter parser 不支持的 YAML 数组。

Data Migration / Backfill: 旧项目和旧 Spec 无需迁移；缺少 `profiles/`、current pointer 或 Profile frontmatter 时维持现有 init/discover/workflow 行为。新 `sdd init` 创建 `profiles/revisions/.gitkeep`，已初始化项目在首次成功 confirm 时按需创建目录。不会自动扫描并回填历史 Spec。未来 Schema 升级必须通过显式新 revision 完成；v1 reader 对未知 major/schemaVersion fail-closed，不就地改写旧 revision。回滚代码后，新增 JSON 制品只是未消费文件，不影响业务工程；仍被 Spec 引用的 revision 不提供自动清理。

Interface Contract: `sdd profile detect <project-dir> [--format text|json]` 只读输出 `PROFILE_STATE: detected|empty`、candidate 和 `CANDIDATE_DIGEST`；empty 时 exit 0，并输出 `NEXT_ACTION: create_bootstrap_spec` 与 standard discover 建议。`sdd profile review <project-dir> --candidate <file>` 只读严格校验候选、路径和 evidence，canonicalize 后输出 exact digest，允许用户先保存并修正 detect 的 JSON。`sdd profile confirm <project-dir> --candidate <file> --expected-digest <sha256> --confirmed-by "human:<name>" --confirmation-evidence "<single-line>"` 是唯一写入口；四项参数缺一、digest 不匹配或 candidate stale 时零写入 exit 2。`sdd profile show <project-dir> [--revision <digest>] [--format text|json]` 只读验证 pointer/revision/digest 后展示。`sdd profile check <project-dir> [--format text|json]` 只读重新检测并返回 `PROFILE_STATE: clean|drifted|missing|invalid`；clean exit 0，其余需行动状态 exit 2，不自动覆盖。`sdd discover` 新增可重复 `--unit <id...>`；存在 confirmed current profile 时至少需要一个有效 unit 或保留值 `project`，否则 `SDD_PROFILE_AFFECTED_UNITS_REQUIRED` / exit 3；无 Profile 时保持旧行为。

API Protocol: text 输出面向 Agent，字段名稳定且一行一个值；JSON 输出只写 stdout 且不混入日志。Candidate 文件是严格 JSON，不接受代码、YAML 或任意 command。人工修正只允许修改 Schema 内的工程事实，并应把无法由 detector 证明的 classification evidence 标为 `confidence: human`；`review`/`confirm` 会重新检查所有 path containment、unit/relation 引用和 source snapshot。Drift 比较将 detector evidence 与重新检测事实比较；human evidence 在对应 unit root 仍存在且引用合法时保持 pinned，不因 detector 无法推断而反复报 drift；若新静态事实与 human classification 冲突，则报告 `review-required`，不能自动覆盖。Spec 创建时从 current pointer 解析 revision，将 revision path、digest 和 normalized affected unit IDs 写入 frontmatter；之后所有读取直接验证该 revision，不回退到 current pointer。

State / Concurrency: detect/review/show/check 全部无锁只读。confirm 先在锁外校验授权参数、candidate 文件可读性和 expected digest 格式，确保缺授权时零写入；随后用项目根 `.sdd-project-profile.lock` 目录进行一次非阻塞获取，锁存在立即 `SDD_PROFILE_CONFIRM_LOCKED` / exit 2，不等待、不合并、不自动重试。锁覆盖重新读取 candidate、canonicalize/digest、source freshness、current/revision 校验、revision 临时文件+原子 rename、current 临时文件+原子 rename 和解锁。提交顺序固定为 revision 后 current，因此失败最多留下未被引用的合法 orphan revision，current 永不指向缺失 revision；重试复用相同 revision。只有 revision/current 提交和解锁均成功才输出 `confirmed` / exit 0。解锁失败以 `SDD_PROFILE_CONFIRM_UNLOCK_FAILED` / exit 2 为控制结果并保留原事务诊断；持续锁定只能在确认无活动 confirm 后人工删除空锁目录，禁止按时间自动清理。

Failure Modes: `SDD_PROFILE_NOT_INITIALIZED`：无 `.sdd-config`/docs root；`SDD_PROFILE_CANDIDATE_INVALID`：Schema、引用、长度或 JSON 非法；`SDD_PROFILE_CANDIDATE_STALE`：source snapshot 与锁内工作区不一致；`SDD_PROFILE_DIGEST_MISMATCH`：expected/canonical digest 不同；`SDD_PROFILE_CONFIRM_AUTH_REQUIRED`：human identity/evidence 缺失或非法；`SDD_PROFILE_CONFIRM_LOCKED`：单写者冲突；`SDD_PROFILE_REVISION_CONFLICT`：同 digest 文件存在但 envelope/profile 校验不一致；`SDD_PROFILE_CURRENT_INVALID`：pointer 越界、revision 缺失或 digest 不符；`SDD_PROFILE_CONFIRM_UNLOCK_FAILED`：解锁失败，提示先检查 current/revision；`SDD_PROFILE_DRIFTED`：check 发现 added/removed/changed facts。所有领域阻断使用稳定 code + exit 2；命令用法错误 exit 3；内部意外错误 exit 1。主事务错误与解锁错误同时发生时，解锁错误为控制结果并附带原始诊断。

Security / Permission: 所有项目、candidate、manifest、pointer 和 revision 路径必须同时通过 lexical containment 与 realpath containment；拒绝逃逸 symlink，不跟随被忽略目录。扫描设置 maxDepth、maxFiles、maxFileSize 和总字节预算，跳过 `node_modules/.git/dist/build/target/vendor` 等目录，防止资源耗尽。package.json 使用 `JSON.parse`，其他 manifest v1 只按文件名/受限文本规则识别，禁止 `require`、eval、shell、package scripts、网络请求和依赖安装。输出/制品不保存绝对路径、环境变量、原始脚本正文或 manifest 片段；动态字符串去控制字符、限长并进行二次安全序列化。`confirmed-by` 是可审计的人类声明，不是 CLI 身份认证；Agent 规范必须要求在调用 confirm 前暂停取得当前用户授权，且不得自行构造授权证据。

Observability: 每个命令输出 `PROFILE_STATE`、`PROFILE_DIGEST`/`CANDIDATE_DIGEST`、unit 数、relation 数、evidence/confidence 摘要、`NEXT_ACTION` 和稳定错误码；JSON 模式提供同构版本化 read model。Revision 保存首次确认审计字段，Spec 保存精确 revision/digest/affected units。check 输出按 added/removed/changed/source-stale/review-required 分类的有界差异，明确标识 detector 与 human evidence 冲突，不输出文件原文。v1 不增加 Console 页面，避免把 Schema/CLI/继承和 UI 扩成同一交付面。

Performance / Capacity: 目标为常规仓库冷扫描在本机秒级完成；默认 maxDepth 8、maxFiles 20,000、单文件 1 MiB、总读取 64 MiB，超限返回明确 blocked 诊断而非部分 PASS。Detector 按已排序路径顺序执行保证确定性；只对证据源计算 SHA-256，不读取二进制和构建产物。check 可复用当前 revision 的 source path 集合做快速比较，但结果语义必须与完整检测一致；首版不实现后台缓存或 watcher。

Compatibility / Rollback: 没有 confirmed Profile 的项目保持全部旧行为；已有 Profile 后，新增 discover 参数要求只作用于该项目。旧 Spec 不要求 backfill，新 Spec 的 revision 引用不可变。`codemap`、Verification Provider 和 `.sdd-config` 接口不变。回滚时可删除命令和模板字段，保留 `mydocs/profiles/` 供人工审计；不得自动删除 revision。Schema v1 的未知字段默认拒绝，未来兼容扩展必须显式提升 reader/schema 版本并提供新 revision，不原地篡改。

Test Strategy: 采用 Node `node:test`，先为 schema/canonicalization、detector registry、store 和 drift evaluator 写 unit RED，再实现最小逻辑；CLI integration 使用真实临时目录和受控 fixtures，覆盖空目录、单 Node 包、npm/pnpm workspace、前后端 monorepo、混合语言 manifest、人工修正 candidate、source stale、未授权 confirm、digest mismatch、锁冲突、revision/current 写入故障、解锁故障、重试/idempotency、历史 revision 继承、affected unit 校验、symlink/路径逃逸、超限和恶意 scripts 不执行。回归运行现有 commands/state/verification 测试与全量 `npm.cmd test`，并运行 `doctor`、`git diff --check` 和限定残留扫描。此任务不需要 E2E Provider；所有 AC 使用 unit/integration verification。

Risks / Trade-offs: Candidate 文件让用户可以纠正启发式结果，但比全自动确认多一步；这是防止误判进入长期项目合同的必要成本。内容寻址 revision + current pointer 比单一可变 JSON 复杂，但解决历史可复现、幂等和失败恢复。多语言 v1 以 manifest 级识别为主，非 Node 依赖关系可能保持 unknown；宁可显式 unknown/human evidence，也不做低质量猜测。CLI 人类身份字段只能审计声明，不能认证真实操作者；真正身份认证不在本地 SDD Core 范围。v1 不做 Console 和领域质量路由，换取可控的 Schema/存储/继承基础。
