## Technical Design

Selected Option / ADR: ADR-001 — 采用“版本化 Console DTO + 请求级 assessment”。新增内部 Verification readiness assessment，并由现有 `readiness.inspect()` 投影既有摘要；Console detail 只构建一次 assessment，分别生成 Verification/Quality 投影和新增 `acCoverage` DTO。拒绝仅增加 DTO 而保留重复计算，也拒绝把 Console 专用视图模型扩展到通用 `workflow.facts`。

Requirement Traceability:
- AC-001：同一 Console detail 请求中的 Verification 与 Quality 复用一份 readiness assessment，新的请求仍重新计算 freshness。
- AC-002：`readiness.inspect()`、Quality CLI 的文本/JSON/退出码和 `e2e-provider-unbound` 分支保持既有契约。
- AC-003：Console detail 追加 `acCoverage` v1 DTO，Web 直接消费字段，不再匹配 `validate.issues` 文案。
- AC-004：DTO 仅输出白名单状态；Provider/Run/路径/审批人/原因等敏感或内部字段不外泄，allowlist 和当前 Spec Provider 范围保持有效。
- AC-005：归档 Spec 不生成 Quality Plan，Run schema、Provider config/Registry、Visual 和路径信任边界均不变。

Impact Scope: 主要修改 `src/verification/readiness.js`、`src/verification/evidence.js`、`src/commands/quality.js`、`src/console/projection.js`、`src/commands/console.js`、`src/core/workflow-gate-facts.js` 的可复用 Coverage facts/projection 边界和 `src/web/console.js`。相应扩展 `tests/verification-console-projection.test.js`、`tests/quality-cli.test.js`、`tests/console-projection.test.js`、`tests/console-api.test.js`、`tests/console-ui.test.js`。不修改 Provider 执行、Run Store、Provider/Adapter allowlist、Visual、路径信任或公开 CLI 注册。

Context / Boundary: assessment 是内部、不可持久化、单次 CLI/Console 请求的领域事实，不是 Run schema、跨请求缓存或 Console API。它可含内部 Provider/Run/freshness 细节；只有专门的白名单 projector 能把它变为 Console `verification` 或 `acCoverage`。严格 Markdown 结构扫描器是另一个内部纯解析边界：它统一排除 HTML 注释/代码块、识别零缩进 Step 与其范围，并供 completion-verification、Coverage facts/gate/DTO 使用。`workflow.facts` 继续承载 workflow/router 摘要，不承载 Console 专用 DTO；Quality Planner 继续只做 AC 派生建议，不执行 Provider。

Domain Model: `ReadinessAssessment` 对当前 Spec 的 E2E AC 解析、必需/缺失 Provider、受限配置、关联 Run、coverage 和 freshness 作出一次性判定。`ReadinessSummary` 是兼容 `readiness.inspect()` 的既有四字段投影。`ConsoleAcCoverage` 是从 v4.2 declaration/record facts 生成的脱敏只读视图，但 Coverage evidence 只承认新的 `Step → AC Coverage → 直接记录/字段` grammar；历史 summary、Notes、代码块或其他嵌套文本均不是领域记录。`QualityComposition` 统一“读取 Quality input → 未绑定 E2E 短路 → 注入已有 readiness summary → Planner”的应用顺序，确保 CLI 与 Console 共享组装规则而不共享呈现。

Architecture View:
```text
C4 Context
CLI quality ──┐                         ┌── Web Console
              ├── internal application ─┤
Console detail ┘                         └── Console detail API

C4 Container / request flow
Spec + config + referenced Runs
              |
              v
  ReadinessAssessment (one request only)
       |                 |                 |
       v                 v                 v
ReadinessSummary   verification projector  QualityComposition
       |                 |                 |
workflow/CLI       Console `verification`  Quality CLI / `qualityPlan`
                                             
v4.2 gate Coverage facts ──> ConsoleAcCoverage projector ──> `acCoverage` v1
```
Console detail 先创建一次 assessment；Verification projector 与 QualityComposition 接收同一只读对象。严格 Markdown scanner 先从正式 Step block 提取 completion/Coverage 的结构事实，随后 gate/DTO 从同一结果派生，独立于人类文案。Quality CLI 单独请求时仍走同一 composition，但不必创建 Console DTO。

Data Model / Schema: 内部 `ReadinessAssessment` 至少包含规范化 E2E AC/Provider 分组、Provider availability、每 Provider 的 Run evidence、coverage/freshness 结论和受控 issue code；只在调用栈内存在。新增根级 Console detail 字段 `acCoverage`：`{ schemaVersion: 1, completionState: "recorded|missing", items: [{ acId, state: "missing|pass|fail|skipped|invalid", skipApprovalState: "not_applicable|approved|incomplete" }], diagnostics: [{ code }] }`。`invalid` 覆盖例如记录指向缺失 Test 文件等既有阻断事实。DTO 不含 `test`、`reason`、`approvedBy`、`approvedAt`、Provider 配置、Run 或路径。既有 `verification`/`qualityPlan` schemaVersion 保持为 1。

Data Migration / Backfill: 不迁移、回填或兼容历史 Execute Log Coverage 数据。新的数据必须写成 `Step → AC Coverage → 直接记录/字段`；只有 `AC Coverage Summary`、Notes、代码块或任意嵌套文本的旧制品一律不形成 evidence，并在 gate/DTO 中 fail-closed 为缺失或 unavailable。DTO 在每次 detail 请求即时生成；旧 API 调用方仍可忽略新增字段。

Interface Contract: 新增内部 `assess(specContent, projectDir, specPath, deps?)` 和只读 projector；`inspect()` 继续返回 `{ state, requiredProviders, missingProviders, issues }`，内部改从 assessment 取 summary。Verification Console projector 可接收可选的当次 assessment；未传入时自行创建，保持现有直接调用与测试兼容。QualityComposition 可接收可选 summary/assessment，并且仅在 Quality input 非 blocking、E2E AC 已全部绑定时使用；否则保留 `e2e-provider-unbound` 短路。共享 scanner 的合法输入只包含零缩进 `Step...:` 内、零缩进精确 `AC Coverage:`、两空格 AC 记录、四空格正式字段/`Scenarios:` 和后者下六空格 Scenario；HTML 注释、代码块、Step 外顶层内容、Summary/Notes/嵌套字段均忽略。Coverage projector 输入此受控 facts，输出固定 DTO，不读取、兼容或解析 `validate.issues`/历史 summary。

API Protocol: `GET /api/specs/:id` 在成功 detail 响应根级追加 `acCoverage`；不删除、不改名、不重排既有字段，亦不改变 `/validate` 端点或 `validate` 字段。字段只使用稳定枚举与诊断 code；未来不兼容扩展须提升 `acCoverage.schemaVersion`，而非修改 v1 含义。Web 改按 v1 DTO 渲染，不能以 validation 文本作为任何状态来源。

State / Concurrency: assessment 由每个调用独立创建，创建完成后只读传递并在请求结束时丢弃。Console detail 同次请求最多创建一份；新的 detail/CLI 请求必须重新读取配置和 Run、重新判断 fingerprint/freshness。不得引入模块级、index cache 或跨请求 memoization；并发请求之间不共享内部对象。

Failure Modes: 缺 Provider、配置错误、Run 读取错误、coverage 不足或 freshness 失效继续按现有 readiness 的关闭失败语义产生受控 blocked/required summary。Quality input blocking 时不检查 readiness；未绑定 E2E 继续生成已有 attention 诊断。assessment/DTO 投影发生异常时，Console 返回既有的安全不可用/阻断投影与白名单 message/code，不以空值或文本猜测显示为通过。

Security / Permission: 保留 Verification config 的 Provider ID 校验、Registry allowlist、Workspace/Process 边界、Run 读取筛选和“仅当前 Spec 引用 Provider”。Console projector 延续 `safeText`、相对路径限制、message 白名单与附件控制；Coverage DTO 不输出任何原始路径、命令、token、审批人、原因或 Run 数据。此任务只读展示，不新增执行入口或权限。

Observability: 不新增 telemetry、日志格式或公开 CLI 输出。通过依赖注入的计数 double 验证 Console detail 的 assessment/readiness 调用次数；通过 DTO fixture 直接断言状态映射和无敏感字段；保留现有 workflow/validate 输出作为兼容观察面。

Performance / Capacity: 目标是在 Console detail 内消除确定的重复配置/Run/freshness 读取，代价是一个短生命周期内部对象和有限白名单投影。不得以跨请求缓存换取性能，因为 freshness 和 Run 证据是时态输入。DTO 的 items 与当前 Spec AC 数量线性相关，不枚举不相关 Provider 或无限 Run 历史。

Compatibility / Rollback: CLI 命令、参数、文本、JSON、退出码和 `e2e-provider-unbound` 保持不变；既有 Console 字段与 schema 保持可用，`acCoverage` 只追加。归档 Quality 不适用、Provider/Run schema/allowlist、Visual 与 path 规则不变。用户明确选择不兼容历史 Coverage 语法：只含 `AC Coverage Summary` 或歧义嵌套字段的历史 Execute Log 不保证 archive-ready/DTO evidence。出现实现回归时，可回退 Console 对可选 assessment 的注入或停止消费新增 DTO；不迁移、不回填旧 evidence，也不删除已有 `validate` 字段。

Test Strategy: 先写失败测试，再实现最小代码。`tests/verification-console-projection.test.js` 覆盖 assessment 到 verification 的投影、Provider 限定、freshness 和脱敏；`tests/quality-cli.test.js` 覆盖 CLI 文本/JSON/exit code 与未绑定短路不变；`tests/console-projection.test.js` 覆盖 Quality 复用 summary、blocking/archived 分支；`tests/console-api.test.js` 覆盖 detail 的新增 `acCoverage` v1、同次 request 单次 assessment 与旧字段保留；`tests/console-ui.test.js` 覆盖 `missing/pass/fail/skipped/invalid` 直接渲染及 validation 文案变化不影响 UI；`tests/workflow-gate-facts.test.js`、命令/state fixture 同时覆盖共享 scanner：新的正式 Step block 可通过，历史 Summary/Notes/代码块、代码块内 completion-verification 与 Step 外 Coverage 全部 fail-closed。最后运行这些聚焦测试、全量测试和 `git diff --check`；若历史 LF fixture 噪声重现，沿用已验证的仅测试进程 LF 归一化，不修改无关模板。

Risks / Trade-offs: 新增 assessment/composition/DTO 三个小边界，短期比直接复制函数多一层适配；换来减少重复 I/O、清楚的 CLI/API 安全契约与可测试回滚。拒绝将 Console 与 CLI 的全部诊断文字统一，因为 CLI 公开语义比内部去重更重要；拒绝把 DTO 放入 `workflow.facts`，因为会把视图版本化责任扩散至无关消费者。
