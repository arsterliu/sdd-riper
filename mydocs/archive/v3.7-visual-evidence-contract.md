## Summary
当前处于 Research 阶段，目标是补齐前端 UI 设计输入与视觉验收证据的工作流契约。
现有能力只覆盖功能性 Playwright E2E；视觉比对、无障碍和性能 runner 尚未接入。
本期将先定义并校验可追溯的视觉证据合同，不实现截图 diff、Figma 同步或新的浏览器执行器。
Research 完成后须经已授权的独立审核，才进入 Innovate、Design 与 Plan。

## Intake

### Requirement
requirement: 为真实前端项目新增可追溯的视觉验收契约：定义 UI 设计输入、视觉基线、路由/状态/视口矩阵以及执行与验收证据，为后续视觉回归 Provider 奠定边界。
goal: 让有设计稿和无设计稿两类前端任务都能在不虚构视觉依据的前提下，形成可审阅、可执行、可复核的 UI 设计与视觉验收链路。

### Constraints
constraints: 本期不实现截图 diff、Figma API 同步、视觉 Provider、无障碍或性能 runner；保持现有功能 E2E 和 Archive 门禁语义不变。

### Scope
包含：视觉设计来源与版本记录、关键页面的路由/状态/视口矩阵、基线与人工确认信息、可供 Execute Log 引用的证据定位规则，以及这些内容在 Spec、Design、文档和校验中的可追溯关系。

不包含：截图像素 diff、Figma API 或插件调用、视觉 Provider、浏览器自动执行、无障碍/性能 runner、既有功能 E2E Provider 或 Archive 门禁语义变更。

### Risks
若把未批准的截图或会变化的外部链接当作基线，后续视觉回归会产生不可审计或误导性结果；若将视觉证据直接等同于功能 E2E 通过，也会破坏既有 Verification 语义。

### Initial Acceptance Hints
有设计稿和无设计稿两种任务均能明确记录视觉依据；每项关键 UI 验收可定位到路由、状态、视口和基线/人工确认；缺少视觉依据时必须如实暴露为待确认，而不能宣称视觉通过。

## Research

### Requirement Review
需求聚焦于为真实前端项目建立“视觉依据从哪里来、何时被批准、如何在执行和验收中引用”的控制面，而不是生成或自动比对 UI。现有 Context 目录能够存放原始材料，但没有机器可读的视觉证据结构；现有 E2E 能证明交互和页面行为，不能表达视觉基线是否存在或是否已批准。因此需要新增一个小而明确的合同层，使设计稿、截图、无稿时的人工方向与后续可自动化的视觉验证形成连续链路。

### Findings
- `sdd discover` 会自动绑定 `mydocs/context/<task-name>/`，但目前只记录路径，不解析其中的 UI 设计来源、截图或状态矩阵。
- standard Spec 模板包含通用 Research、Acceptance、Plan 与独立 Design/Execute Log 引用，尚无视觉来源、视觉基线或视口矩阵字段。
- 当前 Verification registry 仅注册 `playwright-test`，其 capabilities 只有 `gate`；README/GUIDE 明确将 visual runner 列为延期能力。
- 既有 Console E2E 会在失败时保留截图作为证据，且覆盖窄屏无横向溢出；这不是受批准基线驱动的视觉比对，也不产生 visual pass/fail 语义。
- 项目以 Node 18+、内置 `node --test` 作为核心测试约定；本期适合先以纯解析/校验逻辑和模板/文档测试实现，不应引入运行时浏览器或新依赖。

### Open Questions
已解决：视觉合同不因任务属于前端而自动启用。只有任务明确要求视觉保真或 UI 设计质量确认时才启用；无设计稿任务须先形成人工确认的设计方向，再建立首版视觉基线。合同形态、字段最小集与校验严格度将在 Innovate 中比较。

### Assumptions
- 视觉原始材料继续保存在任务已有的 `context-source` 下；合同只引用项目内相对路径或可审计的外部链接，不复制或同步第三方设计文件。
- 无设计稿时允许记录“设计方向 + 人工批准”的首版基线，但不得标记为“还原设计稿”。
- 本期视觉证据的完成状态为说明性、可人工核验的信息，不新增 Archive Gate，也不替代 AC 的现有 `unit | integration | e2e | manual` Verification 枚举。
- 未声明视觉保真或 UI 设计质量确认的任务不启用视觉合同，继续遵循现有 Context、Design 与 Verification 流程。

## Innovate Options
### Option A: 仅约定 Context 文档

Summary: 在 Context 中建议创建 Markdown 文件记录截图和链接，不新增 Spec 开关、结构化清单或校验。

Pros: 改动最小；用户可自由组织材料。

Cons: 无法判断任务是否真的要求视觉验收；Plan/Execute 无稳定引用点；链接、基线和批准状态容易遗漏。

Risks: 后续 visual Provider 必须重新发明输入合同，且无法区分“未启用”与“启用但资料缺失”。

Requirement Fit: 低，只满足资料存放，不满足可追溯和可验证。

### Option B: Spec 显式启用 + Context 结构化清单

Summary: 任务在明确需要视觉保真或设计质量确认时，于 Spec 显式启用视觉合同并引用 Context 中的结构化清单；清单记录来源、页面/状态/视口矩阵、基线、批准和缺口。校验只在已启用的任务运行，结果为说明性事实，不触发新的 Archive Gate。

Pros: 激活意图、原始材料和可验证字段分层清晰；无设计稿场景可先记录已批准方向再建立首版基线；未来 visual Provider 可直接消费同一清单；对旧任务和非 UI 任务完全兼容。

Cons: 需要定义最小 Schema、解析/校验和文档；首次填写比随手放截图多一步。

Risks: Schema 过重会降低采用率；因此本期只约束可追溯所需的最小字段，不引入阈值、diff 或运行配置。

Requirement Fit: 高，满足可选启用、无稿诚实表达、可审阅和未来可扩展的全部目标。

### Option C: 直接新增视觉 Provider

Summary: 同时定义合同并接入 Playwright 截图、基线存储和 diff 结果。

Pros: 能立即自动化视觉回归。

Cons: 需要处理浏览器、字体、动画、动态数据、mask、阈值和基线治理，超出本期边界。

Risks: 在视觉依据尚未标准化时，自动化会固化错误基线，并改变既有 Verification 复杂度。

Requirement Fit: 中低，能力完整但明显超范围。

Selected Option: Option B。用户于 2026-07-30 确认采用“Spec 显式启用 + Context 结构化清单”：只在任务明确要求视觉保真或 UI 设计质量确认时启用；结果保持说明性，不新增 Archive Gate。
