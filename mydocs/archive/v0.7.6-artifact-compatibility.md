## Summary

当前阶段为 Research。任务将统一 Lite 历史制品与当前制品协议的读取兼容性，修复 Execute Log completion step 的边界和顺序门禁。只读兼容历史格式，不迁移或回写 archive；新生成格式维持当前模板。

## Intake

### Requirement
requirement: 修复 Lite Spec 与 Execute Log 在模板、执行指引、解析器和归档校验之间的格式契约不一致：兼容历史 Lite 制品的 Confirmed Requirement 标题结构；使 completion-verification 可安全承载 AC Coverage Summary；强制完成验证为最后一个正式 Execute Step；补齐回归测试，防止归档前通过修改制品格式来规避解析器缺陷。
goal: 让 Lite 及既有可读制品以统一、可验证的格式通过归档门禁，并使校验失败准确指向真实契约问题。

### Constraints
constraints: 仅修改 SDD-RIPER 制品协议、模板、解析/校验实现及测试；不重写或迁移历史归档制品；保持 standard 与 micro 的既有行为兼容；不放宽归档、Challenge、Learning 或自治门禁。

### Scope
解析 `common.scanExecuteLog()` 及 completion 状态投影、Lite Confirmed Requirement 的读取兼容、Validate/Workflow/Spec State 的共享事实、Console 提示和相关单元/命令/状态矩阵回归；不改变归档文件内容、Provider、网络接口或新的 Markdown 输出格式。

### Risks
若把旧 `AC Coverage Summary` 误当作正式 AC Coverage，会放宽归档证据；若只按时间戳或最近 completion 判断，会遗漏 completion 后的新步骤；若 Lite 回退解析过宽，可能误将 standard 或无关字段视为 Lite Research 内容。

### Initial Acceptance Hints
历史 Lite 的嵌套 Confirmed Requirement 与当前顶层格式应产生相同 Research/风险/归档结论；旧 Summary 可完整读取 completion 的四轴字段但不能产生新的 AC 证据；completion 后追加正式 Step 必须阻断 archive-ready。

## Research

### Requirement Review
问题不是 Lite 工作流本身缺少阶段，而是历史制品、当前模板、解析器和门禁消费者对同一 Markdown 结构定义不一致。修复必须以“新格式稳定、旧格式只读兼容、证据不降级”为界：不借由修改制品迎合解析器，也不把展示摘要自动提升为可归档的验证证据。

### Findings
- `lib/common.js` 仅允许固定的正式 Execute Step 顶层字段；`AC Coverage Summary:` 不在白名单，出现时会关闭当前 step，使随后四轴字段无法被 completion parser 读取。
- completion 状态和 `src/core/spec-state.js` 都寻找最后一个 completion，而不验证它是否为物理顺序上的最后一个正式 Execute Step；因此 completion 后追加执行事实可能未被直接拦截。
- 当前 `templates/execute-log.md` 已不生成旧 Summary，但 `src/web/console.js` 仍称 completion 包含 AC Coverage summary；旧 Summary 应被限制为只读兼容而非新格式或正式 AC Coverage。
- 当前 Lite 模板使用顶层 `## Confirmed Requirement`，但历史 Lite 的 `## Research` 下 `### Confirmed Requirement` 不能被 gate facts、Validate 与 Workflow 的现有 Lite 分支一致读取。
- Frozen Profile `mydocs/profiles/revisions/sha256-6a2ee110033e3d1fbfec696750d01a5fd77812a34f7b163b4999267851ae817c.json` 表明目标为根目录 Node/JavaScript 项目；其命令事实仅声明 `npm test`，不需要 Browser、Provider 或视觉基线。
- 现有测试基座覆盖 common、workflow gate facts、workflow、state matrix、commands、governance contract 和 fixture helper，可用临时 fixture 证明兼容性，不能修改 `mydocs/archive/`。

### Open Questions
无。用户已确认修复范围、standard 模式、auto 自治方式及“历史只读兼容、不迁移”的约束。

### Assumptions
- “最后一个正式 Execute Step”按 `scanExecuteLog()` 识别的 Markdown 顺序定义，completion 后的普通文本不构成新 Step。
- Lite 仅在当前顶层 Confirmed Requirement 为空时回退到 `## Research > ### Confirmed Requirement`；standard 与 micro 的既有结构和门禁保持不变。
- 历史 Summary 即使列出 AC 结果，也不替代正式步骤中的 `AC Coverage:` 记录。

## Innovate Options

### Option A: 集中式兼容读取与顺序门禁（Selected）
Summary: 在 `common` 建立最后正式 Execute Step 的共享事实，并在 gate facts 建立按 mode 选择 Confirmed Requirement 的共享读取函数；各消费者复用这些事实，旧 Summary 只在 completion 读取时兼容。
Pros: 单一协议源避免 Validate、Workflow、Spec State 的行为漂移；兼容边界可精确限定；不需要迁移历史制品。
Cons: 会触及多个消费者和测试层，需要证明所有状态投影一致。
Risks: 若共享 helper 的布局匹配过宽，可能错误识别 standard 或无关章节；若将 Summary 解析为 coverage，会放宽归档证据。
Requirement Fit: 完整满足历史只读兼容、completion 顺序强制与证据不降级。

### Option B: 仅修改模板与执行指引，要求手工修复旧制品
Summary: 保持解析器现状，只删除或改写旧 Summary，并要求历史 Lite 制品调整标题层级与 completion 排列。
Pros: 实现改动少。
Cons: 与“不迁移历史制品”和历史制品保持可读的约束冲突；仍会使 archive-ready 对旧格式产生误导性错误。
Risks: Agent 会继续为通过解析而修改证据制品，破坏审计真实性。
Requirement Fit: 不满足历史只读兼容与准确诊断。

Selected Option: Option A。
Selected Rationale: 当前缺陷的根因是多个消费者各自解释 Markdown，而不是新模板缺字段。集中式读取和明确顺序事实能用最小边界兼容历史格式，同时使新格式、正式 AC Coverage 与归档门禁保持严格。

## 目标摘要
当前阶段为 Research。任务将统一 Lite 历史制品与当前制品协议的读取兼容性，修复 Execute Log completion step 的边界和顺序门禁。只读兼容历史格式，不迁移或回写 archive；新生成格式维持当前模板。

## 最终方案
采用“集中式兼容读取与顺序门禁”。在共享层定义历史 Markdown 的窄兼容范围和最后 formal Step，再让 gate facts、Validate、Workflow 与 Spec State 消费同一事实；不通过改写旧制品解决校验问题。

## 关键约束
复用 `scanExecuteLog()`、gate facts 和既有测试 fixture；保留 current template 的新格式；兼容限定在明确的历史 Lite 嵌套结构与 completion 内的旧 Summary；必须维持 Challenge、Learning、AC Coverage 和 timestamp 独立门禁。

## 坑点与风险
兼容范围过宽会让无关文本伪装成证据，过窄会继续阻断真实历史制品；因此只按 mode、固定标题层级和 completion header 启用兼容。新增“最后 Step”门禁会暴露旧主动日志的流程缺口，但这是防止陈旧完成证明被错误复用所必需的收紧。
