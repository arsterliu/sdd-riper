## Summary

当前处于 Plan 阶段。v4.4 采用用户确认的拆分策略，只完成第一阶段：将 Visual Contract 的合法性检查与 Visual Run 的新鲜度、执行结果和状态投影分离，同时保持现有兼容组合输出。普通 Verification 与 Visual 的 Run schema、目录、领域模型、Provider allowlist、路径信任和失败关闭语义均不合并、不迁移。原路线中 Playwright result contract、Reporter 生命周期和底层不可变存证事务的精确去重，将在后续独立 Spec 中处理。

## Intake

### Requirement
requirement: 承接 v4.0 的第四项路线第一阶段，在冻结现有视觉验证行为与安全边界后，分离 Visual Contract inspection 与 Visual Run status，并以兼容组合层保持既有投影语义；Playwright 协议、受控执行和不可变证据写入的精确去重留给后续独立任务。
goal: 消除 Visual Contract 与运行时证据混合计算这一根因，为后续基础设施去重建立可验证边界，同时保持公共 CLI、Provider allowlist、Run schema、路径信任、失败关闭和历史制品读取边界不变。

### Constraints
constraints: 沿用 v4.0 及 v3.7-v3.9 归档材料；先建立可验证基线，再决定重构边界；不得未经确认合并普通 Verification 与 Visual Run 的 schema、namespace 或信任策略；不引入跨请求缓存或新的公开 CLI。

### Scope

- In Scope: 为现有 Visual Contract 建立纯合同 inspection，并以兼容组合层保留现有 `visual inspect`、`verify visual`、readiness 与 Console 所需的稳定状态/诊断输出。
- In Scope: 冻结并回归 fidelity 与 direction/not-applicable 的分流、普通 `verify run` 不受影响、Visual/Verification 独立 Run schema 与目录、Provider capability/allowlist、静态 mapping、realpath 与 fail-closed 边界。
- Out of Scope: 提取或合并 Playwright result contract、Reporter、受控 process orchestration、run-store 原子事务或附件写入；这些内容属于后续第二阶段。不得合并普通 AC×project/测试模型与 Visual scenario/pixel 模型，不得新增 CLI、改写历史 Run 或变更 Visual baseline 审批机制。

### Risks

- 若合同检查仍直接读取 Run、Provider、workspace 或 code-state，将无法区分“合同不合法”与“合同合法但运行失败/过期”，并可能改变现有 DIFF_STATUS 与诊断语义。
- 若为了减少文件而提前合并 Run schema、namespace、Provider capability 或路径策略，会破坏普通 Verification 和 Visual Evidence 的独立安全边界。
- 兼容组合层若遗漏已有未启用、direction、fidelity 或历史 Run 分支，可能造成新的 Plan blocker、伪造 ready 或暴露不应投影的原始信息。

### Initial Acceptance Hints

- `visual inspect` 的四字段输出和稳定诊断保持兼容；纯 Contract inspection 不读取 runtime Run 状态。
- `verify visual` 仍只在已启用且合同完备的 fidelity 场景执行；direction 或未启用时不写 Visual Run；普通 `verify run` 不变化。
- Visual Run 与 Verification Run 的 schema、目录、读写路径和 freshness 语义持续独立；运行状态仅由兼容组合层投影。

## Research

### Requirement Review

v4.0 F-006 指出 Visual Contract 的人工合法/批准事实与最近 Visual Run 的 PASS/FAIL/STALE 是正交事实；F-007 建议只合并完全相同的协议与事务骨架；F-008 要求共享路径原语而不合并领域信任策略。当前项目已具备独立的 Visual Provider、Visual Run store 和正常 Verification Run store。用户确认将原 v4.4 拆分：本 Spec 仅先收敛合同/运行状态边界，后续才处理精确相同的 Playwright 与存证骨架。

### Findings

- `src/commands/visual.js:115-120` 的 `visual inspect` 输出与 `src/visual-evidence/contract.js:111-180` 的合同/边界诊断是既有兼容面，须通过快照回归冻结。
- `src/commands/verify.js:171-292` 的普通 `verify run` 与 `:296-329` 的 `verify visual` 已有不同资格路径：后者只在 fidelity 执行，direction/未启用不写 Run。
- `src/verification/run-store.js:69-117,121-172` 与 `src/visual-verification/run-store.js:53-90,95-138` 的 schema、目录和领域维度不同：前者是 AC×project/测试模型，后者是 scenario/pixel 模型，不能合并。
- `src/visual-evidence/contract.js:24-76,174` 现将合同、Provider、workspace、Run 与 code-state 混合检查；需要拆成纯 Contract inspection 与兼容状态组合。
- `src/verification/adapters/playwright-test/result-contract.js:3-15` 与 `src/verification/adapters/playwright-visual/result-contract.js:3-11`，以及两类 Reporter 生命周期，是后续阶段可验证的精确重复；本期只冻结其调用边界，不提取实现。
- 只读 Research 同时确认 `src/verification/attachment-store.js:18-33` 已承载共享附件复制原语；Provider allowlist、静态映射、realpath、禁止任意命令/URL/环境输入仍是不可跨域的安全边界。

### Open Questions

无。用户已确认按两个独立、可回滚阶段推进；v4.4 只处理合同/运行状态边界，第二阶段另建 Spec。

### Assumptions

- 不改变已有 CLI、schema、namespace 或历史读取，即可通过兼容组合层向现有调用方提供与重构前等价的状态和诊断。
- `ui-impact=no`：本期不改用户界面或视觉设计，只整理视觉验证的后端控制面与投影边界，因此不启用视觉验收合同。
- 现有 Node 测试与 Visual fixture 是行为冻结的主证据；浏览器不可用时只能形成可审计 BLOCKED，不可把未执行的 Visual 场景标记为 PASS。

## Innovate Options

### Option A — 纯 Contract Inspection + 兼容组合投影（推荐）

Option Summary: 将 Visual Contract 的字段、人工批准、baseline/source 与路径合法性提取为不读取 runtime Run 的纯 inspection；由单独的兼容组合层按既有优先级叠加 Provider、workspace、code-state、Visual Run freshness 与诊断，保持现有调用方输出。
Pros: 直接解决 F-006 的事实混合；可用快照测试冻结外部语义；不触及 Run schema、CLI、Provider 执行协议或附件事务；可独立回滚。
Cons: 短期内保留组合适配层，模块数量不会立即减少。
Risks: 若组合顺序或诊断 code 变化，可能影响 `DIFF_STATUS`、readiness 与 Plan blocker；必须先写现有行为回归。
Requirement Fit: 完整匹配 v4.4 第一阶段与用户确认的拆分边界。

### Option B — 同期提取合同、协议与存证公共内核

Option Summary: 在拆分合同/状态时，一并合并 Playwright result contract、Reporter、process orchestration 和 run-store 事务。
Pros: 一次减少更多重复代码。
Cons: 跨越两类 Run 的安全边界与多个适配器，验证与回滚范围显著扩大。
Risks: 容易把普通 AC×project/测试模型与 Visual scenario/pixel 模型、namespace 或失败语义错误合并。
Requirement Fit: 不符合用户已经确认的拆分策略，留给后续第二阶段。

### Option C — 只增加测试、不调整内部边界

Option Summary: 仅补充快照测试，保留 Contract 与 Run 状态混合计算。
Pros: 风险最低、实现最少。
Cons: 无法解决 v4.0 F-006 的根因，后续协议去重仍缺乏清晰边界。
Risks: 继续让调用方依赖混合事实，未来重构成本上升。
Requirement Fit: 仅能作为基线步骤，不应成为 v4.4 的最终方案。

Selected Option: Option A — 纯 Contract Inspection + 兼容组合投影
Selection Rationale: 用户已明确选择拆分推进；Option A 将正交事实先分离，并冻结对外语义，为后续精确去重提供稳定边界。
