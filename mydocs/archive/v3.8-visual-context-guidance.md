## Summary
当前处于 Research 阶段。目标是在每个涉及前端影响面的 Spec 中，由 SDD 引导用户一次性选择视觉验收意图，并将后续资料发现与严格视觉合同分层。
Figma、上传图片、PDF、SVG、参考截图和文字说明都统一作为 Context 来源，不形成来源专属工作流。
纯后端任务跳过该引导；前后端混合任务只要影响任一前端单元即必须选择。未承诺视觉验收时，缺视觉材料不得阻塞。

## Intake

### Requirement
requirement: 让 SDD 统一接收 Figma 链接、用户上传图片/PDF/SVG、参考页面截图与文字说明等视觉 Context，自动发现和分类候选材料，仅针对缺失或歧义信息引导补充；默认不因缺视觉材料阻塞，只有任务明确承诺视觉验收却缺少可信依据时才阻断 Plan。Figma 仅作为 Context 来源，不形成独立工作流。

### Constraints
- 不接入 Figma API、浏览器、截图采集或视觉 diff；外部链接仅作为本地 Context 中的引用文本，不联网。
- 保持已有 `visual-evidence.json` schema v1 与 `visual-evidence: required` 的严格语义兼容。
- 发现层只读、稳定、受 Context realpath 边界和扫描规模限制；不得伪造人工批准、设计稿类别、场景或基线。

### Scope
- 每个新 Spec 的前端影响面判定与一次性视觉验收意图选择。
- 对 Context 资料进行候选发现、分类、缺口报告和最小化补问。
- 将已确认答案转换为既有视觉合同的草稿/启用流程，并维持条件性 Plan 门禁。

### Risks
- 仅依赖文件名会误分类；候选必须标记为推断，保留人工确认。
- 大目录、符号链接和未知二进制会造成性能或越界风险。
- 若将发现结果直接等同于视觉证据，可能让无依据任务错误通过 Plan。

### Initial Acceptance Hints
- 纯后端 Spec 不出现视觉选择；涉及前端的 Spec 只出现一次，且必须记录选择。
- 未选择高保真/方向验收时，缺视觉资料不阻塞；已确认严格验收后，合同缺口才阻塞 Plan。
- 不同来源材料使用同一发现与确认路径，Figma 不得形成特殊分支。

## Research

### Requirement Review
用户希望降低视觉 Context 的使用成本：用户可直接放入任意材料，SDD 负责检查、分类和只针对不确定信息提问。
视觉验收是每个前端相关 Spec 的显式一次性决策，而不是以“是否提到视觉关键词”触发；纯后端任务不应承担此引导。

### Findings
- 当前 `sdd visual init|inspect` 只处理已启用的严格合同；`visual-evidence` 未启用时为 `not-applicable`，因此缺材料默认不会阻塞。
- 已有合同强制来源、场景、人工批准、基线和 Context realpath 边界；`fidelity` 需要有效来源映射、合同人工批准及已批准基线，`direction` 可在批准方向后保持基线 pending。
- `validate`、`next` 和 workflow 已能将已启用但未就绪的视觉合同投影为 Plan blocker，但没有扫描、候选分类、缺口提问或来源统一层。
- 现有文档明确未实现 Figma 同步、浏览器截图、视觉 diff、无障碍和性能视觉门禁；本期不扩大到这些能力。
- 证据来源：`src/commands/visual.js`、`src/visual-evidence/contract.js`、`src/commands/validate.js`、`src/core/workflow.js`、`src/commands/next.js`、`SKILL.md` 及 `tests/visual-evidence-*.test.js`。

### Open Questions
无。视觉意图选择、前端影响面判定和条件性阻塞规则均已由用户确认。

### Assumptions
- 项目 Profile / `affected-units` 可用于识别前端单元；信息不足时 SDD 以一次 Intake 问题补充“是否影响用户界面”。
- 视觉选择至少包含“不需要视觉验收”“方向确认”“高保真验收”；内部字段不要求用户手填。
- 发现层输出候选和缺口，只有用户确认后才能写入或启用严格视觉合同。
- 选择结果必须记录在独立于 `visual-evidence` 的字段或制品中；已有 `visual-evidence` 仅保留空或 `required` 的严格合同语义，不能把“无需视觉验收”误写成已启用合同。

## Innovate Options
### Option A: 独立视觉 Context 引导层（Selected）
Summary: 在严格视觉合同之前新增 ui-impact/intent 选择与只读发现层；用户确认后再显式启用现有合同。
Pros: 用户不需手填 JSON；不改变既有合同 schema；普通前端与纯后端流程成本可控；来源天然统一。
Cons: 新增两个前置字段与发现命令。
Risks: 候选分类可能不准确，必须保持为提示而非事实。
Requirement Fit: 满足一次性选择、自动发现、最小补问与条件性阻塞。

### Option B: 将未确认候选直接写入 visual-evidence.json
Summary: 用同一个 manifest 存储发现结果、审批和严格证据。
Pros: 文件和概念较少。
Cons: 候选与证据混淆，可能误阻塞或伪造启用状态。
Risks: 破坏现有 schema v1 的安全边界。
Requirement Fit: 不满足“发现不等于确认”的关键约束。

### Option C: 仅由 Skill 每次临时提示
Summary: 不增加任何状态和命令，依赖 Agent 在对话中扫描并提问。
Pros: 实现量最小。
Cons: 不能保证每个前端 Spec 只选一次；选择不可审计；无法让 CLI 稳定投影。
Risks: 不同 Agent 的行为不一致。
Requirement Fit: 不满足 SDD 负责检查和分类的要求。

Selected Rationale: 选择 Option A。它将便利层与证据层分离，保留当前严格合同的可信边界，并为未来 Figma MCP 导入提供统一落点而不把外部授权引入本期。
