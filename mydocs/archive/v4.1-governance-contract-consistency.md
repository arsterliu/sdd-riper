## Summary
当前阶段为 Plan，且已获用户批准正式 Technical Design。任务承接 v4.0 的 P0「分布式治理契约漂移」，只收敛可执行合同及其受众投影，不处理工作流 gate facts、readiness 投影或 Visual/Verification 基础设施。
最小 Runtime Contract Registry 将成为离散治理事实的唯一可执行来源；文本模板、Skill、文档、package 和 AI 配置仍按各自读者保留，但由合同测试约束。
Plan 已将测试先行、运行时迁移、投影融合、历史兼容和全量验证拆分；可进入 Execute，但尚未开始修改产品代码。

## Intake

### Requirement
requirement: 基于 v4.0 架构冗余审计的 P0 结论，统一 mode required/recommended 字段、E2E Provider 契约、默认值以及 verdict/reviewer grammar；修复 package 与 AI 配置中的治理合同漂移；建立跨模板、Skill、生成器、validator、状态机和文档投影的一致性测试。
goal: 建立可执行、可审计的治理合同单一来源；在保持现有 CLI、历史制品读取和 fail-closed 语义兼容的前提下，消除 P0 分布式契约漂移。

### Constraints
constraints: 以 v4.0 归档 Spec、Design、Execute Log 和 Learning 为决策背景；不得顺带实施 workflow gate facts 单一化、结构化 readiness projection、Visual/Verification 基础设施或测试 fixture 的后续任务；保持现有公共 CLI 标签、error codes、历史 Spec 兼容和 reviewer evidence 防伪边界。

### Scope
- In Scope: mode 专属字段及其 required/recommended 级别、E2E Provider 元数据、默认值、Challenge verdict 与 reviewer identity grammar 的可执行合同；模板、SKILL、README/GUIDE、package、生成器和根 AI 配置等受众投影；相关 validator/state/readiness 消费点及一致性测试。
- Out of Scope: 抽取或合并 `validate` 与 `spec-state` 的全部 gate facts/routing；结构化 Verification/Quality/Console readiness projection；Visual/Verification Provider、Run schema、path 安全或 fixture 重构；变更公共 CLI 标签、error codes、归档制品内容或既有 Run schema。

### Risks
- 新合同若直接收紧历史 Spec，会改变归档读取或 archive-ready 诊断；必须明确活动制品的严格要求与历史制品的宽容读取。
- 用文案同步替代可执行合同，仍会留下多个权威来源并再次漂移。
- 将 field 合同扩展为完整 gate evaluator 会越过 v4.1 的边界，且与 v4.0 F-002 的后续任务重叠。
- 将本仓 `CRUISE_MAX_ITERATIONS=20` 改回默认 5 会静默改变项目策略；应把它显式表达为项目覆盖而非删除。

### Initial Acceptance Hints
- 新增或更新的合同测试能同时检验 mode 字段、E2E Provider、默认值、verdict/reviewer grammar 与关键投影，而不是靠人工全文比对。
- 现有活动 Spec 的 fail-closed 行为、公共 CLI 文案/error code 及历史制品读取保持兼容。
- 根 AI 配置、生成器和 package 不再传播过期的工作流或安全规则。

## Research

### Requirement Review
本任务的核心不是把所有文档替换成同一段文本，而是为影响治理判断的离散事实建立单一、可执行的定义，并让各受众投影从该定义生成或受其测试约束。需要区分「字段存在但只建议填写」与「当前活动制品必须阻塞」；E2E 的 Provider 同时是验收元数据和证据执行选择，缺失时必须保持 fail-closed。v4.1 只能共享这些小而稳定的合同事实，不能趁机重写 gate evaluator 的职责边界。

### Findings

#### F-001 — micro Plan 字段在模板与机器规则中分裂
Evidence: `templates/spec-micro.md:32-41` 列出 `Scope`、`Touched Files`、`Change`、`Impact Scope`、`Data Impact`、`Interface Impact`、`Acceptance`、`Verification`、`Provider`、`Blast Radius`；`src/commands/validate.js:104-109,401-405` 只对其中一部分字段做必填检查。
Assessment: 必须由 mode 合同同时描述字段集合、required/recommended 级别及消费者，而不是在模板、validator 和状态机各自维护数组。既有历史 micro Spec 的读取保持宽松；本次不抽取整个 Plan gate。

#### F-002 — E2E Provider 契约未覆盖全部投影
Evidence: `templates/spec-standard.md:78`、`templates/spec-lite.md:56`、`templates/spec-micro.md:40` 声明 E2E Provider；`src/verification/readiness.js:46-64` 在缺 Provider 时 fail-closed；`src/commands/validate.js:226-253` 与 `src/core/spec-state.js:339-368` 仅要求 `Test` 或 `Manual Evidence`；`SKILL.md:285` 也未说明 Provider。
Assessment: 合同应明确定义 `Verification: e2e` 时 Provider 为必需元数据，并保持 Test/Manual Evidence 的现有兼容语义；所有模板、Skill、validator/state 诊断与 readiness 都应受同一规则或契约测试约束。

#### F-003 — verdict 与 reviewer identity grammar 存在复制
Evidence: `src/commands/challenge.js:7-26`、`src/commands/validate.js:194-201`、`src/core/spec-state.js:305-307` 分别维护 Challenge verdict/reviewer grammar；`src/core/spec-state.js:8-20` 另有 verdict 到 backtrack target 的映射。
Assessment: 应保留既有 verdict、`subagent:`/`external-agent:`/`human:` 身份 grammar、micro `inline` 例外及 CLI 错误语义，同时将枚举、正则/谓词和 target 映射收敛到可复用合同。Challenge 记录命令仍是唯一写入 Challenge Evidence 的路径。

#### F-004 — 默认值与项目覆盖缺少清晰投影
Evidence: `lib/common.js:37-57` 默认 mode 为 `micro`、Cruise 预算回退为 5；`src/commands/init.js:39-43` 写入 `APPROVAL_POLICY=agent` 与预算 5；`.sdd-config:3` 配置本仓预算 20，未解释其项目覆盖意图。
Assessment: 运行时默认值必须仍由核心常量/读取函数权威定义；模板、生成配置和文档只能投影这些默认值。本仓 20 是可保留的显式覆盖，需用配置注释或投影说明避免被误读为新的全局默认值。

#### F-005 — package 与 AI 规则投影滞后
Evidence: `package.json:4` 仍描述 `Research, Innovate, Plan, Execute, Review`；`src/commands/_gen-ai-configs.js:23-37` 已生成 Profile/Archive、独立审核和 Challenge 防伪规则，而根 `AGENTS.md`、`CLAUDE.md` 未包含其中的 Profile/Archive 规则。
Assessment: `package` 描述、根 AI 配置和生成器应由稳定的当前工作流词汇和受控投影测试约束。根 AI 配置必须保留本仓特有内容；不能以覆盖式生成抹掉项目指令。

#### F-006 — 现有测试基础适合覆盖跨投影合同
Evidence: `package.json:24` 使用 `node --test tests/*.test.js`；`tests/commands.test.js:437-459,2345-2428,2649-2730` 已覆盖生成配置、术语及模板 Provider；`tests/state-matrix.test.js:632-660` 覆盖 Provider fail-closed 与 Plan 路由。
Assessment: 可新增聚焦合同的 `node:test` 测试，并保留命令/状态矩阵中的行为回归。测试必须覆盖活动制品的阻断、历史制品的兼容读取与公开错误语义。

### Confirmed Requirement
Scope Boundary: 引入最小可执行治理合同，统一 mode 的字段集合及 required/recommended 级别、E2E Provider 元数据规则、默认值、Challenge verdict/reviewer grammar 和其面向模板、Skill、文档、AI 配置、validator/state/readiness 的投影；以自动化一致性测试防止再次漂移。不得实施 F-002 的完整 gate facts 单一化、结构化 readiness/Console projection、Visual/Verification 基础设施或 fixture 收敛。
Irreversibility: 新合同会影响新建/活动制品的诊断与用户指引，且可能影响公开 CLI 错误文本；必须保持既有 CLI 标签、error codes、Challenge Evidence 写入路径和历史制品读取。通过将历史输入保留为宽松读取、将严格契约限定为活动/新制品并以回归测试保护，可回滚实现而不迁移归档数据。
Impact Radius: 影响 `lib/common.js`、可能新增的核心合同模块、`src/commands/{validate,challenge,init,_gen-ai-configs}.js`、`src/core/spec-state.js`、`src/verification/readiness.js`、三种 Spec 模板、`SKILL.md`、`README.md`、`GUIDE.md`、根 `AGENTS.md`/`CLAUDE.md`、`package.json` 与相关 `tests/*.test.js`；不改变命令表面、Run schema 或安全路径层。
Dependencies & Constraints: Node.js >=18 与内置 `node:test`；现有 Markdown 标签解析、活动/归档制品定位、Provider readiness fail-closed、reviewer evidence anti-forgery、模板/生成器的受众边界；`CRUISE_MAX_ITERATIONS=20` 必须作为本仓覆盖保留，默认预算仍为 5；不执行 Profile/Provider 初始化或依赖安装。
Acceptance Intent: 可观察地证明每一个合同事实在运行时消费者与文字投影中一致：每种 mode 的字段严格度、E2E Provider、默认值、verdict/reviewer grammar 和现行工作流术语都由同一来源或契约测试保护；新活动 Spec 保持 fail-closed，历史制品可读取，现有 CLI 标签/error codes 与 Challenge Evidence 防伪边界不回归。

## Innovate Options

### Option A — 最小运行时 Contract Registry + 投影一致性测试
Option Summary: 新建纯 JavaScript Governance Contract Registry，集中声明 mode 字段及严格度、E2E Provider 规则、默认值、verdict/reviewer grammar 和 verdict→target 映射。运行时消费者直接复用该合同；静态模板、Skill、文档、package 与 AI 配置保留为受众投影，并由专门测试验证其与合同一致。根 AI 配置通过已有 sdd-riper:start/end 受控区块融合，区块外的项目专属指令不被覆盖。
Pros: 将会影响执行语义的事实从复制逻辑中移出；保留现有公共 CLI、Markdown 格式和每类受众的可读表达；合同测试能捕获遗漏的文档/模板/生成器更新；可把 Cruise=20 明确为项目覆盖而非默认值。
Cons: 需要引入小型核心模块，并在多个消费者中替换本地枚举或正则；静态投影仍需维护，只是有测试保护。
Risks: 误把完整 gate logic 移入 Registry 会越过任务边界；根 AI 文件若把受控块和自定义内容混淆，可能重复说明规则。
Requirement Fit: 完整满足单一可执行来源、跨投影测试、历史读取兼容与 fail-closed 保持；可明确限制为合同事实而非 gate evaluator。

### Option B — 仅新增跨投影一致性测试
Option Summary: 不新增核心合同模块，选择现有实现作为基准，并让测试同时断言模板、Skill、文档、生成器、validator、状态机和 readiness 具有一致文本或行为。
Pros: 代码改动最少；能较快发现后续漂移；对现有运行时结构干扰低。
Cons: 测试自身会成为另一份合同定义；challenge/validate/state/readiness 仍继续维护相近的列表、grammar 和映射，新增特性时仍需多处手改。
Risks: 测试通过只代表当前复制品相同，不能保证运行时真正共享事实；在涉及 error code、历史兼容和 fail-closed 的修改中容易漏掉消费者。
Requirement Fit: 只能部分满足“单一来源”，更适合作为 Option A 的安全网，不适合作为最终方案。

### Option C — 由模板或外部声明文件驱动全部运行时与投影
Option Summary: 新建 JSON/YAML 等外部合同文件，从中生成模板、文档、AI 配置，并让运行时在执行时解析该文件。
Pros: 表面上能让所有投影都从一个声明文件生成；非代码读者可以查看合同。
Cons: 为少量稳定规则引入新解析、schema 校验、加载失败和发布同步路径；静态文档需要生成流程和更新纪律；运行时读取外部文件会扩大失败面。
Risks: 外部合同文件损坏或版本不同步可能阻断 CLI；会把本任务扩大为配置/构建系统设计，且难以保持历史读取兼容。
Requirement Fit: 过度设计，不符合“最小治理合同”和限定影响半径的目标。

Selected Option: Option A — 最小运行时 Contract Registry + 投影一致性测试。
Selection Rationale: 它让运行时必须遵守的治理事实具有唯一可执行来源，同时保留静态投影的读者价值和现有 Markdown/CLI 兼容。受控区块只是一种安全更新根 AI 配置的投影机制，而非第二个合同来源；未被标记的项目指令继续由仓库维护。

## 目标摘要
当前阶段为 Plan，且已获用户批准正式 Technical Design。任务承接 v4.0 的 P0「分布式治理契约漂移」，只收敛可执行合同及其受众投影，不处理工作流 gate facts、readiness 投影或 Visual/Verification 基础设施。

## 最终方案
ADR-001 — 采用最小运行时 Governance Contract Registry 加投影一致性测试。Registry 只拥有稳定、离散且会影响治理行为的事实；运行时消费者直接引用，文字投影保留独立可读性但受合同测试约束。拒绝仅靠测试的 Option B，因为它不能消除运行时重复事实；拒绝外部 JSON/YAML 生成系统的 Option C，因为它扩大了解析、发布和兼容风险。

## 关键约束
Node.js >=18 与内置 `node:test`；现有 Markdown 标签解析、活动/归档制品定位、Provider readiness fail-closed、reviewer evidence anti-forgery、模板/生成器的受众边界；`CRUISE_MAX_ITERATIONS=20` 必须作为本仓覆盖保留，默认预算仍为 5；不执行 Profile/Provider 初始化或依赖安装。

## 坑点与风险
- 共享的合同模块会使消费者有共同依赖，但这正是稳定离散事实应有的依赖；通过禁止 Registry 承担解析、路由和 I/O，避免形成新的大一统 evaluator。
