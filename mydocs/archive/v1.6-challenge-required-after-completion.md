## Summary
本任务修正 Completion Verification 后的 Challenge 路由与门禁提示。
目标不是让 CLI 自动执行模型评审，而是让 `resume` / `next` / `validate --archive-ready` 在 Challenge 尚未记录时明确阻止归档，并给出可执行命令。
实现范围限定在 workflow 状态推导、resume 阶段提示、archive-ready 问题文案和相关回归测试。

## Intake

### Requirement
requirement: 在 standard/lite 任务完成 Completion Verification 后，流程必须明确进入并要求记录 Challenge；如果 Challenge 尚未执行，next/resume/archive-ready 必须阻止归档并给出可执行指引，避免 agent 漏掉应触发的对抗评审。

### Constraints
不引入模型执行器；`sdd challenge` 仍只生成 prompt，`sdd challenge --record-result` 仍负责写入证据。standard/lite 必须保留 subagent Challenge 约束。兼容已有验证逻辑和旧 Spec。

### Scope
包含 `resume` 阶段判断、`next` 动作推导、`validate --archive-ready` 缺失 Challenge 证据时的错误文案，以及命令测试。

### Risks
如果只改文案不改路由，agent 仍可能漏跑 Challenge；如果把缺失 Challenge 误分类为 `FAIL_CODE`，会把流程错误导回 Execute / Debug。

### Initial Acceptance Hints
当 Plan 已批准、Execute Log 已有 completion-verification、但 Challenge fields 为空时，`resume` 应提示 `PHASE_HINT: challenge`；`next` 应提示 `NEXT_ACTION: run_challenge`；`validate --archive-ready` 应失败并给出 `sdd challenge` 与 `--record-result` 的可执行指引。

## Research

### Requirement Review
用户指出：如果某个任务按流程应该触发 Challenge，就需要保障它被触发，否则 Challenge 作为质量门禁失去意义。本需求关注的是“流程不会漏掉”，不是让 CLI 自己调用大模型。

### Findings
现有 `validate --archive-ready` 已会因为 `Challenge Executed By is empty.` 等问题阻止归档，但错误文案不够可执行。`workflow.classifyIssue` 把 Challenge evidence 缺失归类为 `FAIL_CODE`，导致 `next` 输出 `repair_execute_debug`，这与“应先跑 Challenge”不一致。`resume` 只根据 Completion Verification 是否为空把阶段提示为 `archive`，没有单独提示 `challenge`。

### Open Questions
无。用户已要求按该方向修改，版本为 `v1.6`，任务名授权推荐，context 为 `none`。

### Assumptions
Challenge 的“自动触发”在当前 CLI 语义中定义为自动路由和强门禁提示，而不是自动执行模型；真正的独立评审仍由宿主 agent 派发 subagent 后通过 `sdd challenge --record-result` 记录。

### Confirmed Requirement
当 standard/lite 任务已经完成 Plan approval 与 Completion Verification，但尚未记录 Challenge evidence 时，SDD 必须把下一步明确路由为 Challenge，并在归档校验中提供可执行指引。缺失 Challenge 不应被误导为 Execute / Debug 问题；归档仍必须被阻止，直到 `sdd challenge` 与 `sdd challenge --record-result` 完成。

## Innovate Options
Option A: 在现有 validation / workflow / resume 上增加显式 Challenge-required 状态。
Pros: 改动小；保留现有命令模型；能直接修正漏触发路径；测试容易覆盖。Cons: 不会自动运行模型，需要 agent/用户按指引执行。Risks: 需要保证归档门禁文案和 next/resume 状态一致。Requirement Fit: 高。

Option B: 让 `sdd next` 自动调用 `sdd challenge` 并记录结果。
Pros: 看起来更自动。Cons: 当前 CLI 没有模型执行器，无法真实独立评审；自动写 evidence 会破坏“不能手填 Challenge Evidence”的门禁语义。Risks: 伪造质量门禁。Requirement Fit: 低。

Option C: 仅修改文档，要求 agent 记得 Challenge。
Pros: 无代码风险。Cons: 已经发生漏触发，说明文档不足以保证流程。Requirement Fit: 低。

Selected: Option A。用状态路由和归档门禁保障 Challenge 被显式执行，同时不伪造模型评审。

## Plan
1. 在测试中构造 standard spec：已批准 Plan、已填 Design/Acceptance、Execute Log 含 completion-verification，但 Challenge fields 为空；断言 `resume` 输出 `PHASE_HINT: challenge`。
2. 在同一类夹具上断言 `next` 输出 `NEXT_ACTION: run_challenge`，并包含可执行 Challenge 指引。
3. 在 archive-ready 校验上断言缺失 Challenge 时输出包含 `sdd challenge` 和 `--record-result` 的问题文案。
4. 修改 `validateChallengeEvidence` 的缺失字段问题文案，集中表达“Challenge not executed”与记录命令。
5. 修改 workflow 状态推导：当 validation issues 表明 Challenge 未执行时，`nextAction` 为 `run_challenge`，`backtrackTarget` 为 `Challenge`，不再归类为 Execute / Debug。
6. 修改 `resume`：当 Plan 已批准、Completion Verification 已存在但 Challenge Executed By / Evidence 为空时，输出 `PHASE_HINT: challenge` 与对应 sections hint。
7. 覆盖 stale Challenge evidence：当 Execute Log 最新 Timestamp 晚于 Challenge Executed At 时，`resume`/`next`/`validate --archive-ready` 必须要求重新 Challenge，而不是继续信任旧 verdict。
8. 覆盖 partial Challenge evidence：当 verdict 存在但 Executed By / Executed At / Evidence 三字段不完整时，仍必须路由到 Challenge 并给出 `--record-result` 指引。
9. 运行 `node --test tests\commands.test.js` 和 `node --test tests\*.test.js`，把 RED/GREEN 与 AC Coverage 写入 Execute Log。

10. 修正 completion-verification 解析与测试夹具：解析执行日志前必须剔除 HTML 注释，旧夹具必须写入真实 completion-verification DONE，不能依赖模板注释或普通 `Step 1: DONE`。
