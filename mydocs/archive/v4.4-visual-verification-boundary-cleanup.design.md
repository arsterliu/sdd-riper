## Technical Design

Selected Option / ADR: ADR-001 选择“纯 Contract Inspection + 兼容组合投影”。先将 Visual Contract 的治理合法性从运行时 Visual Run 状态中分离，再由薄组合层按当前优先级生成既有调用方需要的状态/诊断。用户已确认把原 v4.0 第四项路线拆成两个独立阶段；本期不处理 Playwright 协议、Reporter 或存证事务的公共内核。

Requirement Traceability: v4.0 F-006 要求将合同合法/人工批准与最近 Run 的 PASS/FAIL/STALE 分离；F-007 只允许后续合并完全相同的协议/事务骨架；F-008 禁止把共享路径原语扩大为跨领域信任策略。AC-001 覆盖正交事实的纯 inspection，AC-002 覆盖兼容投影，AC-003 保护两类 Run 隔离，AC-004 保护 fail-closed 信任边界。

Impact Scope: 主要修改 `src/visual-evidence/contract.js` 与消费其结果的 Visual 状态组合位置；可能涉及 `src/commands/visual.js`、`src/commands/verify.js`、`src/verification/readiness.js`、`src/verification/evidence.js` 和对应测试。`src/verification/run-store.js`、`src/visual-verification/run-store.js`、Playwright adapters、attachment store、公共 CLI 注册和 Web 展示只作兼容回归对象，本期不重构其实现。

Context / Boundary: Visual Contract 是治理输入：是否启用、mode、source、场景、人工批准、baseline 与项目内路径。Visual Run 是时态证据：Provider/Workspace 可用性、code-state、执行、像素比对、Run freshness 和结果。两者不能互为权威。组合层是内部适配器，不是新的公共 API 或跨请求缓存。

Domain Model: `VisualContractInspection` 仅包含合同状态、受控的稳定诊断 code 和必要的资格标记；它不包含 Provider 配置、Run 内容、绝对路径、命令、环境或审批原文。`VisualRunStatus` 继续由现有视觉运行链路生成，保留既有 PASS/FAIL/BLOCKED/STALE 等语义。`VisualReadinessProjection` 只组合上述受控结果，面向既有 CLI、readiness 和 Console 消费者。

Architecture View: `Spec + visual-evidence manifest → VisualContractInspection → Compatibility Composer ← VisualRunStatus ← Provider/workspace/code-state/Visual Run`；Composer 输出给 `visual inspect`、`verify visual`、Verification readiness 与 Console。普通 `verify run → Verification Run store` 保持独立，不流入 Visual Contract inspection；Visual `scenario/pixel → Visual Run store` 保持独立，不改写普通 Verification Run。

Data Model / Schema: 不新增或修改公开 schema。普通 Verification Run 保持其 AC×project/测试模型及 `mydocs/runs/verification/`；Visual Run 保持 scenario/pixel 模型及 `mydocs/runs/visual/`。新的内部 inspection/projection 是短生命周期内存值，以私有字段或受控模块接口传递；仅暴露已有安全投影所需的枚举和诊断 code。

Data Migration / Backfill: 不迁移、回填、改写或重新解释历史 Visual/Verification Run。新逻辑必须能读取现有合法制品；若历史制品缺少当前所需的证据，则按既有 fail-closed 状态投影，不猜测通过。

Interface Contract: 保持 `visual inspect` 的既有四字段输出与诊断、`verify visual` 的 fidelity-only 执行规则、direction/未启用不写 Visual Run、普通 `verify run` 的独立行为以及已有 Console/readiness 投影。内部新增纯 inspection 与 composer 的最小模块接口；不新增 CLI 参数、HTTP 字段、Provider capability、schemaVersion 或公开配置文件。

API Protocol: 不引入网络 API、浏览器控制入口、Figma 集成、任意 URL、任意命令或环境变量输入。Visual adapter 仍仅使用已注册 capability、项目内静态 scenario mapping 和受控 workspace。

State / Concurrency: inspection 与组合均为请求/调用范围内的纯计算，不缓存跨请求的合同、Run、Provider 或 freshness 结果。Run 写入继续由既有视觉存储路径负责；本期不改变原子提交、锁或 staging 生命周期。

Failure Modes: 合同字段/批准/baseline/source/路径不合法时，inspection 返回稳定 fail-closed code；Provider 或 workspace 不可用、Run 缺失/失败/过期时由 RunStatus 返回既有状态，composer 不将其伪装为合同合法或执行成功。异常不得泄露原始路径、命令、环境、Provider 配置或审批文本。

Security / Permission: 保持 Provider allowlist、fidelity 静态 mapping、项目边界、lexical/realpath containment、baseline 人工批准和受控附件策略。禁止以共享模块为由放宽 root、目标文件、realpath 时机、错误码或信任根；普通 Verification 与 Visual 的 schema、namespace、领域结果模型必须独立。

Observability: 使用已有稳定诊断 code 和安全状态投影；增加内部单元/集成测试以证明 inspection 不访问运行时依赖、composer 保持分支优先级、两类 Run 不相互读取或写入。不得增加对外调试信息或敏感原始值。

Performance / Capacity: 纯 inspection 只读取合同和受控路径信息；组合层复用调用范围内已取得的受控状态，避免无意义的重复检查，但不以跨请求缓存交换 freshness 正确性。复杂度保持与合同场景数和当前 Run 查询规模线性相关。

Compatibility / Rollback: 采用薄组合层保持外部行为；如发现回归，可停止将消费方接入新 inspection/composer 并恢复原组合路径，无需迁移数据。不得改变 CLI、诊断 code、Run schema、目录、历史制品读取、Visual baseline 或普通 Verification 行为。

Test Strategy: 先为当前 `visual inspect`、`verify visual`、readiness 与 Console 输出建立行为快照；再以 TDD 为纯 inspection 写合同字段/批准/baseline/source/realpath 的红灯测试；以集成测试覆盖缺失、FAIL、STALE、PASS Run 的兼容组合，direction/未启用不写 Run，以及普通/Visual Run 隔离。最后运行 Visual、Verification、Console 相关测试、全量 `npm.cmd test` 和 `git diff --check`；浏览器环境不可用时保留可审计 BLOCKED，不伪造 PASS。

Risks / Trade-offs: 组合层短期保留适配复杂度，但避免一次跨越协议/事务/存储的高风险重构。最大的风险是误改现有诊断优先级或把运行异常混入合同缺陷；通过先冻结快照、限制内部接口与独立 Challenge 控制。后续第二阶段仅在 v4.4 已验证边界后，另行创建 Spec 处理精确重复的 Playwright 与不可变存证骨架。
