## Technical Design

Selected Option / ADR: ADR-001 选择“分阶段抽取精确同构基础设施”。第一步只提取 process-result evaluator 与 Reporter 生命周期工厂，第二步才提取 immutable Run commit transaction。每条链路保留薄 adapter/Run-store wrapper，继续独占领域建模、静态配置和安全决策。该选择来自用户确认的 Option A。

Requirement Traceability: v4.0 F-007 允许且只允许合并完全相同的协议和事务骨架；F-008 要求共享原语不得扩大为跨领域信任策略。v4.3 冻结 Provider/Registry/Run-store 错误语义和无跨请求 freshness 缓存，v4.4 冻结合同/运行态边界及双 Run 隔离。AC-001 覆盖结果协议等价，AC-002 覆盖 Reporter 边界，AC-003 覆盖原子事务与双 namespace，AC-004 覆盖高层编排兼容，AC-005 覆盖失败关闭与信任根。

Impact Scope: 预计涉及 `src/verification/adapters/playwright-test/`、`src/verification/adapters/playwright-visual/`、`src/verification/run-store.js`、`src/visual-verification/run-store.js`，以及对应测试。`src/commands/verify.js`、Registry、readiness、Console、Visual config、attachment-store、process-gateway 只作为兼容回归对象；本期不重构其高层逻辑。

Context / Boundary: 普通 Verification 是 AC×project、受控 allowEnv、测试标签与 E2E Run 的领域；Visual 是静态 scenario、PNG、pixel diff、baseline 与 Visual Run 的领域。两者只在受控 Playwright 终态、Reporter 生命周期和 immutable commit 顺序上同构。共享代码是模块私有基础设施，不是新的领域模型、配置、CLI、网络 API 或跨请求缓存。

Domain Model: `ProcessOutcome` 仅表示现有 process/Reporter terminal 事实与既有结果对象；`ReporterLifecycle` 仅表示 nonce 校验和 hello→test*→end 事件顺序；`ImmutableCommit` 仅表示已验证 Run 的 staging-to-rename 存证步骤。AC tags、environment digest、design/diff-base、scenario/pixel、baseline、Visual attachments 和 domain diagnostics 不进入这些通用模型。

Architecture View: `verify run → playwright-test wrapper → shared evaluator / Reporter factory → test normalizer → verification Run wrapper → shared transaction → mydocs/runs/verification/`。`verify visual → playwright-visual wrapper → shared evaluator / Reporter factory → visual normalizer + pixel/baseline → visual Run wrapper → shared transaction → mydocs/runs/visual/`。两条路径继续通过既有 `process-gateway`（shell:false、受控调用）与 `attachment-store`（realpath、限额、hash、copy）；它们不相互流入。

Data Model / Schema: 不新增或修改公开 schema。普通 Run 保持 AC/test execution、environment digest、design/diff-base 等 root fields；Visual Run 保持 scenario/pixel、threshold、baseline/current digest 等 root fields。两 wrapper 在调用事务前先调用自己现有的 validator；共享事务只处理已验证对象和 wrapper 固定的内部常量。Reader、排序与历史制品解释不变。

Data Migration / Backfill: 不迁移、不回填、不重写、不重新解释历史 Run。共享 helper 对新调用保持与旧写入路径相同的最终目录和 `run.json` 格式；已有存档继续由原 reader 读取。

Interface Contract: 既有两个 result-contract 模块路径继续导出原 API，内部委托同一 evaluator。既有 Reporter 文件和 adapter manifest/capability 保留；factory 只接收 wrapper 固定的 capability 与 payload mapper。两个 commit 函数继续公开原函数名、参数和错误码；内部 transaction 不导出为 CLI/配置接口，namespace、collision code、validator 和 reader 由 wrapper 固定。

API Protocol: 不新增 HTTP、CLI 选项、Provider capability、schemaVersion、URL、任意命令、selector 或环境输入。普通 adapter 继续在已授权 allowEnv 内工作；Visual adapter 继续传递空环境并仅使用静态 scenario binding。握手 nonce、Reporter version/capability 与输出文件约束的既有失败关闭顺序不变。

State / Concurrency: 每次执行保留现有一次性 nonce 和局部 staging 生命周期。commit 顺序固定为领域验证、workspace lexical/realpath containment、静态 namespace、初次 collision、staging 创建、附件复制、`run.json` 的 `wx` 写入、二次 collision、rename；异常清理 staging。不得增加模块级 mutable state 或跨请求缓存。

Failure Modes: evaluator 必须保持 timeout、signal、缺 end、interrupted、failed、非零退出、PASS 的旧优先级；Reporter 任何 nonce/version/capability/顺序异常均不得保留 PASS。transaction 在 validator、workspace、attachment、写入或 rename 失败时保留原领域错误码并清理 staging；畸形 Run 不得创建最终目录。共享 helper 不能把任一域的异常翻译为另一个域的成功、错误码或 Run 状态。

Security / Permission: 共享层不接收外部可控 root、namespace、target file、URL、selector、命令或环境。domain wrapper 保留 manifest/allowlist、静态 mapping、capability、allowEnv、baseline approval、lexical/realpath containment、attachment policy 和错误工厂。事务 helper 只在 validator 与 realpath 检查后运行，且 namespace 由 wrapper 内部常量提供；这防止共享层成为路径逃逸或任意执行入口。

Observability: 保持现有 JSONL Reporter 事件、稳定诊断 code、Run 目录、错误码和 CLI 输出。新增 parity/lifecycle/transaction 测试只断言稳定事实，不输出命令、环境原文、绝对路径或原始审批信息。Execute Log 记录 Windows LF 归一化预加载仅用于测试进程的前置条件。

Performance / Capacity: evaluator 与 Reporter factory 降低两套重复条件判断而不改变事件数量。transaction 继续只复制由 domain wrapper 允许的附件，保持现有限额和原子写入；不引入额外全量扫描、缓存或后台任务。

Compatibility / Rollback: 两个 wrapper、schema、directory、reader、CLI 与错误码不变，因此可通过撤回 wrapper 对共享 helper 的内部接线恢复原实现，无需数据迁移。若 parity 或真实 Playwright 回归出现语义变化，应先撤回当前阶段 helper 接线，而非改写历史 Run 或放宽 fail-closed。

Test Strategy: 首先为两个 result contract 编写表驱动 parity 测试，覆盖 timeout、signal、缺 end、interrupted、failed、非零退出和 PASS 的精确返回对象及顺序。其次测试 Reporter wrapper 的 hello 首位、nonce/version/capability、普通 tags、Visual 无 tags 与官方附件元数据。然后测试两个 Run-store 的畸形输入无目录、静态 namespace/冲突码、workspace/attachment realpath、staging 清理和 content-addressed 附件。最后回归 `verify run`、`verify visual`、Visual/Verification Run 隔离、现有 CLI 和真实 Playwright 证据；在当前 Windows 环境全量测试要显式使用仅测试进程内的 CRLF→LF 预加载。

Risks / Trade-offs: Option A 短期保留薄 wrapper 和两次接线，但避免一次性抽取三种骨架导致的跨域耦合。最大风险是“看似通用”的参数把动态 namespace/路径或 payload 语义带入共享层；通过私有接口、wrapper 固定常量、先验证后提交和双域回归限制该风险。本期刻意不消除 normalizer 或高层编排重复，以换取安全与回滚边界。
