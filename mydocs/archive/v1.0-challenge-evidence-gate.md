## Summary

当前阶段：Research。目标：为 Challenge 对抗评审增加执行证据门禁，防止实现者跳过 Challenge 直接写 PASS。关键约束：门禁模式与 Plan Approval 对齐（manual/auto/advisory），validate --archive-ready 强制校验证据三要素。

## Intake

### Requirement
Challenge 对抗评审没有执行证据门禁——实现者可以直接写 `Challenge Verdict: PASS` 而不实际执行 Challenge，validate 不会拦截。

### Constraints
- 门禁模式与 Plan Approval 对齐（manual/auto/advisory）
- standard/lite 模式下 `Challenge Executed By` 必须是 `subagent`
- micro 模式下可以是 `inline`
- 不改变 Challenge 的裁决逻辑，只增加执行证据校验

### Scope
- `src/commands/validate.js`：新增 `validateChallengeEvidence()` 函数
- `templates/spec-standard.md`、`spec-lite.md`、`spec-micro.md`：新增 Challenge 证据字段
- `SKILL.md`/`GUIDE.md`：更新 Challenge 门禁说明
- `tests/commands.test.js`：新增门禁测试

### Risks
- 现有已归档 spec 没有 Challenge 证据字段 → 归档 spec 不受影响（validate 只检查 active spec）
- 现有 active spec 缺少证据字段 → validate 会报新 issue，需要补充

### Initial Acceptance Hints
- validate --archive-ready 检查 Challenge Executed By / At / Evidence 三要素
- auto 模式下 AI 可填写但三要素必须齐全
- manual 模式下 Challenge Executed By 必须由人工填写
- standard/lite 必须是 subagent，micro 可以是 inline

## Research

### Requirement Review
1. **歧义**：Challenge 证据门禁是否应该复用 GATE_POLICY 配置，还是单独配置？
2. **隐含假设**：假设 GATE_POLICY 配置同时控制 Plan 门禁和 Challenge 门禁
3. **风险**：现有 active spec 缺少 Challenge 证据字段，validate 会新增 issue

### Findings
1. `validate.js` 中 `validatePlanGate()` 已实现 Plan 门禁三要素校验（Approved By / Approved At / Gate Evidence），是 Challenge 证据门禁的参考实现
2. `validateChallengeVerdict()` 目前只检查 FAIL_* verdict，不检查执行证据
3. spec 模板中 Review Verdict 区域已有 Challenge Verdict / Backtrack Target / Challenge Summary 三个字段，缺少 Challenge Executed By / At / Evidence
4. GATE_POLICY 配置（manual/auto/advisory）在 `.sdd-config` 中设置，被 Plan 门禁和 workflow 共用

### Open Questions
1. Challenge 门禁是否复用 GATE_POLICY？
   - 建议：是的，复用。一个 spec 的门禁策略应该统一，不需要 Plan 用 auto 而 Challenge 用 manual

### Assumptions
1. GATE_POLICY 同时控制 Plan 门禁和 Challenge 证据门禁
2. 归档 spec 不受新门禁影响（validate 只检查 active spec 的 archiveReady）

### Confirmed Requirement
1. Spec 模板新增 `Challenge Executed By:`、`Challenge Executed At:`、`Challenge Evidence:` 三个字段
2. `validate --archive-ready` 新增 `validateChallengeEvidence()` 校验三要素
3. auto 模式：AI 可填写，三要素齐全即通过
4. manual 模式：`Challenge Executed By` 不能是 `auto-gate`，必须由人工填写
5. standard/lite：`Challenge Executed By` 必须包含 `subagent`（不能是 `inline`）
6. micro：可以是 `inline`
7. advisory 模式：与 auto 行为一致，Review 阶段额外提示人工确认

## Innovate Options

### Option A：独立 CHALLENGE_GATE_POLICY 配置
新增独立的 Challenge 门禁策略配置，与 GATE_POLICY 分离。

- 优点：灵活，Plan 和 Challenge 可以用不同策略
- 缺点：配置复杂度增加，用户需要理解两个门禁策略
- 匹配度：低——过度设计

### Option B：复用 GATE_POLICY（推荐）
Challenge 证据门禁复用 GATE_POLICY 配置，与 Plan 门禁策略一致。

- 优点：配置简单，一个策略控制所有门禁；用户心智模型统一
- 缺点：不能单独调整 Challenge 门禁策略
- 匹配度：高——一个 spec 的门禁策略应该统一

### Rejected Options
- Option A：过度设计，增加用户认知负担

### Selected Option
**Option B：复用 GATE_POLICY**
