## Summary
当前处于 Research 阶段，尚未进入设计或实现。
任务以 Console 为 v3.4 Project Profile 与 v3.5 Quality Plan 的内部 dogfood 载体，并同步改善信息架构与布局。
Profile、Quality Plan 与 Verification 均为只读派生数据；Acceptance Criteria 仍是唯一验收真相，Console 不得形成第二套工作流。
已确认既有 Console 有 Provider / Run / 矩阵投影，但尚未暴露 Profile 与 Quality Plan，且右侧详情以长纵向堆叠呈现。

## Intake

### Requirement
requirement: 将 SDD Console 增强为 v3.4 Project Profile 与 v3.5 Quality Plan 的可视化 dogfood 场景：以只读派生视图展示当前项目画像、质量策略解释与验收状态，同时优化 Console 信息架构与布局；Console 自身以已配置的 Playwright E2E Provider 验证。
goal: 验证 v3.4 Profile 与 v3.5 Quality Plan 在 Console 中可被准确、可理解地消费，并提升 Console 的任务状态、质量决策和验证证据可读性。

### Constraints
constraints: 保持 AC 为唯一验收真相；Quality Plan 与 Profile 仅为只读派生物；不创建第二套工作流；不破坏既有 Verification 视图；遵循 v3.0 Provider/Adapter 边界；布局优化需兼顾窄屏。

### Scope
包含：Console 后端对已确认 Profile、选中 Spec 的 Quality Plan 与既有 Verification 证据的安全只读投影；Console 前端的项目概览、任务详情信息架构、响应式布局和相应自动化测试。
不包含：改变 Profile 确认语义、Quality Plan 策略规则、AC 格式、Provider / Adapter 契约，或为 Console 新增可写工作流。

### Risks
Quality Plan 可能因 Profile 缺失、Spec 输入不完整或 E2E readiness 不可读取而处于阻塞状态；Console 必须展示可理解的诊断，不能把阻塞状态误报为通过。
Profile、Quality Plan 与 Verification 的数据可能包含路径或诊断内容；投影必须沿用既有脱敏与项目边界原则，不能泄漏本地敏感信息。
当前三栏加长详情布局在常见笔记本宽度下会压缩阅读区；布局调整不能破坏现有窄屏无横向溢出和局部滚动承诺。
`status` 当前仅表示生命周期 `draft | archived`，而非工作推进状态；若直接以校验问题数量标记“阻塞”，会把尚未到达的后续门禁错误呈现为故障。

### Initial Acceptance Hints
主视区优先让用户一眼识别 Spec 总量，以及每个 Spec 的当前阶段与状态；项目质量与验证详情应服务于选中 Spec 的进一步判断。
态势板须并列呈现 Lifecycle、Current Phase 与只读派生的 Work State；仅 Challenge 回退或明确等待授权可被标记为需要动作，不能把普通未完成阶段或未来门禁称为阻塞。
用户能在不离开 Console 的情况下识别当前项目 Profile 状态、选中任务的 Quality Plan 状态、策略原因、AC 映射与 E2E readiness。
当 Profile 或 Quality Plan 不可用、缺失或阻塞时，用户能看到原因与恢复动作，且不会把派生建议误解为新的验收门禁。
Quality Plan 只对选中的活动 Spec 投影；归档 Spec 明确显示不生成当前策略投影，不以 current Profile 回退计算历史结果。
现有 Verification Provider、Run、freshness 与矩阵信息保持可见、可读和安全脱敏；窄屏不产生页面横向溢出。

## Research

### Requirement Review
现有 Console 已通过 `/api/specs/:id` 为选中 Spec 附加 Verification projection，但项目级 `/api/project` 与前端均未消费 Profile 或 Quality Plan。
`profile show` 读取已确认的项目画像；`quality plan` 基于选中 Spec、已确认 Profile 和既有 E2E readiness 生成只读派生计划，并会以结构化 diagnostics 表达阻塞或关注项。
因此本任务需要增加受项目边界约束的只读投影，而不是让前端复制策略规则或调用任意命令。

### Findings
现有页面由项目轨（340px）、Spec 清单（工作区的 38%）与详情区组成。详情区把状态、Verification、阶段、制品、方法、AC、Cruise、归档校验顺序纵向堆叠，关键信息需要较长滚动才能比较。
既有 Verification 区已经具备 Provider readiness、Run history、AC × project matrix、附件诊断与窄屏局部横向滚动，必须保留且避免重复建设。
质量计划的稳定投影边界包括 source、AC facts、policy focus、AC mappings、E2E readiness、diagnostics 与 blocking；项目画像的稳定边界包括确认状态、revision、digest、units 和 relations。
当前项目尚未有已确认的当前 Profile；这恰好是 dogfood 所需的“Profile 缺失 / Quality Plan 阻塞”状态，Console 需要能诚实呈现它。
独立审核第 1 轮确认方案 A 与既有架构一致，但要求收束“状态”语义：Lifecycle 为 `Draft / Archived`，Current Phase 为工作流阶段，Work State 才是 `In progress / Awaiting plan approval / Awaiting archive authorization / Needs repair / Archived` 等面向用户的只读摘要。普通 Research、Design 等尚未完成的后续门禁不得汇总为“Blocked Gates”。
`quality plan` 仅使用 Spec 前置数据中精确绑定的不可变 Profile revision，不能回退到项目 current Profile；它的命令包装层会写入进程退出状态，Console 不应直接调用该 CLI 包装层。
既有 Verification Console projection 已对路径和诊断做脱敏；Profile 与 Quality Plan 新投影也必须只返回白名单字段及稳定诊断，不能直接透传 evidence、manifest、command reference、确认说明、原始异常或 diagnostics details。
独立审核最终确认：三层状态语义、项目级 Profile current pointer 与活动 Spec Quality Plan exact revision 的边界、归档 Spec 的不投影边界、纯读取服务和脱敏约束均已充分收束；方案 A 可进入 Innovate。

### Open Questions
无阻塞性开放问题。Profile 与 Quality Plan 采用“摘要优先、选中 Spec 详情内按需展开”的渐进展示，具体字段与交互由 Technical Design 固化。

### Assumptions
布局优先级已由用户确认：先显示 Spec 总量，以及每个 Spec 的阶段和状态；Quality Plan、Profile 与 Verification 作为选中 Spec 的决策详情。
用户已选择方案 A：采用“项目摘要 → Spec 态势板 → 选中 Spec 决策详情”的信息层级；不采用按阶段看板或仅强化现有窄列表的方案。
项目级 Profile 摘要针对当前选择的项目读取 current pointer，以只读方式报告 `confirmed / missing / invalid` 状态；选中活动 Spec 的 Quality Plan 则从其精确绑定的 revision 计算。两类数据均从 Core 模块直接读取并经专用投影输出；浏览器端不执行 CLI 命令，也不解释或改写策略。
质量计划的 blocking、attention 与 E2E readiness 是说明性状态，不改变既有 Spec 阶段门禁或 Archive 授权语义。
Quality Plan 仅针对选中的活动 Spec；归档 Spec 返回明确的“当前策略不适用”只读状态。Profile 投影只展示确认状态、revision/digest、单元数量及经白名单过滤的单元摘要。
Work State 由已有 lifecycle、workflow phase、Plan / Archive 授权事实与 Challenge 回退事实派生，不增加状态持久化、不改变 `workflow.phase`，也不把未来门禁校验问题映射为“Needs repair”。

## Innovate Options
### Option A: Spec 态势板优先，详情按需展开（selected）

保留项目轨与既有只读 Console 路由，将工作区重组为“项目摘要 → 宽幅 Spec 态势板 → 选中 Spec 决策详情”。态势板使用现有 Spec index 事实，但显式区分 Lifecycle、Current Phase 与 Work State；Profile 摘要进入项目级上下文，Quality Plan 与 Verification 仅在选中任务详情显示。

优点：直接满足用户“总量、每个 Spec 的阶段和状态”的首屏需求；复用既有索引、筛选、详情和 E2E fixture；不会引入第二工作流。代价：需要重做前端主布局，并为浏览器新增稳定的只读投影契约。

### Option B: 按阶段 Kanban 分组

把 Spec 卡片按 Research、Design、Execute 等阶段分栏展示，并在卡片中保留状态标记。

优点：工作流推进感较强。缺点：多阶段和多 Spec 时横向空间与可比性变差，窄屏必须频繁切换；Lifecycle 与 Work State 仍容易被压缩成单一颜色，不能优先满足“全部 Spec 一览”。不采用。

### Option C: 保留现有三栏，仅增强窄列表卡片

维持项目轨 / 38% Spec 列表 / 详情区比例，仅在现有卡片增加状态徽标和质量摘要。

优点：改动最小。缺点：Spec 总量、阶段分布和横向比较仍退居次要区域，详情继续主导首屏，不符合已确认的视觉优先级。不采用。

Decision: 用户已确认 Option A。它把已有事实提升为主视图，而不是另建状态机；新 Work State 仅是已有 workflow 事实的受控、只读摘要。

## 目标摘要

## 最终方案
ADR-CQP-001：采用“Spec 态势板优先 + 选中任务渐进详情”的 Console 重组方案。现有 `spec-index` / `project-indexer` 继续是 Spec 生命周期和工作流事实来源；Console 在 HTTP 边界复制这些事实并派生受限 Work State，而不修改缓存或 workflow。项目级 Profile 摘要从 current pointer 读取，Quality Plan 仅在选中活动 Spec 的详情中由既有纯读取链路计算；归档 Spec 返回固定 not-applicable 状态。

## 关键约束
复用 `spec-index` / `project-indexer` 提供的 Spec 事实，Profile store 的 current pointer / 已确认 revision，Quality 的 `loadQualityInput → readiness.inspect → buildQualityPlan` 纯读取链路，以及 Verification 既有的脱敏模式。Console 后端不得调用 `profile`、`quality`、`verify` CLI 命令，不得复制 Quality Catalog 规则；浏览器不得执行命令。项目级 Profile 摘要仅通过 current pointer 报告 `confirmed / missing / invalid` 状态并输出白名单字段；选中活动 Spec 的 Quality Plan 只能使用该 Spec 精确绑定的不可变 revision，不能以 current Profile 回退或重解释任务。异常和 diagnostics 必须压缩为稳定 code、固定恢复动作和脱敏文本。

## 坑点与风险
方案 A 用更大的态势板换取详情区的首屏空间；用户需要选择任务后再深入 Quality / Verification，但这是已确认的信息优先级。Profile 摘要故意不跑 drift detector，避免把耗时扫描和猜测引入 Console；因此 confirmed 不等同于最新。真实项目当前仍是 Profile missing，只能 dogfood 空态；确认路径由受控 fixture 覆盖，若用户需要真实 current Profile，须走单独授权流程。Quality 视图可能因精确输入或 readiness 不可用而显示 blocking / unavailable，这些永远是说明性诊断，不是新 workflow Gate。
