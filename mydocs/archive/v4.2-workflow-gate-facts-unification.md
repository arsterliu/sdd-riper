## Summary
当前阶段为 Research。v4.2 承接 v4.0 的 F-002/F-005 与 v4.1 的兼容性学习，收敛工作流 gate 的共享事实，而不扩大为投影、Visual、Verification 基础设施或 fixture 重构。
`spec-state` 保持权威的 gate/router；`validate` 保持针对制品的诊断、warning 与 CLI 呈现。Provider readiness 只能在一次 evaluate 内复用，不得跨请求缓存 freshness。
任务不涉及 UI 视觉变更，已确认 `ui-impact=no`。独立只读证据已确认重复位置、归档/历史兼容边界和 fail-closed 约束。

## Intake

### Requirement
requirement: 收敛 spec-state 与 validate 的重复 gate 规则和一次评估中的 Provider readiness 重算；保持 spec-state 为权威路由、validate 为诊断与呈现，保留历史制品兼容和 fail-closed 语义。
goal: 将工作流 gate 事实收敛为可复用、可验证的共享规则，减少语义漂移且不改变既有 CLI 行为。

### Constraints
constraints: 沿用 v4.0 审计；不混入结构化投影、Visual/Verification 基础设施或测试 fixture 重构；保留 CLI 标签、错误码、历史 Spec 读取、Provider allowlist 与 fail-closed 行为。

### Scope

- In Scope: `src/core/spec-state.js`、`src/commands/validate.js` 与它们对 `src/verification/readiness.js`、Governance Contract、Spec snapshot 和既有测试的内部协作边界。
- In Scope: 提取可复用的纯 gate facts/rules、使同次 evaluation 的 Provider readiness 仅计算一次，并保持 evaluator、validator 与 indexer 对活动/归档/历史制品的一致结论。
- Out of Scope: 结构化 Verification/Quality/Console 投影、Web 文本反解析、Visual Contract/Run 拆分、Provider 执行编排、Run Store、path 基础设施、fixture 体系和外部 CLI 协议扩展。

### Risks

- 将 validator 的诊断文案、warning 强度或 exit-code 语义错误地下沉为路由规则，尤其将普通 `validate` 的 advisory/warning 误收紧为 archive-ready blocker，导致既有调用方和测试行为变化。
- 为去重引入跨请求 readiness 缓存，使 Provider 配置、Run freshness 或证据变化后返回过期结论。
- 误把显式 archive 兼容扩展到未标注 location 的历史快照，绕过活动制品的 fail-closed Provider 要求。
- 把静态 Governance Contract 与运行时制品事实混为一个大一统注册表，扩大本任务边界并提高回滚风险。

### Initial Acceptance Hints

- `spec-state`、`validate --archive-ready` 和索引消费者对相同 Spec 输入给出一致的归档 gate 结论；普通 `validate` 保留既有 advisory/warning 语义。
- 每次 `specState.evaluate()` 对 Provider readiness 至多检查一次，且不跨 evaluate 复用 freshness。
- `validate` 保留既有诊断、warning、CLI 标签和 archive-ready 呈现；活动制品仍 fail-closed。
- 显式 archive 可按既有规则放宽 Provider readiness；未标注 location 的历史调用方保持活动路径的关闭失败语义。

## Research

### Requirement Review

本任务要消除的是同一 gate 事实被两套实现分别解释的语义漂移，而不是把所有验证代码集中到一个文件。应优先共享可判定的内部 facts/rules，保留 `spec-state` 的路由权威和 `validate` 的制品级诊断职责。普通 `validate` 可继续以 warning/advisory 暴露不完整字段；只有 `validate --archive-ready` 必须与权威 workflow completion/blocker 结论收敛。v4.1 已将静态治理枚举收敛至 Contract；v4.2 只处理运行时制品状态的收敛，不能借机改变历史制品、Provider allowlist、freshness 或 fail-closed 策略。

### Findings

#### F-001 — Gate Facts 在权威路由与诊断层重复判定

`src/core/spec-state.js:395-475` 集中判定 Research、Design、Acceptance、Provider、Plan、Completion 和 AC Coverage，并为工作流提供 gate/router 结论。`src/commands/validate.js:215-266,314-395` 又对 AC、Plan、Research、Design/Micro Plan 等规则进行独立判断；`validate.js:539-570` 在普通模式保留诊断/warning 强度，`:595-605` 仅在 archive-ready 结尾回收 `specState.evaluate()` 的 blockers。两层职责不同但底层事实重叠，应共享纯内部 facts/rules，而不是改变普通 `validate` 的诊断文本、warning 或命令呈现。

#### F-002 — 同次 Evaluate 重复检查 Provider Readiness

`src/core/spec-state.js:436-450` 为 blocker 检查 Provider readiness，`:568` 生成返回 facts 时再次调用 `readiness.inspect()`。`src/verification/readiness.js:47-94` 对缺 Provider、配置或运行异常、覆盖不足和 freshness 不足均采取 fail-closed。可在一次 evaluation context 内传递同一 inspection；不得跨调用长期缓存，因为配置、Run 和 freshness 都是可变输入。

#### F-003 — 活动、归档与历史快照的兼容边界必须明确

`tests/state-matrix.test.js:162-185,632-694` 证明索引/状态一致性，并约束仅显式 archive 可跳过 Provider readiness；没有 `location` 的旧快照仍按活动路径 fail-closed。v4.1 Learning Record 进一步要求兼容放宽只能由明确状态触发。因此任何共享规则必须保留活动/归档的正向分支，不得由缺少字段反推“非活动”。

#### F-004 — 静态治理 Contract 是可复用模式而非运行时状态容器

`src/core/governance-contract.js` 已集中静态默认值、字段要求和 reviewer/verdict grammar。它可作为最小不可变 Contract 的实现范式；本任务的运行时 gate facts 仍应由 Spec snapshot 和当次 readiness inspection 产生，以避免将静态枚举、时态证据和 CLI 诊断合并为不可审计的单体。

### Open Questions

无阻塞性产品问题。Innovate/Design 需要在不改变公开输出的前提下决定共享 facts/rules 的最小模块边界，以及 `validate` 以何种只读输入消费该结果。

### Assumptions

- 当前 `spec-state` 继续拥有最终 workflow phase、next action 与 challenge target 的路由权威。
- 当前 `validate` 继续拥有面向制品的错误、warning 和 archive-ready 呈现；普通 validate 的 advisory/warning 与 archive-ready 的阻断语义是明确不同的兼容路径，本次不会删改对外 CLI 标签或 error code。
- Provider readiness 只在单次 `evaluate()` 的局部上下文缓存；每次新的 evaluate 必须重新 inspect。
- 仅 `location === archive` 可触发活动 Provider 要求的兼容放宽；缺省 location 视为活动路径。

## Innovate Options

### Option A — Minimal Shared Gate Facts

Option Summary: 新增内部 Gate Facts 收集层，一次从 Spec snapshot 与当前 Provider readiness 生成可复用事实；`spec-state` 负责将事实映射为权威路由，`validate` 按命令模式把同一事实投影为既有诊断或 archive-ready blocker。
Pros: 消除主要重复和同次 readiness 双算；保留现有命令职责、输出兼容与回滚边界；不把时态证据并入静态 Governance Contract。
Cons: 短期会存在一个新的内部数据结构，必须明确其只读、单次调用生命周期。
Risks: 若事实粒度过粗，可能收紧普通 `validate` 的 warning；若缓存越过一次 evaluation，可能返回过期 freshness。
Requirement Fit: 完整覆盖 v4.0 F-002/F-005 与 v4.2 的兼容约束。

### Option B — Only Memoize Provider Readiness

Option Summary: 仅在 `spec-state.evaluate()` 内保存第一次 readiness inspection，其他重复 gate 规则保持原状。
Pros: 变更最小，能解决 F-005。
Cons: 不能解决 `spec-state` 与 `validate` 的重复事实和后续语义漂移。
Risks: 形成局部优化，延续双权威规则。
Requirement Fit: 仅部分满足。

### Option C — Validate Fully Delegates To Spec State

Option Summary: 让 `validate` 完全以 `spec-state` 的 blocker 列表作为唯一输入。
Pros: 去重程度最高。
Cons: 会把普通 `validate` 的制品诊断、warning、文案和 exit-code 语义误变为路由语义。
Risks: 破坏既有 CLI 行为和测试的兼容承诺。
Requirement Fit: 不满足普通/归档验证模式分离的约束。

Selected Option: Option A — Minimal Shared Gate Facts。
Selection Rationale: 用户确认内部重构必须兼容现有输出。Option A 以最小内部事实层收敛重复，同时保留 `spec-state` 与 `validate` 的职责和普通/归档命令模式差异。

## 关键约束
Node.js、现有 Markdown/Snapshot 解析、Governance Contract、Provider allowlist、Run freshness、历史 Spec/Run、既有 CLI 标签和 error code；必须保留 archive 的显式兼容边界、无 location 的 fail-closed 语义、普通 validate 的诊断/warning 强度、archive-ready 的阻断语义和每次 evaluate 的新鲜 inspection。

## 坑点与风险
新增内部模型会增加一层结构，但其职责严格限于事实收集，换取消除双权威和重复 I/O。把更多诊断下沉会降低重复更多，但会破坏普通 validate 的兼容语义，故明确拒绝。
