## Intake

### Requirement
requirement: 修复 SDD-RIPER 控制面一致性审计发现的门禁绕过、状态路由分歧、归档占位符、风险误判、Skill 协议漂移，以及 Cruise、主 Agent、Challenge reviewer 角色边界文档回归。
goal: 让 validate、next、resume、status、archive、console 与 Skill 对同一 Spec 状态给出一致、可收敛且不可绕过的判断。

### Constraints
constraints: 保留现有 Spec 制品模型与 CLI 命令形态；兼容可识别的历史制品但不得让新制品利用兼容分支绕过门禁；Cruise 仅负责编排，主 Agent 回退到目标阶段后按该阶段权限修复。

### Scope
In Scope:
- 统一 `validate`、`workflow`、`resume`、`status`、`archive`、console/spec index 对阶段与归档就绪状态的判定语义。
- 强制 Challenge Verdict、Summary、Evidence、执行身份和时间形成完整且一致的归档门禁。
- 强制新格式 Execute Log 的 completion-verification 四轴与 AC Coverage 闭环，并为可识别的历史日志设计显式兼容边界。
- 修复 `PASS_WITH_CONCERNS` 在 Learning 已完成后无法进入 Ready 的状态收敛问题。
- 修正文档中由 Review 约束机械改名形成的 Cruise 角色边界回归。
- 修复 Archive 通过验证后注入未填写摘要、中文风险否定误判、`status` Challenge 假阳性。
- 防止仓库 Skill 与已安装 Skill 在版本号相同的情况下携带不同控制协议。

Out of Scope:
- 不改变 RIPER 主阶段顺序，不新增 reviewer 身份类型，不接入具体 agent 平台。
- 不把 Cruise 改造成模型执行器，不让 SDD CLI 直接修改业务代码或替代宿主 Agent。
- 不借机重构与控制面判定无关的业务功能、Web UI 样式或通用 Markdown 解析。

### Risks
- 多个命令当前各自复制字段解析和 gate predicate，局部修复可能继续产生跨命令漂移。
- 收紧归档校验可能阻断历史 Spec；若兼容条件不具备可识别标志，新制品仍可伪装成旧格式绕过门禁。
- Challenge freshness、Learning 完成态和 `PASS_WITH_CONCERNS` 的组合状态较多，错误优先级可能造成死循环或提前归档。
- Skill 安装同步涉及工作区源文件、安装目标和生成 AI config，若只校验文本版本号仍无法识别内容漂移。

### Initial Acceptance Hints
- 空白、未知或与 Evidence 不一致的 Challenge Verdict 必须阻止 archive-ready。
- 只有 `Status: DONE`、没有四轴或 AC Coverage 的新 Execute Log 必须被拒绝。
- 同一 Spec 在 `resume`、`next`、`status`、console 和 `validate --archive-ready` 中必须得到相容的阶段与 blocker 解释。
- `PASS_WITH_CONCERNS` 且 Learning 已完成、无其他 blocker 时必须进入 Ready / archive-ready。
- `FAIL_CODE` 应由 Cruise 路由主 Agent 回到 Execute / Debug；Challenge reviewer 本身仍只读。
- 中文“无不可逆变更”“全部可回滚”等否定表达不得触发 `irreversible`。
- archive 产物不得在门禁通过后新增未填写占位符。

## Research

### Requirement Review
用户先要求审计当前 SDD 是否存在明显逻辑矛盾，随后确认本 Spec 应包含此前审计发现的全部问题，而不是只处理 Cruise 文档。讨论进一步澄清：Cruise 的预期模型一直是“编排循环”，真正的修复由主 Agent 在 `BACKTRACK_TARGET` 对应阶段完成，然后重新执行 Completion Verification 与 Challenge；因此 Cruise 本身的运行模型不是缺陷，缺陷是 Review 只读约束在文档合并时被错误改名为 Cruise 约束。

本任务不是添加更多平行 gate，而是收敛现有控制面：一个权威状态评估结果应同时驱动 CLI、console、archive 和宿主 Agent 提示。任何兼容策略都必须区分“可识别的历史制品”和“当前新制品”，不能继续以“零条记录则跳过”的方式默认放行。

### Findings
- **Challenge Verdict 可绕过**：`src/commands/validate.js` 的 `validateChallengeVerdict()` 只拒绝 `FAIL_*`，不要求非空或属于允许枚举；`src/core/workflow.js` 在没有合法显式 verdict 且 validation 无 issue 时推导为 `PASS`。只读内存复现显示空 verdict 与 `MAYBE` 均得到 `validationOk=true`、`archive_ready`。
- **Challenge Summary 可为空**：`src/commands/challenge.js` 使用 `opts.summary || ''` 并写出非空的 `Challenge Evidence: PASS - `；archive-ready 不检查 Summary 非空或 Summary/Evidence/Verdict 一致性。
- **Completion Verification 可为空壳**：`lib/common.js` 的完成态只识别真实 `Step: completion-verification` 后的 `Status: DONE`；`src/commands/validate.js` 在 AC Coverage 为零条时直接跳过 L1-L4。只读内存复现用一个只有 Step、Status、Timestamp 的日志仍得到 archive-ready OK。
- **`resume` 可绕过上游门禁**：`src/commands/resume.js` 只要 Plan Gate 满足，就依据 Execute completion 与 Challenge 字段输出 execute/challenge/archive；不检查 Research、Innovate、Design、Acceptance。只读复现清空 Research reviewer、Design 引用和 Acceptance 后仍输出 `PHASE_HINT: archive`。
- **`PASS_WITH_CONCERNS` 无法收敛**：`src/core/workflow.js::nextAction()` 只有 `PASS` 返回 `archive_ready`。当前 v2.4 的真实命令同时出现 `validate --archive-ready = OK`、`resume = archive`、`next = repair_learning_check`、`BLOCKERS: none`。
- **Cruise 文档角色回归**：Git 历史显示提交 `1373760` 在合并 Review 与 Completion Verification/Challenge 时，把 `Allowed/Forbidden Review writes` 机械改名为 `Allowed/Forbidden Cruise writes`，但保留了 reviewer 的只读限制。`src/commands/cruise.js` 的实际 prompt 一直要求主 Agent 按回退目标修复，因此运行逻辑可工作，错误位于角色边界表述。
- **Archive 在验证后制造占位符**：`src/commands/archive.js` 在 archive-ready 通过后追加四个 `not filled` HTML 占位注释，而 `validate.js` 明确把同一标记视为未解决占位符。仓库中已有 13 个归档 Spec 保留该占位符；`TEAM-GUIDE.md` 所述“归档后编辑再 resume 验证”也无法由没有 active Spec 的 resume 完成。
- **中文风险否定误判**：`workflow.riskFlags()` 使用带 ASCII `\b` 的正则识别中文“无/可逆”，导致 `Irreversibility: 无不可逆数据迁移。变更可回滚。`仍被标为 `irreversible`。当前 v2.4 已真实触发该误报，并使 Cruise 输出人工停止提示。
- **`status` Challenge 假阳性**：`src/commands/status.js` 以 Completion Verification section 是否有文本判断 Challenge；空标签或非法 verdict 也可显示 `Challenge: OK`，与 archive-ready 的证据语义不一致。
- **同版本 Skill 协议漂移**：仓库 `SKILL.md` 与本机安装的 `C:/Users/liuyl/.codex/skills/sdd-riper/SKILL.md` 都声明 `version: 2.0.0`，但前者使用 `APPROVAL_POLICY=agent|human`，后者仍指导 `GATE_POLICY/auto-gate`；当前 validator 又明确拒绝 `auto-gate`。
- **结构性根因**：`labelValue`、Plan Gate、Challenge pass/recorded 等 predicate 分散复制在 `validate.js`、`workflow.js`、`resume.js`、`status.js`、`spec-index.js`、`archive.js`，测试主要覆盖单命令主路径，缺少跨命令状态矩阵。
- **相关 Learning**：v2.2 要求控制面改名覆盖读取、校验、生成、提示、测试、文档和审计入口；v1.6 要求 Challenge 完整性与 freshness 使用统一判定；v2.4 要求枚举同一门禁的 missing/empty/invalid/partial/stale 分支；v2.0 要求模板化 Markdown 风险推导只读取真实填写内容。

### Assumptions
- 当前仓库尚未承诺长期兼容所有无 schema 标识的历史活跃日志；兼容必须通过显式版本、归档位置或可验证结构识别，不能由“缺字段”本身触发。

- Skill 同步问题应由可自动验证的内容身份解决，不能只依赖人工记得运行安装命令。

## Innovate Options
<!-- Compare at least two options. Write the option analysis in Chinese. -->

### Option A: 局部加固并抽取少量共享 helper
Option Summary: 保留 `validate`、`workflow`、`resume`、`status`、`spec-index` 各自的状态推导，只把 Challenge、Plan Gate、completion-verification 等重复 predicate 抽到共享 helper，并逐个修复已知分支。
Pros:
- 改动范围最小，容易按现有测试逐点落地。
- 对 CLI 输出结构和 console 数据模型影响较小。
Cons:
- 各消费者仍然拥有自己的阶段优先级和状态组合逻辑，未来仍会漂移。
- 很难证明 `resume`、`next`、`status`、console、archive 对所有组合状态一致。
Risks:
- 修完当前九类问题后，新的 missing/partial/stale 组合仍可能只在某个命令中被遗漏。
Requirement Fit: 能解决表面缺陷，但不能满足“门禁事实只计算一次并由所有消费者共享”的 Acceptance Intent。
Rejected Rationale: 不解决结构性根因，长期维护成本和再次出现控制面分叉的概率仍高。

### Option B: 统一纯状态评估器 + 薄命令适配层（推荐）
Option Summary: 建立一个无写入、可单元测试的权威状态评估器。它从规范化后的 Spec/Design/Execute Log/Learning 快照计算结构化 gate facts、blocker code、phase、backtrack target、next action 和 archive readiness；`validate`、`resume`、`next`、`status`、archive 与 console/spec-index 仅格式化或聚合该结果。Challenge 记录、Archive 写入和 Skill 安装仍由现有命令负责，但必须消费同一契约。
Pros:
- 直接消除多套 predicate 和阶段优先级，是所有审计问题的共同修复点。
- 可以用状态矩阵一次验证所有消费者，并明确区分事实、路由和展示。
- 保留 Markdown 制品和现有 CLI，不需要引入数据库或新运行时。
- 可将历史兼容限制在明确边界：归档目录只读展示；所有 active Spec/重开任务使用严格新门禁。
Cons:
- 涉及多个核心模块迁移，初始 diff 和回归测试规模较大。
- 需要谨慎定义结构化 blocker code 与现有用户可见文案的兼容关系。
Risks:
- 若一次性替换所有消费者，遗漏旧行为会造成广泛回归；需要按 evaluator → validate/archive → routing → status/console 的顺序迁移。
- Skill 内容身份校验和 Archive 摘要生成不属于纯评估器，需要作为同一设计中的外围一致性组件单独处理。
Requirement Fit: 完整满足单一事实源、不可绕过、可收敛、跨命令一致和可测试兼容边界要求。
Recommendation Rationale: 在不改变制品模型和 CLI 的前提下，能够根治门禁逻辑分叉；复杂度与收益匹配本任务的 standard 模式和跨模块风险。

### Option C: 版本化制品 AST + 显式事件状态机
Option Summary: 为全部 Markdown 制品建立严格 schema/AST 和版本号，把阶段转换表示为显式事件；CLI 只读写事件并由状态机重放得到当前状态，同时提供历史制品迁移器。
Pros:
- 状态转换、兼容和审计语义最严格，长期可扩展性最好。
- 可以从模型层禁止非法转换和伪造的新格式制品。
Cons:
- 需要重做模板解析、写入、迁移、console 数据接口和大量历史兼容逻辑。
- 明显超出当前九类缺陷的必要范围，增加制品迁移与事件一致性的新风险。
Risks:
- 可能把轻量 Markdown 工作流变成复杂的数据库式协议，违背 SDD 当前的低依赖定位。
Requirement Fit: 理论上完全覆盖，但成本和引入的系统复杂度远高于本任务需求。
Rejected Rationale: 过度设计；当前只需一个纯评估器和明确的 active/archived 兼容边界即可获得主要收益。

Selected Option: Option B。用户已确认统一纯状态评估器、薄命令适配层、active 严格门禁、Cruise/主 Agent/Challenge reviewer 角色边界、归档摘要预校验、Skill 内容指纹与状态矩阵测试方向。

### AC-001: Challenge gate rejects invalid or evidence-free verdicts
Requirement: archive-ready 必须要求 Challenge Verdict 属于允许枚举，Summary 非空，Backtrack Target 与 verdict 映射一致，Evidence 与 Verdict/Summary 一致，并满足身份与 freshness 门禁；任何未知或空值不得推导为 PASS。
Type: functional
Verification: integration
Automated: yes
Test: tests/state-matrix.test.js; tests/commands.test.js

Scenario: 非法 Challenge 不能归档
  Given 一个其他归档条件均满足的 active Spec
  When Challenge Verdict 为空、为 `MAYBE`、Summary 为空或 Evidence 与 Verdict 不一致
  Then `validate --archive-ready` 返回 blocker
  And `next` 不得输出 `archive_ready`

Scenario: 合法 Challenge 可以继续路由
  Given Challenge 通过 `sdd challenge --record-result` 写入完整且新鲜的 PASS 或 PASS_WITH_CONCERNS 证据
  When 统一状态评估器计算 Challenge gate
  Then Challenge gate 通过，并根据 Learning 状态进入 Learning Check 或 Ready

### AC-002: active Execute Log requires complete completion and AC evidence
Requirement: active Spec 的 completion-verification 必须包含 DONE、Result、AC Coverage Summary、四轴清单、Verification、有效 Timestamp；只要 Spec 声明 AC，就必须存在覆盖记录，零 Coverage 不得作为兼容分支放行。
Type: functional
Verification: integration
Automated: yes
Test: tests/state-matrix.test.js; tests/commands.test.js

Scenario: 空壳 completion-verification 被拒绝
  Given Execute Log 只有 `Step: completion-verification` 与 `Status: DONE`
  When 运行 archive-ready 校验
  Then Completion gate 返回缺失字段 blocker
  And 每个声明的 AC 都报告缺少执行证据

Scenario: 完整 completion-verification 通过
  Given 四轴、Verification、Timestamp 与所有 AC Coverage 均完整且结果有效
  When 运行统一状态评估
  Then Completion gate 通过并允许进入 Challenge

## 目标摘要
Research Gate 已由独立 reviewer 通过，Option B Technical Design、Acceptance Criteria 与 Plan 已完成并通过 agent Plan Gate，目标是消除 SDD-RIPER 控制面在门禁、阶段路由、归档、风险推导和 Skill 分发上的多源判定与协议漂移。

## 最终方案
采用 Option B：统一纯状态评估器 + 薄命令适配层。拒绝继续在各命令内局部维护 gate predicate，也不引入事件溯源或数据库式状态机。权威状态由规范化 artifact snapshot 一次计算；命令只负责读取、展示或执行已经通过门禁的写操作。

## 关键约束
必须遵守 No Spec No Code、Research/Challenge 独立审查、Plan Approval、Completion Verification、Learning Check 与 Challenge freshness 规则；复用现有 Node.js/Markdown 制品，不引入外部数据库或平台绑定。历史兼容必须可识别且可测试；主 Agent、Cruise orchestrator、Challenge reviewer 的职责边界必须在 Skill、CLI prompt、生成指令和文档中一致。

## 坑点与风险
最大风险是迁移期间新旧状态逻辑并存。缓解方式是先建立状态矩阵和兼容 wrapper，再依次迁移写门禁、路由和展示，最终全文扫描并删除重复 predicate。结构化 blocker code 会增加少量内部模型代码，但换取跨消费者确定性。active 严格校验可能暴露旧日志问题，这是预期修复而非回归；必须通过清晰迁移提示降低使用成本。
