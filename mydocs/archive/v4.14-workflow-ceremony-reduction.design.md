# Technical Design

## Technical Design

Selected Option / ADR:
采用 Spec 的方案 A，在现有合同和单一 Learning 判断中删除普通任务手续。保持数据结构、消费者与专属门禁，不增加配置开关或另一套流程实现。
Requirement Traceability:
- R1 对应创建输入规则与生成配置；R2 对应 micro 模板/Skill 与从模板生成的集成用例。
- R3 对应 SDD 自有派发协议；R4 对应 learningTriggers、既有状态消费者及回归矩阵；R5 对应现行文档与生成规则一致性。
Impact Scope:
产品逻辑仅需 src/core/learning.js 与 src/core/ai-config-rules.js；其他改动集中在 templates/spec-micro.md、SKILL.md、SDD 自有 protocols、README/GUIDE/REFERENCE/TEAM-GUIDE、仓库内四个 Agent 配置和相应测试。归档、授权、Provider、视觉执行逻辑不修改。
Context / Boundary:
原始用户意图与非目标保存在 Spec 引用的 Context；五个 CR 字段、AC、批准及证据仍是控制依据。规则中明确不得把当前代码表现倒写成需求、用项目默认代替用户选择或跨任务复用授权。
Domain Model:
维持现有 Spec、Design、Execute Log、Learning 模型。Learning triggers 只改变普通 BUGFIX/DEVIATED_MINOR 的自动触发结果，不删除真实状态记录；重要触发条件和自主沉淀复用规则的入口保留。
Architecture View:
创建信息：ai-config-rules → SKILL/生成配置/文档指导。
任务结构：micro 模板 → discover → 原有 validate/执行/Challenge/归档摘要。
学习状态：Execute Log + Spec + verdict → learningTriggers → workflow-gate-facts / spec-state / spec-index → 既有 CLI 与控制台投影。
由现有消费者继承集中判断，不给 CLI 或控制台添加另一个豁免分支。
Data Model / Schema:
无 schema 变化。micro 的五个 Plan 验证字段原样保留，Selected Option 单行说明真实方案并用于归档摘要。Scope/Touched Files/Change/Blast Radius 不再默认生成空白字段，用户仍可按需补充，历史字段继续可读。
Data Migration / Backfill:
无迁移。历史 Spec、执行日志与归档均不重写；现有活动任务使用相同函数读取已有记录，普通状态只改变是否自动要求新建 Learning。
Interface Contract:
- 用户已明确提供/确认且仍适用于当前任务的创建输入直接复用；缺失、矛盾或真实歧义继续询问。CLI 必填参数和模式冻结语义不变。
- 五项 micro Plan 验证字段与交付摘要字段 Selected Option 分别解释用途，避免宣称整个任务只有五项信息。
- BUGFIX/DEVIATED_MINOR 无其他重要信号时返回空 Learning triggers；BUGFIX_ESCALATED、DEVIATED_MAJOR、PASS_WITH_CONCERNS、reopened-from 仍触发。FAIL_LEARNING 仍由既有 Challenge 路由阻塞。
- 验收不足、重复失败模式仍按现有指导提炼可复用规则，不因普通状态豁免而忽略。
- 删除非审查分工的固定数量门槛，保留独立 reviewer 角色与当前任务授权。
API Protocol:
无新增或改名的 CLI/API，无需新配置。生成配置继续使用现有 managed-block 写入路径，保留用户自定义区块。
State / Concurrency:
不修改授权事件、摘要锁、Plan 激活、阶段顺序、Challenge 新鲜度或并发策略；Plan 未获当前用户批准前不改产品代码。只读 reviewer 无文件写权限。
Failure Modes:
- 缺失 micro 的真实方案会导致归档摘要失败，因此保留 Selected Option，禁止用验证通过措辞代替实际方案。
- 只修改文档未修改函数会继续触发 Learning；只修改函数会留下旧指导，因此对应行为与一致性检查同时覆盖。
- 测试夹具通过 replace 填可选字段可能静默失效；至少一条集成用例从当前精简模板生成 micro，并只填写仍需要的信息，证明完整路径。
- 重要信号和普通状态混合时不得误判为可豁免；不同阻塞项需单独组合验证。
Security / Permission:
真实用户授权、目标/范围/风险变化的停止点、supervised 人工 Plan 批准、独立审查、AC Coverage、E2E SKIPPED、归档和平台权限要求保持不变。测试中的 human:fixture 只用于隔离夹具，不能用于本任务授权。
Observability:
无需新增统计系统。通过精简模板是否仍默认要求四个重复字段、规则是否要求重复确认，以及普通修复任务是否出现 Learning blocker 衡量减法。真实执行结果和问题按现行要求记入 Execute Log。
Performance / Capacity:
取消普通状态触发会减少无意义制品；运行时仅收窄一个固定集合判断，无新增扫描、缓存或依赖。
Compatibility / Rollback:
保留原字段读取、Selected Option 摘要以及重要门禁。按代码/模板/指导作为一组回退，防止行为和提示再次分叉；不删除已存在的 Learning 文件。仓库外安装 Skill 的同步不在本轮范围。
Test Strategy:
- 先用相关行为测试确认变更前失败，再最小实现：learning 单元状态矩阵、实际生成 micro 的 CLI 集成、普通 Learning 豁免与重要条件混合场景、已有索引投影一致性。
- 防漂移矩阵包含：缺失/失败 AC、未完成 Completion Verification、失败/过期 Challenge、supervised 未获人工批准、Scope/Risk/Plan 漂移、缺失归档授权。
- 复用并补充现有 governance-contract / ai-config-parity 规则检查，验证正向指导且拒绝反向语义；不把单纯改旧断言当成行为证据。
- 实施后运行 npm test、sdd doctor 与 git diff --check；检查全部当前指导是否残留旧要求。测试中的完整归档链只操作隔离夹具，避免本 Spec 的前置验收依赖后置 Challenge。
- 实施与验证证据以 execute-log-file 为准；不从历史记录推断通过。
- Planning Validation: 已运行当前 Spec 的 sdd validate，仅报告 Plan Approved By 为空和 Execute Log 为空；这是待批准、未实施阶段的真实状态，不记为通过。sdd quality plan 已将七个 AC 映射到 unit/integration，现有 Profile 的 unknown role 仅产生 attention，不需要新增或确认 Profile。未执行任何 Provider。
Risks / Trade-offs:
保守减法保留了重要 Learning 和 Selected Option 的现有要求，收益小于全流程重构，但验证边界清楚且可回退。待本轮验证后再决定是否拆出专业能力或简化授权模型，不在本 Spec 内扩张。
