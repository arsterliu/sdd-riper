## Summary

当前阶段：Research。目标：补齐 Console 详情页对后端已计算但未渲染的高影响可观测性数据（Risk Flags、Design Method Advisory、Learning Triggers、Blockers 列表、Challenge Summary）。关键约束：Console 是只读投影，不参与流程流转；改动范围限定在 `src/web/console.js` 渲染层 + `src/web/console.css` 样式层 + `src/web/index.html` 结构层。

## Intake

### Requirement
<!-- SDD_REQUIREMENT -->
Console 详情页缺少 5 类后端已计算但前端未渲染的可观测性数据，影响对任务状态的判断。

### Constraints
- Console 是只读投影，不驱动流程流转，不新增写操作
- 后端 API 已通过 `parseSpec` 传回完整数据，无需修改后端
- 不新增 API 端点
- 保持现有功能不退化

### Scope
- `src/web/console.js`：新增渲染函数，读取 spec 对象中已有但未渲染的字段
- `src/web/console.css`：新增 Risk Flags、Design Method、Learning Triggers、Blockers 的样式
- `src/web/index.html`：新增 detail 区域 section 容器
- 不修改 `src/commands/console.js` 后端
- 不修改 `src/core/spec-index.js` 数据层

### Risks
- 前端渲染字段增多可能让详情页信息过载 → 需合理分区和折叠

### Initial Acceptance Hints
- 详情页可见 Risk Flags 标签（如有）
- 详情页可见 Design Method Advisory（方法 + 焦点字段 + 备注）
- 详情页可见 Learning Triggers（为什么需要 Learning）
- 详情页可见 Blockers 完整列表
- 详情页可见 Challenge Summary

## Research

### Requirement Review
1. **歧义**："可观测性缺口"范围需要明确——是只做高影响的 3 项还是全部 5+ 项？
2. **隐含假设**：假设后端 `parseSpec` 返回的 `workflow` 和 `completion` 对象已被完整序列化到前端 JS——需验证
3. **风险**：信息过载——详情页已有 Phase Progress、Artifacts、Archive Validation 三个大 section，再加内容可能导致页面过长
4. **外部依赖**：无

### Findings
1. `spec-index.js:parseSpec()` 返回的对象包含完整的 `workflow`（含 `riskFlags`、`designMethod`、`challengeSummary`、`blockers`、`reviewBrief`、`gateEvidence`）和 `completion`（含 `learningRequired`、`learningArtifact.triggers`），这些字段通过 `/api/specs/:id` 端点完整传到前端
2. `console.js` 前端只读取了 `spec.workflow` 中的 `gatePolicy`、`cruisePolicy`、`nextAction`、`challengeVerdict`、`backtrackTarget`、`gateEvidence`，以及 `spec.cruiseRun`——`riskFlags`、`designMethod`、`blockers`、`challengeSummary` 完全没读取
3. 前端 `renderBlocker()` 已有控制面信息展示区，但只渲染了文本行，没有结构化的分区卡片
4. 详情页 HTML 已有 `next-blocker`、`gate-list`、`artifact-list`、`validation-result` 四个 section 容器，没有 Risk / Design Method / Blockers 的容器
5. 现有 CSS 已有 pill（complete/progress/waiting/not-started）样式体系，可直接复用于 Risk Flags 标签

### Open Questions
1. 新 section 是插入现有 section 之间还是追加到末尾？
   - 建议：Risk Flags 和 Blockers 放在 Phase Progress 之前（状态概览优先），Design Method 和 Learning Triggers 放在 Artifacts 和 Archive Validation 之间
2. Blockers 列表是否只在有阻塞项时展示？
   - 建议：是的，无阻塞项时显示"无阻塞项"一行

### Assumptions
1. 前端 JS 能直接读取 `spec.workflow.riskFlags`、`spec.workflow.designMethod`、`spec.completion.learningArtifact.triggers`、`spec.workflow.blockers`、`spec.workflow.challengeSummary`——无需后端改动
2. 用户不需要折叠/展开控制——当前所有 section 都是展开的

### Confirmed Requirement
1. 详情页新增 **Risk Flags** 展示区：有 risk flag 时显示彩色标签（security→红、billing→橙、migration→蓝、public-api→紫、irreversible→红），无 flag 时显示"无风险标记"
2. 详情页新增 **Design Method Advisory** 展示区：显示 applies、methods、focusFields、notes
3. 详情页新增 **Learning Triggers** 展示区：显示触发原因列表，无触发时显示"不要求 Learning Record"
4. 详情页新增 **Blockers** 展示区：显示完整阻塞项列表
5. 详情页 **Challenge Summary** 在现有 blocker 卡片中追加显示
6. 不修改后端代码，不改数据模型，不新增 API 端点

## Innovate Options

### Option A：独立 Section 方案
每个可观测性维度（Risk Flags / Design Method / Blockers / Learning Triggers）各占一个独立 section，与现有的 Phase Progress、Artifacts、Archive Validation 并列。

- 优点：结构清晰、易维护、每个 section 职责单一
- 缺点：详情页 section 数量从 4 增到 7+，页面可能偏长
- 风险：信息过载，用户需要滚动
- 匹配度：高——与现有 section 组织方式一致

### Option B：合并到 Blocker 卡片方案
把 Risk Flags、Design Method、Blockers、Learning Triggers、Challenge Summary 全部合并到现有 `next-blocker` 卡片区域，作为一个增强版"控制面状态卡"。

- 优点：信息集中、减少 section 数量、用户一眼看全
- 缺点：单卡片信息密度高，渲染逻辑复杂
- 风险：卡片过长，反而降低可读性
- 匹配度：中——与现有 blocker 卡片定位冲突（blocker 是"下一步是什么"，新增的是"为什么/怎么做"）

### Option C：分组 Section 方案（推荐）
将新增内容分为两组：(1) **状态概览** section（Risk Flags + Blockers + Challenge Summary）放在 Phase Progress 之前，(2) **方法论 & Learning** section（Design Method + Learning Triggers）放在 Artifacts 之后。每个组是一个 section。

- 优点：结构有层次（状态概览→门禁进度→产物→方法论→归档校验），信息密度适中
- 缺点：比 Option B 多一个 section
- 风险：低
- 匹配度：最高——按信息类型分组，符合用户从"当前状态"到"怎么推进"的认知路径

### Rejected Options
- Option B：单卡片信息过载，违背"section 职责单一"原则

### Selected Option
**Option C：分组 Section 方案**
