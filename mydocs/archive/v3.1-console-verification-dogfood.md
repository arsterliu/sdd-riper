## Summary
Research 阶段：补全 Console 的 Verification 只读证据视图，并用真实 `playwright-test`/Chromium E2E dogfood v3.0。
当前 Console 已显示 Provider readiness 摘要，但缺少 Run 历史、freshness、AC×project 矩阵、诊断与附件元数据。
拟复用现有 Playwright fixture workspace，测试真实 Console 服务与受控项目数据；Console 不获得执行 Adapter 的能力。

## Intake

### Requirement
requirement: 补全 SDD Console 的 Verification Provider、不可变 Run、freshness、AC×project 覆盖与诊断可视化，并让 Console 自身通过 v3.0 playwright-test Provider 的真实 Chromium E2E Gate，以 dogfooding 验证 v3.0 前端消费能力；Console 保持只读，不增加执行按钮。
goal: 形成 v3.0 的首个真实自托管前端消费者，同时验证前端开发体验、Provider 初始化、@AC 映射、Run freshness 和控制面投影一致性。

### Constraints
constraints: 参考已归档 v3.0 Spec/Design 和当前 Console；无额外外部资料；不扩展 playwright-mcp、Custom Adapter、visual/a11y/performance；底层安全和包管理器异常仍由现有 contract tests 验证。

### Scope
增加 Verification 只读 API projection、Console Run/矩阵/诊断界面、响应式样式和真实 Playwright E2E；复用 v3.0 Provider/Adapter/Run 合同。必要时扩展 `spec-index` detail facts，但不改变 gate 判定所有权。

### Risks
Run 中含路径、进程输出和诊断，API 若直接暴露 run.json 会突破脱敏/containment 边界；E2E 若依赖当前仓库历史 Run 会不确定；若页面增加执行按钮会违反 v3.0 Console 只读合同。

### Initial Acceptance Hints
选择 Spec 后可观察 Provider、Adapter、配置、最新 Run、freshness、GateDecision、AC×project 和脱敏诊断；缺失 Provider/Run 有明确空态；页面无执行入口；真实 Chromium 测试用 `@AC-###` 建立多对多映射并由 `sdd verify run` 生成不可变证据。

## Research

### Requirement Review
需求包含两个相互绑定的交付物：补全 Console 的 Verification 可观测性，以及让该前端通过 v3.0 正式 E2E gate。前者验证 v3.0 的消费价值，后者验证 Provider 初始化、workspace 解析、Reporter、AC 标签和不可变 Run 的真实链路。

### Findings
1. `src/web/index.html` 已有只读 `Verification Provider` 区域，`renderProviderReadiness()` 只展示 state、required 和 missing，没有 Run 详情或矩阵。
2. Console detail API 直接返回 `specIndex.getSpec()`；`workflow.facts.providerReadiness` 已接入中央 evaluator，但没有面向 UI 的 Verification Run projection。
3. `run-store.runsForProvider()` 只读取并校验 Run Schema，不拥有当前 freshness；权威 freshness 由 `readiness.inspect()` 调用 `fingerprint.evaluateRunFreshness()` 动态计算。Console projection 必须复用共享 freshness/evidence helper，不信任持久化 `run.freshness`，也不复制 gate 判定逻辑。
4. 根 `package.json` production dependencies 只有 commander，不能为 dogfood 直接加入 Playwright。`tests/fixtures/playwright-workspace` 有独立 manifest/lockfile，但 `node_modules` 与 `.playwright-browsers` 被忽略；必须提供显式测试 bootstrap：按 lockfile 执行 `npm ci`，再通过本地 `playwright` script 安装 Chromium。该步骤属于开发/CI 准备，`sdd verify run` 不得隐式安装；Adapter Resolver 若发现 workspace-local `.playwright-browsers`，将其作为派生运行参数注入，不把调用者临时环境变量纳入 freshness；浏览器缺失时 gate 必须 BLOCKED/失败，不能 SKIP。
5. Console server 支持无项目启动、`POST /api/project` 选择项目和真实 spec detail。E2E global setup 必须创建唯一临时目录、初始化 Git 并提交基线、生成完整 SDD/Provider/Run 事实，随后启动唯一固定测试端口并等待 HTTP 就绪；配置固定 `workers: 1`，测试通过 API 选择唯一临时项目；global teardown 按记录的 PID 终止服务并删除 marker 所属临时目录，不依赖仓库历史 Run。选择 setup/teardown 直接拥有服务生命周期，是因为 Playwright webServer 在 Windows 上未能稳定回收 CLI 子进程树。
6. 当前测试已有 Console API/静态 UI断言与真实 Chromium fixture，可分层为 projection 单测、Console API 集成测试和 Playwright E2E。Projection 需要显式白名单 Schema：Provider/Adapter/config/projects、Run identity/status、动态 freshness+reasons、AC/project facts、重新脱敏且限长的 diagnostics，以及附件 `name/mediaType/size/sha256/受控相对路径`；禁止 process、environment、绝对路径、原始测试 ID、原始 Run JSON 或附件内容。

## Innovate Options
Option A（选择）：抽取共享 Verification Evidence Evaluator，由 readiness 和新的 Console Projection 共同消费。Projection 只输出版本化白名单 read model；Console detail API 按需加载，前端渲染 Provider、Run、矩阵与诊断。优点是 gate 与 UI 同源、边界清晰、可独立测试；代价是需要小幅重构 readiness。

Option B（拒绝）：在 `console.js` 中直接调用 Run Store 并自行计算 freshness/矩阵。实现较快，但会复制 gate 逻辑，未来容易出现 Console 显示 ready、中央 evaluator 却 blocked 的漂移。

Option C（拒绝）：把完整 `run.json` 返回浏览器，由前端自行聚合。开发量最小，但暴露 process/environment/路径等非 UI 字段，并把信任边界和业务判定推向浏览器，不可接受。

## 目标摘要
Research 阶段：补全 Console 的 Verification 只读证据视图，并用真实 `playwright-test`/Chromium E2E dogfood v3.0。

## 最终方案
选择 Option A：共享 Verification Evidence Evaluator + 安全 Console Projection + 真实 Playwright dogfood。中央 evaluator 拥有 freshness 与 AC×project evidence 选择；Console 只消费白名单 read model，不解析 Run 原文。

## 关键约束
Core production dependency 不增加 Playwright；E2E 只使用 fixture workspace 显式声明且 lockfile 管理的 `@playwright/test`，并由独立 bootstrap 显式安装 Chromium；Console API 对所有浏览器可见动态字符串执行白名单、二次脱敏、限长及相对路径 containment；E2E 固定单 worker，临时项目清理必须同时验证 temp realpath、专用前缀、marker kind/token 和记录 PID，并等待服务退出。

## 坑点与风险
共享 evaluator 重构可能影响 readiness，需状态矩阵回归。E2E bootstrap 增加 CI 时间，但换取干净环境可复现。固定单 worker牺牲速度，避免 Console 全局项目选择互相污染。
