## Learning Record

Source Spec: mydocs/specs/v3.8-visual-context-guidance.md
Trigger: Challenge 先后发现 Profile 聚合范围和前端/混合任务可选择 ui-impact=no 的绕过路径；随后又发现 Execute Log 的错误插入顺序使最终审计不忠实。
Observed Problem: 仅在字段为空时推导 Profile，或仅依靠命令输入合法性，会让已绑定前端/混合范围的任务持久化矛盾的 no/not-applicable 状态；而以模板锚点追加执行记录时，可能命中注释中的同名文本并破坏事实顺序。
Root Cause: 一次性选择的业务不变量没有同时在写入入口和读取/工作流层落实；日志追加没有使用唯一的文件末尾锚点，也没有在最终 Challenge 前核对物理顺序与最后 completion-verification。
Decision Rule: 对由不可变 Profile 和 affected-units 已证明包含 frontend 的 Spec，ui-impact 必须为 yes，命令写入前拒绝矛盾选择，普通工作流也必须把手工写入的矛盾状态阻塞；未知或纯后端范围保留人工选择空间。Execute Log 只能追加到真实文件末尾；若历史记录已错序，保留历史并追加勘误和新的最后完成验证，不改写过去。
Applies When: 新增任何由 Profile、清单或其他权威元数据推导的用户选择；以及为 Standard/Lite Spec 追加 Execute Log、Completion Verification 或 Challenge 修复事实时。
Does Not Apply When: 没有权威元数据能够确认前端影响时；此时只能引导确认，不能把未知当成前端事实。对已经归档的历史制品，不应通过重写改变其审计顺序。
Recommended Action: 先为命令入口、手工篡改和 workflow 投影分别写回归测试；使用同一份精确绑定数据在写入与验证两层判断；提交前检查 Execute Log 的真实末尾、最后一个 completion-verification 是否覆盖最新修复与全量测试，再发起 Challenge。
Evidence: tests/visual-context-workflow.test.js 覆盖 project 聚合、frontend/mixed 的 no 拒绝、backend/unknown 允许及手工篡改 blocker；最终全量 node --test tests/*.test.js 为 399 tests、394 PASS、0 FAIL、5 SKIPPED；最终 Challenge PASS。
