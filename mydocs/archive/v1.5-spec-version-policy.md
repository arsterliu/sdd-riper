## Summary
当前任务调整 Spec 创建与版本策略：保留现有 `vN.M` 兼容，同时新增 `vN.M.P` 支持。
`version` 明确定义为迭代 / 交付批次聚合键，`version + task-name` 是 Spec 唯一键。
创建 Spec 前，agent 不得自行决定 `version` 和 `task-name`，必须由用户输入或确认，并询问是否有参考资料。
实现需覆盖 CLI 校验、文件解析、归档 / reopen 路径解析、文档与 agent 指南。

## Intake

### Requirement
requirement: 同时支持 vN.M 与 vN.M.P 两种 Spec version；version 表示迭代或交付批次，同一 version 下 task-name 必须唯一；创建 Spec 前 agent 不能自主决定 version/task-name，必须人工输入或确认，并询问参考资料。

### Constraints
constraints: 兼容已有 `vN.M-*` 文件；不引入 revision / 全局 spec-id；先保持现有平铺目录结构；用测试证明两段和三段版本均可工作。

### Scope
包含 `discover` 版本校验、公共 spec 文件名解析、latest/source spec 选择、archive/reopen/spec-index/new-learning 等依赖版本正则的路径，以及 README/GUIDE/SKILL/AI 配置生成文案。

### Risks
旧正则分散在多个模块，若只改 `discover`，console、archive、reopen 仍可能无法识别 `vN.M.P`。
agent 指南若只写“可建议”而不写“必须人工确认”，仍可能继续静默推导版本和任务名。

### Initial Acceptance Hints
`discover --version v1.3.6 --task-name sdk-adapter` 应创建同名前缀的 Spec / Design / Execute Log。
`v1.3.6-sdk-adapter.md` 与 `v1.3.6-api-contract.md` 可并存；重复 `v1.3.6-sdk-adapter.md` 必须被拒绝。
README/SKILL 应要求创建前确认 version、task-name、requirement、context-source。

## Research

### Requirement Review
用户明确要求同时支持两位和三位版本号，现实中两者都会存在；因此不能简单把旧 `vN.M` 迁移为 `vN.M.P`。
用户明确反对 AI 自主决定创建 Spec 的核心字段；这属于流程门禁，不应只靠口头约定。
版本语义是并行开发中的聚合键：同一版本下可以拆多个任务，成员并行开发不同 `task-name`。

### Findings
当前 `discover` 要求 `--version/--spec-version` 必填，但正则只允许 `vN.M`。
`common.versionExists` 已经按 `version + task-name` 检查唯一性，但错误信息没有说明“同版本任务名唯一”。
`findLatestSpec`、`findSourceSpec`、`normalizeSlug`、`spec-index.parseFileName`、`archive`、`reopen`、`new-learning` 均存在只匹配两段版本的正则。
`bin/cli.js` 已支持 `--version` 作为 `--spec-version` 别名；本次不改命令接口。
`SKILL.md` 当前 `discover` 示例仍可能让 agent 直接创建 Spec，需要补充“先收集并确认 version/task-name/context”的硬规则。

### Open Questions
无。用户已确认版本 `v1.5`，任务名授权由我推荐，参考资料为 `none`。

### Assumptions
`1.5` 规范化为 CLI 版本格式 `v1.5`。
本任务不改变目录结构，仍使用 `mydocs/specs/v1.5-task.md` 这类平铺路径。
三段版本的排序按 major、minor、patch 递减；两段版本的 patch 视为 `0`。

### Confirmed Requirement
同时支持 `vN.M` 与 `vN.M.P` 两种 Spec version。`version` 表示迭代 / 交付批次，同一 version 下允许多个并行 Spec，但 `task-name` 在该 version 内必须唯一。创建 Spec 前，agent 必须让用户输入或确认 `version` 与 `task-name`，并询问是否有参考资料 / context；agent 不能静默推导这些核心字段后直接执行 `discover`。

## Innovate Options
Option A: 最小扩展现有 `vN.M-task` 模型，允许 `vN.M.P-task`，并集中版本解析。
Pros: 兼容旧文件；改动面可控；符合用户“保留当前格式并扩展三位版本”的要求。
Cons: 仍是平铺目录，大版本下任务很多时列表会较长。
Risks: 必须清理所有两段版本正则，否则行为不一致。
Requirement Fit: 高。

Option B: 改为 `version/task-name.md` 分组目录。
Pros: 聚合更直观。
Cons: 会牵动 archive、console、artifact 引用和历史路径，超出当前需求。
Risks: 迁移成本高。
Requirement Fit: 中。

Option C: 引入全局 spec-id / revision。
Pros: 唯一性强。
Cons: 用户已指出 revision 管理复杂，且不符合“同 ID 下不同任务聚合”的模型。
Risks: 流程负担变重。
Requirement Fit: 低。

Selected: Option A。先把版本格式、唯一性语义和 agent 创建门禁做准确，保留未来目录分组的可能。

## Plan
1. 在公共层增加或复用统一版本正则 / 解析能力，支持 `vN.M` 和 `vN.M.P`，并让版本比较包含 patch。
2. 先写失败测试：覆盖 discover 三段版本创建、两段兼容、同版本任务唯一、三段版本 latest/source/archive/reopen 解析、AI 指南文案。
3. 修改 `discover` 校验与错误提示，保留 `--version` / `--spec-version` 接口。
4. 修改 `common`、`spec-index`、`archive`、`reopen`、`new-learning` 等只识别 `vN.M` 的正则。
5. 更新 `SKILL.md`、README/GUIDE 和 init 生成的 AI 配置文案，明确 agent 创建 Spec 前必须人工确认 version/task-name 并询问 context。
6. 运行 `node --test tests/*.test.js`，把结果和 AC 覆盖写入 Execute Log。
