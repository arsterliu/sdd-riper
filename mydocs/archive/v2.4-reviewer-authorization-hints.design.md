## Design Note

Approach:
采用提示层最小改造：新增一个平台无关的 reviewer 授权提示常量/文案，输出到 `sdd challenge` prompt、`sdd next` blocker 场景和 validation guidance；同时更新生成 AI config 与顶层文档。现有 reviewer 类型校验保持不变：standard/lite 只接受 `subagent:<id>`、`external-agent:<id>`、`human:<name>`，micro Challenge 额外接受 `inline`。

核心文案应表达三件事：
1. 可审计 reviewer 类型：`subagent:<id>`、`external-agent:<id>`、`human:<name>`；micro Challenge 可用 `inline`。
2. 自动化 reviewer 覆盖 subagent、external-agent、review bot 或其他 agent 平台工具；只要当前宿主环境要求授权，执行者就必须暂停并主动请求用户显式授权后再继续。
3. 不得跳过 Research / Challenge gate，不得伪造 reviewer。
Impact Scope:
影响 CLI 用户提示、validation blocker、生成的 AI 指令、顶层文档和测试。不会改变 `--executed-by` 参数、Spec 字段、Challenge verdict、archive readiness 逻辑或实际 agent 调度行为。
Interface / Data Impact:
CLI 输出新增若干提示行；错误码和输入参数保持不变。持久化数据格式不变，不新增 frontmatter 或 Spec 字段。文档中的 reviewer 类型表达与代码保持一致。
Compatibility:
旧 Spec、旧 Challenge evidence 和现有测试夹具继续有效。新增提示只增加输出内容，不删除现有关键字符串；测试应避免要求精确全文匹配。`external-agent:<id>` 继续作为第三方 agent、review bot、CI reviewer 等平台的通用承载类型。
Risks:
主要风险是文案重复后再次漂移，因此测试要覆盖 CLI 和关键文档/生成配置。另一个风险是把“需要授权”误读成 SDD 自己管理授权，本设计只要求提示执行者暂停并主动请求用户显式授权，不让 CLI 代替宿主平台判断授权状态。
Test Strategy:
使用 node:test 回归测试。先写失败测试，覆盖 `sdd challenge` prompt、`sdd next` 缺 Challenge blocker、生成 AI config 文案、顶层文档/skill 文案一致性，以及 “pause and request explicit user authorization before proceeding” 主动请求授权措辞；实现后运行 targeted tests，再运行 `node --test tests/*.test.js` 和 doctor。
