## Technical Design

Selected Option / ADR:
ADR-001：选择“Spec 显式启用 + Context 结构化清单”。任务只有在明确需要视觉保真或 UI 设计质量确认时才通过 `sdd visual init` 启用；命令为目标 Spec 创建清单并写入引用。相比仅约定文档，该方案有稳定、可解析的输入；相比直接接入视觉 Provider，它不预设浏览器、diff、阈值或基线存储机制。
Requirement Traceability:
- 视觉依据可追溯：`visual-evidence-file` 引用任务 Context 内的结构化清单，覆盖 AC-001、AC-002。
- 有稿/无稿均不误导：清单的 `mode` 区分 `fidelity` 与 `direction`，批准信息独立记录，覆盖 AC-003。
- 不改变既有门禁：检查只形成 Plan 前信息与既有 AC 可引用的证据，不向 Archive 增加新的全局条件，覆盖 AC-004、AC-006。
- skill 负责条件式引导：生成的 agent 配置在识别到视觉需求后提示启用与检查，覆盖 AC-005。
Impact Scope:
修改 CLI 命令注册、Spec frontmatter 模板、Spec 创建/选择辅助逻辑、工作流/校验的只读投影、agent 配置生成、README/GUIDE/INTEGRATIONS 与 Node 测试。新增视觉合同解析/检查模块、`visual` 命令和 Context 清单模板。不会修改 Profile、Quality、Verification Provider/Run、Console、Archive 存储格式或业务项目代码。
Context / Boundary:
视觉合同只处理项目内活动 Spec 及其 `context-source` 所指的任务 Context。外部 URL（例如 Figma）只能作为来源文本保存，不发起网络访问；本地来源和基线均须解析为任务 Context 下的文件。合同不生成设计稿、不抓取截图、不运行浏览器，也不判断像素是否相同。
Domain Model:
Visual Evidence Contract 是与 Spec 一对一的可选只读模型。Spec 是启用意图与清单定位的权威；Context 清单是来源、场景、基线与批准事实的权威；Design 说明如何消费该合同；Execute Log 与现有 AC 保存实际执行和人工证据。合同状态由输入派生，不写回清单：`not-applicable`、`blocked`、`pending-approval`、`ready`；`direction` 在方向批准后可为 `ready`，同时以 `baseline: pending` 表示首版截图需在 Execute 中补齐。
Architecture View:
`src/commands/visual.js` 是唯一写入入口，负责解析指定 Spec、确认或创建默认 `mydocs/context/<task-name>/`、复制清单模板，并原子更新该 Spec 的两个 frontmatter 字段。`src/visual-evidence/` 提供无副作用的 parse、路径 containment、schema validation 与 readiness projection。`src/core/workflow.js`、`src/commands/next.js` 和普通 `validate` 只读取 projection，在启用任务未就绪时提示/阻止 Plan 审批；`validate --archive-ready` 不调用这条额外门禁。`_gen-ai-configs.js` 把条件式引导写入生成的宿主 skill 配置。所有模块只通过普通对象和稳定诊断 code 通信。
Data Model / Schema:
Spec frontmatter 新增 `visual-evidence: "" | "required"` 与 `visual-evidence-file: ""`。清单采用项目内 JSON：`schemaVersion: 1`、`mode: "fidelity" | "direction"`、`sources[]`、`scenarios[]`、`approval`。每个 scenario 包含稳定 `id`、`route`、`state`、`viewport { width, height }` 与 `baseline { path | "", status: "approved" | "pending" }`。`fidelity` 要求每个关键场景具有可定位的来源和已批准基线；`direction` 要求可读的方向来源和 `approval.approvedBy: human:<name>` / ISO 时间，允许 baseline 为 pending。解析器拒绝未知 schemaVersion、重复 id、空 route/state、非法视口、缺必填批准和越出 Context 的本地路径。
Data Migration / Backfill:
不做迁移或回填。缺少 `visual-evidence` 的全部历史 Spec 一律投影为 `not-applicable`；不会扫描旧 Context、猜测截图或修改已有文件。
Interface Contract:
新增 `sdd visual init <project-dir> --spec <path-or-name> --mode <fidelity|direction>`。该命令只允许操作已解析且位于项目内的活动 Spec；如果 Spec 没有 context-source，则创建并绑定默认任务 Context；若已有 Context 不可写、清单已存在或路径不在项目允许范围内，则 fail-closed 并输出稳定诊断。新增只读 `sdd visual inspect <project-dir> --spec <path-or-name>`，输出 `VISUAL_EVIDENCE_STATE`、`PLAN_READINESS`、`BASELINE_STATUS` 与 diagnostics。普通 `sdd validate` 和 `sdd next` 对启用且未 ready 的任务报告同一诊断；未启用任务不增加输出或阻断。
API Protocol:
无 HTTP API、Provider API 或外部网络协议变更。CLI 输出沿用键值行与诊断列表的既有风格；错误 code 至少包括 `VISUAL_EVIDENCE_NOT_ENABLED`、`VISUAL_EVIDENCE_FILE_MISSING`、`VISUAL_EVIDENCE_SCHEMA_INVALID`、`VISUAL_EVIDENCE_PATH_OUTSIDE_CONTEXT`、`VISUAL_EVIDENCE_APPROVAL_PENDING`。这些 code 是面向 skill 与后续 Console/Provider 的稳定边界，详情文本不得泄漏绝对路径或外部 URL 中的敏感查询参数。
State / Concurrency:
`init` 写清单前检查目标不存在，并以临时文件后 rename 的方式写入；更新 Spec 前再次确认其路径、任务名与 context-source，防止误写其他任务。`inspect`、`next`、`validate` 无写入、无重试；并发修改造成读取失败时返回 `blocked` 与稳定诊断，下一次调用重新读取。
Failure Modes:
未启用任务返回 `not-applicable`；已启用但缺清单、JSON 错误、schema 不支持、文件引用不存在、路径越界或字段不足返回 `blocked`；有可读依据但缺人工批准返回 `pending-approval`；满足对应 mode 的 Plan 前最小条件返回 `ready`。`direction` 的 `baseline: pending` 仅表示 Execute 后仍需在相关 manual AC 中补充证据，不能被误报为视觉比对已通过。
Security / Permission:
所有 Spec、Context 与基线路径均先做 lexical 与 realpath containment；拒绝符号链接逃逸、绝对路径和 Context 外相对路径。`init` 只在用户已选中的活动 Spec 及其 Context 写入，不执行命令、安装依赖、访问浏览器或网络。批准人必须是 `human:<name>`；它是审计声明，不做身份认证。
Observability:
`inspect` 和工作流提示输出稳定状态、缺失字段和恢复动作；Execute Log 仍记录截图文件、人工复核和对应 AC 的证据。不会记录设计文件完整 URL、机器绝对路径或环境变量。
Performance / Capacity:
每次检查只读取一个小型 JSON 清单及其声明的本地文件元数据；不递归扫描 Context、图像解码或计算像素 diff。复杂度随 scenario 数量线性增长，适用于常规任务级清单。
Compatibility / Rollback:
所有字段和命令均为加法式。未启用字段的旧 Spec、既有 `sdd discover`、功能 E2E、Provider readiness、Console 和 Archive 行为保持不变。回滚时删除 visual 命令和只读投影即可；已存在的 Context JSON 与 frontmatter 字段可被旧版本忽略，不需要数据回滚。
Test Strategy:
以 `node --test` 覆盖纯解析器、schema 与 containment、`visual init` 的精确写入边界、`visual inspect` 的四种状态、`next`/普通 `validate` 的 Plan 前提示、`validate --archive-ready` 与未启用/旧 Spec 的不变性、生成 skill 文本中的条件式指引，以及完整回归 `npm test`。不引入浏览器、Playwright 运行、网络或新依赖。对 `direction` 的首版基线使用受控 fixture 的 manual AC/Execute Log 证据模拟，而非像素比对。
Risks / Trade-offs:
JSON 对机器校验友好但不如 Markdown 随意；通过模板、文档和 `visual init` 降低填写成本。首版不把视觉状态加入 Archive Gate，降低对已有项目的破坏性，但依赖任务 AC 诚实覆盖基线补齐；Challenge 将检查视觉任务是否遗漏该 AC。后续 visual Provider 必须保持对 schemaVersion 1 的兼容，不能把 `ready` 误解释为像素 diff PASS。
