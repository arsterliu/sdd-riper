## Learning Record

Source Spec:
mydocs/specs/v3.0-verification-adapter-framework.md
Trigger:
归档 v3.0 reopen 后将双锁模型收缩为项目级单锁；Execute Log 出现 BUGFIX，Challenge Finding 为 `EXISTING_RULE_APPLIES`。
Observed Problem:
原实现为一个低频、显式配置命令引入 Provider 竞争锁、配置等待锁和并发合并语义，扩大了错误、恢复与测试状态空间；用户确认该命令无需支持同一项目并发执行。
Root Cause:
既有设计把“共享配置读改写需要事务保护”扩展成“不同实体应并发合并、同实体应竞争成功”，超出了命令的实际吞吐和可用性需求。
Decision Rule:
复用归档 Learning 的边界：原子替换不等于事务安全，共享配置仍需事务锁；但当命令是低频、显式、幂等覆盖且产品不要求实体级并发成功时，不引入实体竞争锁、等待或合并。使用单一共享锁 fail-fast，调用者稍后重试。
Applies When:
项目初始化器、配置生成器或其他低频显式命令修改单个共享文件，并且同一项目并发执行不属于产品合同。
Does Not Apply When:
业务明确要求并发调用必须成功、存在高频写入吞吐目标，或不同实体更新必须自动合并；这些场景需要另行设计事务存储与并发控制。
Recommended Action:
设计文件型配置写入时先确认是否真的需要并发成功。若不需要，锁外做不读取共享状态的静态 preflight；单次非阻塞获取共享锁；锁内完成读取、修改、校验和原子写入；冲突 fail-fast 并由调用者重试。测试覆盖锁冲突、事务失败释放、原配置保护、解锁失败、双错误和重试。
Evidence:
单锁聚焦 8/8 PASS；CLI 20/20 PASS；关联 75 PASS、1 SKIP；全量 250 PASS、1 SKIP；旧双锁运行时/当前指南扫描零匹配；独立 Challenge 四轴 PASS。
