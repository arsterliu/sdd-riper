## Summary
<!-- 3-5 lines in Chinese: current phase, goal, key constraints, latest progress. -->

当前处于 Research 完成、方案探索待确认阶段。v4.5 承接 v4.0 第四项路线的第二阶段，并以已归档 v4.4 的合同/运行态边界为前提，只处理两条 Playwright 链路中语义完全同构的基础设施重复。可共享对象严格限于进程结果判定、Reporter 生命周期与不可变存证事务骨架；Visual 与普通 Verification 的领域模型、Run schema、目录、错误码和信任边界继续隔离。本期不涉及用户界面或视觉设计合同。

## Intake

### Requirement
requirement: 承接 v4.0 路线图第四项的第二阶段，在已完成 v4.4 合同检查与运行态投影边界分离的基础上，仅提取并复用完全同构的 Playwright 结果协议、Reporter 生命周期和不可变 Run 存证事务骨架；继续保持 Visual 与普通 Verification 的领域模型、Run schema、目录、信任边界和失败语义独立。
goal: 在不改变现有 CLI、Provider allowlist、静态映射、realpath containment、fail-closed 规则或历史制品读取语义的前提下，减少两条验证链路中精确重复的受控执行与存证基础设施，并为后续维护建立可验证边界。

### Constraints
constraints: 参考已归档 v4.0、v4.3、v4.4 制品；不合并 Visual 与普通 Verification 的 Run schema、namespace、AC×project 与 scenario/pixel 领域模型；不增加公开 CLI、网络入口、任意命令/URL/环境输入或跨请求缓存；Research 与 Challenge 的独立审核均须在用户明确授权后派发。

### Scope

- In Scope: 提取并复用两个 Playwright adapter 中具有相同状态优先级与精确输出的进程结果判定协议；抽取受控的 Reporter 生命周期工厂；在两个既有 Run-store wrapper 之下提取 validate-first、realpath-first、staging、附件复制、`wx` 写入、二次碰撞检查与 `rename` 提交的内部事务骨架。
- In Scope: 为共享内核建立跨 adapter 的等价性回归，并冻结普通链的 tags/AC 覆盖语义与 Visual 链的 scenario/PNG/pixel/baseline 语义；验证已有 CLI、readiness、历史 Run 读取与错误码不变。
- Out of Scope: 合并 `run()` 与 `runVisual()` 高层编排、normalizer、adapter/Provider manifest、Run schema、namespace、reader/sort、Visual static mapping、baseline/diff，或把共享 helper 扩展成接收任意命令、URL、selector、环境或路径输入的通用执行器。

### Risks

- 将“语义同构”误判为“领域可合并”，可能遗失普通链的 AC tags 或 Visual 链的静态 scenario/PNG 约束，造成伪 PASS、错误覆盖或不可信证据。
- 改变 process-result 判定顺序，可能把 timeout、signal、Reporter 缺失或非零退出错误投影为普通 FAIL 或 PASS。
- 将 transaction helper 的 namespace、validator 或 realpath 检查改成动态输入，可能扩大目录/工作区信任边界，或在畸形 Run 时留下可观察目录。
- Windows `core.autocrlf=true` 下全量测试需要显式记录仅用于测试进程的 LF 归一化前置条件；不得把该结果误述为裸 `npm.cmd test`。

### Initial Acceptance Hints

- 两个 adapter 对相同 process/Reporter 终态输入输出完全一致的状态、gateDecision、诊断 code 与判定优先级；旧模块路径继续可用。
- 共享 Reporter 仍保持 hello→test*→end、nonce/version/capability 的失败关闭握手；普通链保留 tags，Visual 链不暴露 tags。
- 两个 Run-store wrapper 继续各自验证领域 schema、使用静态 namespace 和原错误码；共享事务不接受未验证的 root、namespace 或 Run 内容。
- 普通 `verify run` 与 `verify visual` 的资格分支、受控调用、存证字段及读写隔离保持兼容，Visual 不得写入普通 Verification Run。

## Research

### Requirement Review

v4.0 F-007 将“仅合并完全相同的协议与事务骨架”列为可接受的去重路径，F-008 同时禁止把路径原语扩大为跨领域信任策略。v4.4 已先完成合同检查与 Visual Run 投影分离，因此本期不再触碰合同/运行态边界，而是只在两个受控 Playwright adapter 和两条 immutable Run commit 链路中识别精确同构部分。用户已确认将该工作单列为 v4.5，并继续以 v4.0、v4.3、v4.4 归档制品为约束。

### Findings

- `playwright-test/result-contract.js` 与 `playwright-visual/result-contract.js` 的 `evaluate(processResult, endEvent)` 判定顺序和安全输出语义一致；差异仅为排版，适合抽为内部 evaluator，但必须冻结 timeout、signal、缺 end、interrupted、failed、非零退出和 PASS 的优先级。
- 两个 Reporter 都执行输出文件/nonce 校验、JSONL emit 与 hello→test*→end 生命周期；普通 payload 包含 tags，Visual payload 刻意不含 tags，且两个 manifest capability 分别为 `gate` 与 `visual-gate`，因此只可共用生命周期骨架，不可共用 payload 语义或 adapter 身份。
- `process-gateway.js` 已是唯一 shell:false、已验证 Playwright 调用与环境白名单入口，`attachment-store.js` 已是唯一附件 realpath/限额/hash/copy 原语；本期不重复抽取它们。
- 普通和 Visual Run-store 的 validate→workspace realpath→静态目录→collision→staging→附件→`run.json` `wx`→二次 collision→rename→cleanup 骨架同构；但 validator、namespace、Run root fields、reader/sort、错误码和领域字段不同，只能由 domain wrapper 继续独占。
- 普通 normalizer 基于 AC tag × project，Visual normalizer 基于静态 scenario binding、唯一 PNG 与像素 diff；高层 `run()` / `runVisual()` 还分别承载 allowEnv/脱敏 与 fidelity/baseline/diff，禁止合并。
- v4.3 冻结 Provider config/Registry/Run-store 错误语义且禁止 freshness 跨请求缓存；v4.4 冻结 Visual/Verification 双 schema、双目录以及 allowlist、static mapping、realpath、baseline approval 与 fail-closed 边界。

### Open Questions

无。用户已确认本期仅进行第二阶段的精确去重；共享边界、禁止合并对象与参考制品已由 Research 固化。

### Assumptions

- 内部共享模块可新增，但不得成为新 CLI、Provider capability、公开配置或跨请求缓存的入口；两个 adapter 和两个 Run-store 保留现有导出与调用路径。
- 共享事务仅接收 wrapper 已完成领域校验后的受控参数；namespace、错误工厂、validator、reader 与领域 Run 构建保持在 wrapper 内。
- 全量测试在当前 Windows 工作区使用只读临时 LF 归一化预加载时可重复；该环境前置条件将在 Plan、Execute Log 和 Challenge 证据中完整记录。

## Innovate Options
<!-- Compare at least two options. Write the option analysis in Chinese. -->

### Option A — 分阶段抽取精确同构基础设施（推荐，已选）

Option Summary: 先以 table-driven parity 固定 process-result evaluator 与 Reporter 生命周期，抽为内部共享模块并保留两个 adapter wrapper；第一阶段回归通过后，再抽取 Run-store 的 immutable transaction helper，两个 domain wrapper 继续独占 validation、namespace、error code、reader/sort 与 Run 构建。
Pros: 每一步都有小而可验证的行为边界；优先冻结最容易误报 PASS/FAIL 的协议；事务抽取在协议稳定后进行，便于定位回归和独立回滚。
Cons: 短期会保留更多薄 wrapper，提交数量可能多于一次性重构。
Risks: 若共享 helper 越过已验证输入边界，仍可能扩大信任范围；必须以 wrapper 常量和测试证明 helper 不接受动态 namespace/root/target。
Requirement Fit: 完整满足 v4.0 F-007 的“仅合并精确同构协议/事务”与 F-008 的跨域边界限制，也符合用户确认的第二阶段拆分范围。

### Option B — 一次性建立统一 Playwright 基础内核

Option Summary: 同时抽取 result contract、Reporter、transaction，并让两个 adapter 与 Run-store 同期接入。
Pros: 共享文件数量最少，表面重复消除更彻底。
Cons: 同时改变协议、生命周期与落盘路径，失败定位和回滚范围更大。
Risks: 容易把 tags、AC×project、scenario/pixel、capability 或错误码错误参数化，形成看似通用但跨越领域信任边界的内核。
Requirement Fit: 仅部分匹配；虽然能减少重复，但不符合当前优先小步可验证和严格隔离的约束。

### Option C — 只增加等价性测试、不做提取

Option Summary: 为两条链路添加快照/表驱动测试，保留现有重复实现。
Pros: 实现风险最低，完全不影响生产代码。
Cons: 无法消除 v4.0 F-007 识别的精确重复，也无法为后续维护提供单点修复。
Risks: 重复实现继续漂移，后续修复仍需双改。
Requirement Fit: 只能作为 Option A 的前置测试策略，不足以完成本期目标。

Selected Option: Option A — 分阶段抽取精确同构基础设施
Selection Rationale: 用户明确选择 A。它将可共享的协议与事务拆成两个可独立验证、可独立回滚的步骤，同时以 wrapper 保留所有域内 schema、namespace、信任策略和失败语义，最贴合 v4.0/v4.4 已冻结的边界。
